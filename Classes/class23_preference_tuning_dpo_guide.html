03 — Core Concept

What is Preference Tuning?

Why It's Needed

After Stage 1 (domain knowledge) and Stage 2 (instruction following), the model can answer questions — but not necessarily in the way humans actually prefer. The model might give technically correct but practically unhelpful responses. Preference tuning fixes this.

Definition
Preference Tuning = aligning the model with human preferences
by training it to prefer chosen responses over rejected ones
"We are doing preference tuning to align the model with human responses. ChatGPT has done this particular training, and you will find that in many enterprises, we are doing this kind of training."

Sunny's Exam Analogy (from the Blackboard)

Sunny used this specific example to illustrate what preference tuning does:

Preference Tuning Illustrated
PROMPT (user question)
"How to prepare for the exam within 48 hours?"
REJECTED (poor answer)
Study 48 hours continuously without a break.
✗ Unhealthy, impractical advice
CHOSEN (better answer)
Take the important questions. Learn from previous question papers. Take short breaks between study sessions.
✓ Practical, balanced, helpful
Goal: Train the model to always prefer the chosen response over the rejected one. Do this across many examples → model learns what "better" looks like.

The Preference Data Format — 3 Required Columns

Unlike SFT (3 columns: instruction, input, output), preference data has a different structure:

Preference Dataset Structure — JSONL format
prompt
The user instruction / question. What the model is asked.
chosen
The BETTER (preferred) response. What humans would prefer as the answer.
rejected
The WEAKER (rejected) response. What the model should learn NOT to produce.
+ Optional metadata columns: source, page, topic — stored in the dataset for traceability

Sunny's dataset for this class: pharma_preference_dataset.jsonl — 48 rows, pharma domain, 3-column preference format (prompt / chosen / rejected), split 80/20 → 8 rows for validation. Created manually with SME help for a realistic production simulation.

Creating the Preference Dataset

"If you are working in any real-time project, let's say you are working for a pharma company, for healthcare, for aviation — you are going to be training your own LLM. In that case, you will create this data manually. You will take the help of Subject Matter Experts, and they will help to create this kind of data. Otherwise, you can create this data with the help of AI — give the required document to AI, give the appropriate prompt, and based on that knowledge, AI will generate the data for you."

Method 1: Manual (SME)

Human Subject Matter Experts review AI responses and label which are chosen (preferred) vs rejected. Slow but highest quality. May take 6 months to 2 years for large datasets. Best for production.

Method 2: Synthetic (AI-generated)

Provide domain documents to a stronger LLM (GPT-4, Claude) with a prompt asking it to generate preferred and rejected response pairs. Faster but quality depends on the generating model.

04 — The Methods

4 Preference Alignment Algorithms

Sunny explained all 4 algorithms, clarifying which use reinforcement learning and which don't. In today's practical, DPO is demonstrated. RLHF will be shown in the next class; GRPO and ORPO are self-study assignments.

RLHF + PPO
Reinforcement Learning from Human Feedback
RL-based · Introduced by OpenAI

The original alignment framework used by OpenAI. Uses PPO (Proximal Policy Optimization) — an actor-critic reinforcement learning algorithm. Requires a separate reward model. Complex to implement. Now largely considered outdated in the current context.

GRPO
Group Relative Policy Optimization
RL-based · Introduced by DeepSeek

An updated version of PPO, introduced by DeepSeek. Still uses reinforcement learning but is more efficient. Very popular currently — used in DeepSeek B4. Available in HuggingFace TRL. Given as self-study/assignment.

DPO ← Today's Focus
Direct Preference Optimization
Non-RL · Stanford University · NeurIPS 2023

Eliminates the need for a reward model and RL training. Trains directly on (prompt, chosen, rejected) triplets using maximum likelihood. Much simpler than RLHF. The language model itself acts as a secret reward model. Most popular for practical implementation today.

ORPO
Odds Ratio Preference Optimization
Non-RL · Advanced DPO variant

An advanced version of DPO. Still non-RL, no reward model needed. Available in HuggingFace TRL. More recent improvement over DPO. Given as self-study/assignment alongside GRPO.

05 — Architecture Deep Dive

The 3-Stage LoRa Merge Pipeline

Sunny drew this on the blackboard and spent significant time on it. This is the sequential pipeline used in industry-grade multi-stage fine-tuning.

Sequential Merge Approach (Sunny's Recommended Method)
M0 (Base Model)
+
L1 (CPT Adapter)
→ Merge →
M1
← used as base for Stage 2
M1
+
L2 (SFT Adapter)
→ Merge →
M2
← used as base for Stage 3
M2
+
L3 (DPO Adapter)
→ Merge →
M3 ✓ FINAL MODEL

Two Approaches: Merge vs Runtime Append

Approach 1: Sequential Merge (Recommended)

M0 + L1 → M1 → M1 + L2 → M2 → M2 + L3 → M3. Each stage gets the full knowledge of all previous stages baked into the weights. Simple, predictable, inference-ready model (M3) without any adapter loading.

Approach 2: Runtime Append (Flexible)

Keep M0 as base. Load any adapter (L1, L2, or L3) at inference time. Allows routing — different tasks use different adapters. More flexible but requires careful adapter selection. Code commented in notebook.

The Class 10–12 Analogy (Why You Can't Skip Stages)

"M0 model is a raw model — which is a Class 10 student. M1 model is a merged model, where we have Class 10 knowledge AND Class 11 knowledge (L1 LoRa). M2 is again a merged model with the M1 stage knowledge and L2 LoRa — this is the Class 12 student. Now, just think — if this particular M0, we are going to append L2, it's Class 10 and Class 12. Is this combination fine? No, it is not fine, because in between, Class 11 is missing. Class 11 knowledge is missing. This is a complete analogy which I'm trying to explain. Don't go with that particular approach."
⚠️

You cannot skip stages. Applying L2 (SFT adapter) on top of M0 (base model) without the domain knowledge from L1 (CPT adapter) is like teaching a Class 12 curriculum to a Class 10 student — the prerequisite knowledge from Class 11 is missing. Always follow the sequential pipeline.

DPO Practical — Step by Step

TRL Library — The Key Dependency

📚

TRL = Transformer Reinforcement Learning (HuggingFace library). Despite the name, it's the library for ALL preference alignment — including non-RL methods like DPO and ORPO. Under TRL you get: DPOTrainer, GRPOTrainer, RewardTrainer, SFTTrainer — one library for the entire fine-tuning ecosystem.

Step 1 — Load the Preference Dataset

from datasets import load_dataset
from trl import DPOConfig, DPOTrainer
from transformers import (
    AutoModelForCausalLM, AutoTokenizer,
    BitsAndBytesConfig
)
from peft import LoraConfig, get_peft_model, PeftModel
import os

# ── Directories ──────────────────────────────────────────────────
PREFERENCE_OUTPUT_DIR = "outputs/pharma_tinyllama_preference"
ADAPTER_SAVE_DIR      = "outputs/pharma_preference_lora_adapter"  # L3
os.makedirs(PREFERENCE_OUTPUT_DIR, exist_ok=True)
os.makedirs(ADAPTER_SAVE_DIR,      exist_ok=True)

# ── Load preference dataset (JSONL format) ────────────────────────
# Format: {prompt, chosen, rejected, source, page, topic}
preference_data = load_dataset(
    "json",
    data_files = "pharma_preference_dataset.jsonl",
    split      = "train"       # load as train split
)
print(ff"Total rows: {len(preference_data)}")          # 48 rows
print(preference_data[0])  # check first row: {prompt, chosen, rejected, ...}

# ── Train/validation split ───────────────────────────────────────
split_data = preference_data.train_test_split(
    test_size = 0.2,   # 20% validation
    seed      = 42    # reproducibility — same split every run
)
train_dataset = split_data["train"]   # ~40 rows
eval_dataset  = split_data["test"]    # ~8 rows
print(ff"Train: {len(train_dataset)} | Eval: {len(eval_dataset)}")

Step 2 — Load M2 Model (Instruction-Tuned Merged Model)

python · load M2 base model for DPO 
# ── Load M2 (instruction-merged model) as base for DPO ───────────
# M2 = M0 + L1 merged + L2 merged (non-instruction + instruction stages done)
# This is the "preference base model" — what DPO trains on top of

M2_MODEL_PATH = "outputs/pharma_tinyllama_merge_instruction_model"
# OR from HuggingFace Hub: "your-username/pharma-tinyllama-merge-model"

# Quantization config (4-bit QLoRa for T4 GPU)
bnb_config = BitsAndBytesConfig(
    load_in_4bit              = True,
    bnb_4bit_quant_type       = "nf4",
    bnb_4bit_compute_dtype    = "float16",
    bnb_4bit_use_double_quant = True
)

# Load the M2 model with quantization
preference_base_model = AutoModelForCausalLM.from_pretrained(
    M2_MODEL_PATH,
    quantization_config = bnb_config,
    device_map          = "auto"
)
preference_base_model.config.use_cache = False

# Load tokenizer
tokenizer = AutoTokenizer.from_pretrained(M2_MODEL_PATH)
tokenizer.pad_token = tokenizer.eos_token

# ── Attach LoRa Adapter 3 (L3) — preference fine-tuning target ───
lora_config = LoraConfig(
    r              = 16,
    lora_alpha     = 32,
    target_modules = ["q_proj", "v_proj"],
    lora_dropout   = 0.05,
    bias           = "none",
    task_type      = "CAUSAL_LM"
)
# M2 model + L3 adapter (L3 starts random, will be trained by DPOTrainer)
preference_model = get_peft_model(preference_base_model, lora_config)
print(ff"Trainable params: {preference_model.print_trainable_parameters()}")

Step 3 — DPOConfig (Training Configuration)

python · DPOConfig 
# ── DPOConfig — all training hyperparameters ──────────────────────
# Requires: DPOConfig and DPOTrainer from trl (that's all you need)

dpo_config = DPOConfig(
    # Output
    output_dir                  = PREFERENCE_OUTPUT_DIR,  # checkpoints + metadata

    # Training duration
    num_train_epochs             = 3,
    max_steps                    = -1,          # -1 → use num_train_epochs

    # Batch settings
    per_device_train_batch_size  = 2,
    per_device_eval_batch_size   = 2,
    gradient_accumulation_steps  = 4,

    # Optimizer
    optim                        = "paged_adamw_32bit",
    learning_rate                = 2e-5,
    lr_scheduler_type            = "cosine",
    warmup_ratio                 = 0.1,

    # Logging & evaluation
    logging_steps                = 10,
    evaluation_strategy          = "steps",
    eval_steps                   = 50,
    report_to                    = "none",     # no wandb/tensorboard

    # Checkpointing
    save_strategy                = "steps",
    save_steps                   = 50,
    save_total_limit             = 2,

    # Precision
    fp16                         = True,        # use float16 on T4 GPU

    # DPO-specific
    beta                         = 0.1,         # KL penalty weight
    remove_unused_columns        = False,      # keep metadata columns

    # Max token lengths for preference data
    max_prompt_length            = 512,
    max_length                   = 1024,
)

Step 4 — DPOTrainer (The Core Training Class)

python · DPOTrainer 
# ── DPOTrainer — the main class for preference fine-tuning ────────
trainer = DPOTrainer(
    model          = preference_model,   # M2 + L3 adapter (L3 to be trained)
    ref_model      = None,              # None → TRL uses internal ref behavior
    # Note: ref_model is optional in DPO (unlike RLHF which requires it)
    # When None, TRL internally maintains the reference policy via a function
    args           = dpo_config,
    train_dataset  = train_dataset,
    eval_dataset   = eval_dataset,
    tokenizer      = tokenizer,
)

# ── Start training ────────────────────────────────────────────────
trainer.train()
# Training begins — you will see the output table below

DPO Training Output Metrics — Explained

After training starts, Sunny explained every metric column in the output:

MetricWhat it Means
stepCurrent optimizer step number during training
train_lossDPO loss on the training data — should decrease over time
eval_lossDPO loss on the validation (unseen) data
entropyHow certain the model is in its predictions. High entropy = more random/uncertain. Low entropy = more confident.
num_tokensTotal number of tokens processed so far during training
logits_chosenRaw model score (log probability) for the chosen/preferred answer
logits_rejectedRaw model score (log probability) for the rejected answer
mean_token_accuracyAverage token-level accuracy across all predictions
rewards_chosenReward score for the preferred response (should increase)
rewards_rejectedReward score for the rejected response (should decrease)
reward_accuracyHow often the model correctly ranks chosen above rejected
reward_marginGap between chosen reward and rejected reward (larger = better alignment)
logps_chosenLog probability sum for the chosen response tokens
logps_rejectedLog probability sum for the rejected response tokens
📈

What "good training" looks like: train_loss decreasing, reward_margin increasing (model increasingly prefers chosen over rejected), reward_accuracy moving toward 1.0. These are the key signals that DPO is working correctly.

Step 6 — Inference with the Preference-Aligned Model

python · inference with DPO model 
# ── For inference: load M2 base + append L3 adapter ─────────────
# This is an APPEND operation (not merge) — faster for inference testing

from peft import PeftModel

# Load the M2 base model (instruction-merged)
base_for_inf = AutoModelForCausalLM.from_pretrained(
    M2_MODEL_PATH, device_map="auto", torch_dtype="float16"
)
# Append L3 adapter on top (no weight merging — adapter loaded in VRAM)
preference_inf_model = PeftModel.from_pretrained(
    base_for_inf, ADAPTER_SAVE_DIR
)

def build_preference_prompt(instruction, input_text=""):
    """Build the Alpaca-style prompt for inference."""
    if input_text:
        return ff"### Instruction:\n{instruction}\n\n### Input:\n{input_text}\n\n### Response:\n"
    return ff"### Instruction:\n{instruction}\n\n### Response:\n"

def generate_preference_response(question, max_new_tokens=200):
    prompt = build_preference_prompt(question)
    inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
    with __import__('torch').no_grad():
        outputs = preference_inf_model.generate(
            **inputs,
            max_new_tokens = max_new_tokens,
            temperature    = 0.7,
            do_sample      = True,
            pad_token_id   = tokenizer.eos_token_id
        )
    response = tokenizer.decode(outputs[0], skip_special_tokens=True)
    return response.split("### Response:")[-1].strip()

# Test with a pharma question
question = "What are the side effects of metformin?"
response  = generate_preference_response(question)
print(ff"Q: {question}\n\nA: {response}")

# ── Full pipeline merge: M2 + L3 → M3 (Final Model) ─────────────
# After inference testing, merge L3 into M2 to create the final M3 model
from peft import PeftModel

m3_model = PeftModel.from_pretrained(base_for_inf, ADAPTER_SAVE_DIR)
m3_merged = m3_model.merge_and_unload()   # bakes L3 into weights → M3

FINAL_MODEL_DIR = "outputs/pharma_tinyllama_final_model"
m3_merged.save_pretrained(FINAL_MODEL_DIR)
tokenizer.save_pretrained(FINAL_MODEL_DIR)
print(f"✓ Final model (M3) saved to: {FINAL_MODEL_DIR}")

# ── Push M3 to HuggingFace Hub ────────────────────────────────────
m3_merged.push_to_hub("your-username/pharma-tinyllama-final-model")

08 — Self-Check

Quiz — Test Your Understanding

📝 Class 23 Concept Check

1. What is preference tuning and what problem does it solve that Stage 1 (CPT) and Stage 2 (SFT) cannot?

▶ Show Answer
Preference tuning (Stage 3) aligns the model's outputs with human preferences. Stages 1 and 2 give the model domain knowledge (CPT) and the ability to follow instructions (SFT). But the model may still produce technically correct yet unhelpful, unsafe, or low-quality responses — like telling someone to "study 48 hours without a break." Preference tuning trains the model to prefer better (chosen) responses over worse (rejected) ones, by showing it paired examples of both. This is the same technique ChatGPT and other commercial LLMs use for alignment.

2. What are the 3 required columns in a preference dataset, and what does each contain?

▶ Show Answer
prompt: the user's instruction or question — what the model is being asked. chosen: the better/preferred response — what human evaluators (or SMEs) consider the higher-quality answer. rejected: the weaker/worse response — what the model should learn NOT to produce. The DPO training objective makes the model assign higher probability to the chosen response than the rejected response for each prompt.

3. What are the 4 preference alignment algorithms Sunny covered? Classify each as RL-based or non-RL.

▶ Show Answer
RL-based: (1) RLHF+PPO (Reinforcement Learning from Human Feedback) — introduced by OpenAI, uses Proximal Policy Optimization with an actor-critic framework and requires a separate reward model. Now largely outdated. (2) GRPO (Group Relative Policy Optimization) — introduced by DeepSeek, an updated version of PPO, very popular currently. Non-RL: (3) DPO (Direct Preference Optimization) — by Stanford, NeurIPS 2023. Trains directly on preference pairs using maximum likelihood. No reward model needed. Most popular for practical use. (4) ORPO (Odds Ratio Preference Optimization) — an advanced variant of DPO, also non-RL.

4. Explain the 3-stage LoRa merge pipeline in order. What do M0, M1, M2, M3, L1, L2, L3 each represent?

▶ Show Answer
M0 = original base model (e.g. TinyLlama). L1 = LoRa adapter trained in Stage 1 (CPT on domain raw text). M1 = M0 + L1 merged (has domain knowledge). L2 = LoRa adapter trained in Stage 2 (SFT on instruction data, using M1 as base). M2 = M1 + L2 merged (has domain knowledge + instruction following). L3 = LoRa adapter trained in Stage 3 (DPO on preference data, using M2 as base). M3 = M2 + L3 merged = the final production-ready model with domain knowledge, instruction following, AND preference alignment.

5. Using Sunny's "Class 10–12 analogy," explain why you cannot apply L2 directly on top of M0.

▶ Show Answer
M0 is like a Class 10 student (base knowledge). M1 = M0 + L1 merged = Class 10 + Class 11 knowledge. M2 = M1 + L2 merged = Class 10 + Class 11 + Class 12 knowledge. If you try to apply L2 (Class 12 curriculum) directly on M0 (Class 10 student), you skip Class 11 entirely — the prerequisite knowledge is missing. The adapter L2 was trained assuming the model already has the Stage 1 (L1) knowledge baked in. Without it, the fine-tuning is built on an incorrect foundation, leading to poor model quality.

6. What is the TRL library, and which classes from it are needed for DPO training?

▶ Show Answer
TRL (Transformer Reinforcement Learning) is HuggingFace's library for preference alignment and fine-tuning. Despite the name, it covers both RL-based and non-RL methods. For DPO you need exactly two classes: DPOConfig (configures all training hyperparameters: output_dir, epochs, batch_size, optimizer, DPO-specific beta parameter) and DPOTrainer (the main training class that takes the model, ref_model=None, training args, train_dataset, eval_dataset, and tokenizer). TRL also contains GRPOTrainer, SFTTrainer, RewardTrainer, and ORPOTrainer.

7. What is the role of ref_model=None in DPOTrainer, and how does this differ from RLHF?

▶ Show Answer
In DPO, ref_model=None means TRL will internally maintain the reference policy behavior using a frozen copy of the initial model (via a function), without requiring you to explicitly load a separate reference model. This is one of DPO's key simplifications over RLHF. In RLHF, you explicitly need: (1) a separate reward model (trained on human preference labels) and (2) a reference policy model (to compute KL divergence during PPO). DPO eliminates both — the language model itself acts as a secret reward model (per the paper: "Your Language Model is Secretly a Reward Model"), making the training much simpler and computationally cheaper.
