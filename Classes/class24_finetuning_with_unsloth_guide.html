02 — Unsloth Deep Dive

Why Unsloth?

Standard HuggingFace + PEFT fine-tuning works — but it's memory-hungry and slow. Fine-tuning a 7B model in 16-bit requires ~30GB VRAM. Most people don't have that. Unsloth solves this by combining QLoRA with hand-written Triton GPU kernels and a custom backpropagation engine.

2×

Faster Training

Hand-tuned Triton GPU kernels replace PyTorch's generic operations. Same math, radically faster execution — no accuracy tradeoff.

70%

Less VRAM

QLoRA + gradient checkpointing + 8-bit optimisers reduce peak memory from 20–30GB to 6–8GB for a 7B model.

0%

Accuracy Loss

Unlike many fast-training libraries, Unsloth uses mathematically identical computations — it's an optimisation, not an approximation.

Free

Runs on Colab T4

A Google Colab T4 GPU (15GB VRAM, free tier) is enough to fine-tune 7–8B models with QLoRA. No expensive cloud GPU needed.

How Unsloth Achieves Speed

The performance gains come from three main sources:

01

Custom Triton Kernels

The Unsloth team manually derived backpropagation equations for transformer layers and rewrote them as highly optimised Triton GPU kernels. These are purpose-built for LoRA training patterns, unlike PyTorch's generic CUDA operations.

02

Gradient Checkpointing ("unsloth" mode)

Standard gradient checkpointing recomputes activations to save memory, but recomputation costs time. Unsloth's custom mode is smarter — it selectively checkpoints only the most memory-intensive layers, reducing recomputation overhead by up to 30%.

03

4-bit NF4 Quantisation (QLoRA)

The base model is loaded in 4-bit NF4 format, reducing weight storage from 16-bit to 4-bit (4× compression). Only the small LoRA adapter matrices remain in full precision (bfloat16/float16) during training.

03 — Core Concepts

Key Concepts

📖 Key Terminology

FastLanguageModel
Unsloth's main class. Drop-in replacement for HuggingFace's AutoModelForCausalLM — used to load pre-trained models with Unsloth's speed optimisations.
get_peft_model()
Unsloth wrapper that attaches LoRA adapter matrices to the loaded model and marks them as trainable. Configures rank, alpha, target modules, dropout, and other LoRA hyperparameters.
LoRA Adapter
A small (~100MB) file containing only the trained A and B matrices from LoRA training. The base model weights are NOT included — the adapter is applied on top of the base model at inference time.
Merged Model
The result of mathematically combining the LoRA adapter into the base model weights, creating a single standalone model. Larger file (~15GB for 7B in 16-bit) but simpler to serve.
GGUF Format
A binary format for quantised models used by llama.cpp. Enables running large models on CPU/Mac or modest GPUs. Required for Ollama and LM Studio deployment.
Ollama
A tool for running LLMs locally with a simple CLI and REST API. Accepts GGUF models and makes local deployment as easy as ollama run my-model.
Modelfile
An Ollama configuration file that specifies the base GGUF model path, chat template, system prompt, and generation parameters. Unsloth generates this automatically.
save_method
Unsloth's export option: "lora" saves only the adapter; "merged_16bit" saves the full model in bfloat16; "merged_4bit" saves the merged model in 4-bit precision.

NF4 Quantisation — Why 4-bit Works So Well

Standard 4-bit quantisation cuts model size by 4× but loses accuracy because it doesn't account for how neural network weights are distributed. QLoRA introduced NF4 (NormalFloat4) — a 4-bit data type designed specifically for the normal (Gaussian) distribution that neural network weights follow.

📐

NF4 intuition: If you know weights follow a bell curve, you can place your 4-bit "buckets" more densely near zero (where most weights cluster) and more sparsely in the tails. This is information-theoretically optimal for normally distributed data — you get much better accuracy per bit than standard integer quantisation. This is why QLoRA nearly matches full 16-bit fine-tuning accuracy despite storing the base model in 4 bits.

Step 1 — Load the Model

Unsloth provides pre-quantised models on HuggingFace Hub (suffixed -bnb-4bit or -unsloth-bnb-4bit). These download much faster than the raw 16-bit model since they're already 4-bit compressed.

python · model loading 
from unsloth import FastLanguageModel
import torch

# ── Configuration ─────────────────────────────────────────────────
max_seq_length = 2048   # set to 4096 for longer contexts (needs more VRAM)
dtype = None             # auto-detects bfloat16 on Ampere+ or float16 on T4
load_in_4bit = True     # QLoRA: loads base model in 4-bit NF4 format

# ── Supported models (choose one) ─────────────────────────────────
# "unsloth/llama-3-8b-bnb-4bit"            ← Llama 3 8B base
# "unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit"  ← Llama 3.1 8B Instruct
# "unsloth/mistral-7b-v0.3-bnb-4bit"       ← Mistral 7B
# "unsloth/Qwen2.5-7B-Instruct-bnb-4bit"   ← Qwen 2.5 7B
# "unsloth/gemma-2-9b-bnb-4bit"            ← Gemma 2 9B

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name = "unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit",
    max_seq_length = max_seq_length,
    dtype = dtype,
    load_in_4bit = load_in_4bit,
    # token = "hf_..."  # needed for gated models like Llama
)

print(f"Model loaded! Parameters: {model.num_parameters()/1e9:.1f}B")
print(f"VRAM used: {torch.cuda.memory_allocated()/1e9:.2f} GB")
🔥

Instruct vs Base model for SFT: For most practical fine-tuning (specialising on a domain or style), start from an instruct model — it already knows how to follow instructions, so your SFT needs fewer examples to achieve good results. Use a base model only if you're doing CPT first or need to avoid any prior instruction-following biases.

Step 2 — Attach LoRA Adapters

python · LoRA configuration 
model = FastLanguageModel.get_peft_model(
    model,
    # ── LoRA Hyperparameters ──────────────────────────────────────
    r = 16,                # LoRA rank. 8–64 for SFT. Higher → more capacity, more VRAM
    lora_alpha = 16,       # scaling factor. Usually = r. Effective scale = alpha/r = 1
    lora_dropout = 0,      # 0 is optimal per Unsloth benchmarks
    bias = "none",         # "none" is optimal

    # ── Target Modules ───────────────────────────────────────────

        "q_proj",   # Query projection
        "k_proj",   # Key projection
        "v_proj",   # Value projection
        "o_proj",   # Output projection
        "gate_proj",# MLP gate
        "up_proj",  # MLP up
        "down_proj",# MLP down
        # Add "embed_tokens", "lm_head" only for CPT (new vocabulary)
    ],

    # ── Memory & Stability ───────────────────────────────────────
    use_gradient_checkpointing = "unsloth",  # Unsloth's custom mode (30% less memory)
    random_state = 42,
    use_rslora = False,     # True only at rank ≥ 64 for stability
    loftq_config = None,   # LoftQ for better QLoRA initialisation (optional)

Step 4 — Configure & Run Training

python · SFTTrainer + training 
from trl import SFTTrainer
from transformers import TrainingArguments
from unsloth.chat_templates import train_on_responses_only
from unsloth import is_bfloat16_supported

# ── Training Arguments ────────────────────────────────────────────
training_args = TrainingArguments(
    output_dir              = "./outputs",
    num_train_epochs        = 3,
    per_device_train_batch_size = 2,
    gradient_accumulation_steps = 4,        # effective batch = 8
    warmup_ratio            = 0.05,
    learning_rate           = 2e-4,
    fp16                    = not is_bfloat16_supported(),
    bf16                    = is_bfloat16_supported(),
    logging_steps           = 20,
    optim                   = "adamw_8bit",  # 8-bit Adam → 4× less memory than fp32
    weight_decay            = 0.01,
    lr_scheduler_type       = "cosine",     # smoothly decays LR
    seed                    = 42,
    save_strategy           = "steps",
    save_steps              = 200,
    evaluation_strategy     = "steps",
    eval_steps              = 100,
    load_best_model_at_end  = True,
    report_to               = "none",       # change to "wandb" for experiment tracking
)

# ── Train/val split ───────────────────────────────────────────────
split = dataset.train_test_split(test_size=0.05, seed=42)

# ── Build SFTTrainer ──────────────────────────────────────────────
trainer = SFTTrainer(
    model              = model,
    tokenizer          = tokenizer,
    train_dataset      = split["train"],
    eval_dataset       = split["test"],
    dataset_text_field = "text",
    max_seq_length     = max_seq_length,
    dataset_num_proc   = 2,
    packing            = False,       # False to preserve loss mask boundaries
    args               = training_args,
)

# ── Apply prompt masking — CRITICAL for SFT ─────────────────────
trainer = train_on_responses_only(
    trainer,
    instruction_part = "### Instruction:\n",
    response_part    = "### Response:\n",
)

# ── Check memory before training ─────────────────────────────────
gpu_stats = torch.cuda.get_device_properties(0)
start_gpu_memory = round(torch.cuda.max_memory_reserved() / 1024**3, 3)
max_memory = round(gpu_stats.total_memory / 1024**3, 3)
print(ff"GPU = {gpu_stats.name}. Max VRAM = {max_memory} GB.")
print(ff"Reserved before training = {start_gpu_memory} GB.")

# ── TRAIN ────────────────────────────────────────────────────────
trainer_stats = trainer.train()

# ── Memory & time stats after training ───────────────────────────
end_memory = round(torch.cuda.max_memory_reserved() / 1024**3, 3)
print(ff"Peak VRAM used: {end_memory} GB / {max_memory} GB")
print(ff"Training time: {trainer_stats.metrics['train_runtime']:.0f}s ({trainer_stats.metrics['train_runtime']/60:.1f} min)")
print(ff"Final training loss: {trainer_stats.metrics['train_loss']:.4f}")

05 — Saving & Deployment

Saving & Exporting Your Model

After training, you have three export strategies. The right choice depends on how you plan to serve the model.

Option 1

LoRA Adapter Only

Saves just the ~100MB adapter file. Must be loaded alongside the base model at inference time.

✓ HuggingFace deployment
✓ Unsloth inference
✓ Smallest file size
Option 2

Merged Model (16-bit)

Adapter merged into base model. Standalone ~15GB file. No dependency on the base model.

✓ vLLM serving
✓ HuggingFace Inference API
✓ Best accuracy
Option 3

GGUF Format

Quantised binary for llama.cpp / Ollama / LM Studio. Runs on CPU or modest GPU. Various quantisation levels available.

✓ Local inference (Ollama)
✓ Mac / CPU deployment
✓ Smallest for inference

    return {"text": texts}

dataset = dataset.map(format_alpaca, batched=True, remove_columns=dataset.column_names)
split   = dataset.train_test_split(test_size=0.05, seed=42)

# ─── CELL 6: Train ──────────────────────────────────────────────
trainer = SFTTrainer(
    model=model, tokenizer=tokenizer,
    train_dataset=split["train"], eval_dataset=split["test"],
    dataset_text_field="text", max_seq_length=MAX_SEQ_LEN,
    packing=False, dataset_num_proc=2,
    args=TrainingArguments(
        output_dir="./outputs", num_train_epochs=EPOCHS,
        per_device_train_batch_size=BATCH_SIZE,
        gradient_accumulation_steps=GRAD_ACC,
        learning_rate=LR, warmup_ratio=0.05,
        lr_scheduler_type="cosine", optim="adamw_8bit",
        bf16=is_bfloat16_supported(), fp16=not is_bfloat16_supported(),
        evaluation_strategy="steps", eval_steps=100,
        logging_steps=20, load_best_model_at_end=True,
        seed=42, report_to="none",
    ),
)
trainer = train_on_responses_only(
    trainer, instruction_part="### Instruction:\n", response_part="### Response:\n")

stats = trainer.train()
print(ff"Training done! Loss: {stats.metrics['train_loss']:.4f}")

# ─── CELL 7: Inference ──────────────────────────────────────────
FastLanguageModel.for_inference(model)
messages = [{"role":"user", "content":"List 5 benefits of meditation."}]
inputs = tokenizer.apply_chat_template(
    messages, tokenize=True, add_generation_prompt=True, return_tensors="pt").to("cuda")
model.generate(input_ids=inputs, max_new_tokens=200,
               streamer=TextStreamer(tokenizer, skip_prompt=True))

model.save_pretrained("my_adapter")
tokenizer.save_pretrained("my_adapter")

07 — Practitioner Notes

Tips, Pitfalls & Best Practices

✅ Best practices

  • ✓ Always call FastLanguageModel.for_inference(model) before generating — it enables 2× faster inference through kernel optimisations.
  • ✓ Use is_bfloat16_supported() to automatically detect whether to use bf16 (Ampere+ GPUs like A100) or fp16 (T4, older GPUs).
  • ✓ Check VRAM before and after training with torch.cuda.max_memory_reserved() — it's the best indicator of whether your config fits the GPU.
  • ✓ Use adamw_8bit optimiser — it reduces optimiser state memory from ~24GB (fp32 Adam) to ~6GB with negligible accuracy cost.
  • ✓ For GGUF export, q4_k_m is the community-standard recommendation — a good balance of size and quality for most use-cases.
  • ✓ Let Unsloth generate the Modelfile automatically. Manually writing it risks using the wrong chat template, causing poor Ollama outputs.
  • ✓ Push both the adapter AND a GGUF to HuggingFace Hub — adapter for HF/vLLM users, GGUF for local users. They're complementary audiences.

❌ Common mistakes

  • ✗ Forgetting train_on_responses_only() — causes CPT-style training instead of SFT prompt masking.
  • ✗ Running GGUF export before saving the adapter — if the Colab session crashes during GGUF conversion, you lose your training. Always save the adapter first.
  • ✗ Using the wrong chat template in Ollama — if inference output is gibberish, this is almost always the cause. Check your Modelfile.
  • ✗ Not setting load_best_model_at_end=True — without it, training uses the final checkpoint, not necessarily the best val-loss checkpoint.
  • ✗ Using packing=True for SFT without careful masking — breaks prompt masking boundaries across packed samples.
  • ✗ Expecting GGUF conversion to be fast — it takes 5–15 minutes on Colab T4. Don't restart the runtime thinking it's frozen.

08 — Self-Check

Quiz — Test Your Understanding

📝 Concept Check Questions

1. How does Unsloth achieve 2× faster training compared to standard HuggingFace + PEFT without any accuracy loss?

▶ Show Answer
Unsloth manually derived the backpropagation equations for transformer LoRA layers and rewrote them as hand-tuned Triton GPU kernels. These kernels are purpose-built for LoRA training patterns, unlike PyTorch's generic CUDA operations. Because the math is identical (not approximated), accuracy is preserved. Combined with a custom gradient checkpointing mode, this yields 2× speed and 70% less VRAM with 0% accuracy degradation.

2. What is the difference between saving as a LoRA adapter vs. a merged model? When would you choose each?

▶ Show Answer
A LoRA adapter (~100MB) contains only the trained A and B matrices — it requires the original base model to be loaded alongside it at inference time. A merged model (~15GB) mathematically combines the adapter into the base model, creating a standalone file that doesn't need the base model separately. Use the adapter when you want a small file and will always have the base model available (e.g. HuggingFace/Unsloth inference). Use the merged model when you need a standalone artifact for vLLM, cloud APIs, or sharing without requiring users to also download the base model.

3. Why is NF4 quantisation better than standard INT4 for neural network weights?

▶ Show Answer
Neural network weights follow an approximately normal (Gaussian) distribution — most weights are near zero, with fewer large values. Standard INT4 distributes its 16 values uniformly across the weight range, wasting precision on values that rarely occur. NF4 (NormalFloat4) places its 16 values according to the normal distribution — densely near zero and sparsely in the tails. This is information-theoretically optimal for normally distributed data, giving significantly better accuracy per bit than INT4.

4. What is a Modelfile in Ollama, and why should you let Unsloth generate it rather than writing it yourself?

▶ Show Answer
A Modelfile is a configuration file Ollama uses to create a model — it specifies the base GGUF path, the chat template (system, user, assistant delimiters), EOS tokens, and generation parameters. Unsloth generates it automatically using the exact same chat template that was used during training. If you write it manually, you risk specifying the wrong template or wrong EOS token, causing the model to generate gibberish, infinite output, or repeated text in Ollama — one of the most common deployment failures.

5. Why should you save the LoRA adapter before running GGUF export on Colab?

▶ Show Answer
GGUF conversion using llama.cpp can take 5–15 minutes on a Colab T4 GPU, and Colab sessions can disconnect or time out. If the session crashes during GGUF export, you lose your trained weights entirely. Saving the lightweight adapter first (~100MB, takes seconds) ensures your training is always safely preserved. You can then re-run GGUF export in a fresh session by loading the adapter.

6. What does q4_k_m mean in GGUF quantisation and why is it typically recommended?

▶ Show Answer
In llama.cpp's GGUF naming: "q4" = 4-bit quantisation, "k" = k-quant method (uses super-blocks for better quality), "m" = medium size variant. K-quants are generally better than plain q4_0 because they quantise different layers at different bit widths — keeping sensitive layers (like attention projections) at slightly higher precision. q4_k_m is community-recommended as the sweet spot: a 7B model fits in ~4GB VRAM/RAM, quality is very close to f16, and it's compatible with all llama.cpp-based tools including Ollama, LM Studio, and Jan AI.

7. What is the purpose of FastLanguageModel.for_inference(model) and when must you call it?

▶ Show Answer
It switches the model from training mode to inference mode, enabling Unsloth's inference-specific kernel optimisations (including xformers attention and other speed improvements). It must be called after training is complete and before generating any output — calling generate() without it still works but is about 2× slower. If you load a saved model for inference (not training), call it immediately after loading.
