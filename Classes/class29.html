03 — Core Concept

What is RAG?

Breaking Down the Acronym

R
Retrieval
Finding the most relevant information from your documents using similarity search
A
Augmented
Enriching the user's question by adding retrieved context before sending to the LLM
G
Generation
The LLM generates a final grounded answer using the augmented prompt + context

The One-Line Definition

From the Class Notes
RAG = Give relevant context to the LLM before answering

RAG is a technique that helps an LLM answer questions using external data such as PDFs, documents, websites, databases, or company knowledge bases. The LLM itself doesn't need to be retrained — it simply receives the relevant document chunks as additional context alongside the user's question.

📖 Precise Definitions (from class notes)

Retrieval
Finding relevant information from documents using mathematical similarity operations (cosine similarity, dot product) in a vector database.
Augmentation
Adding the retrieved information as extra context to the user's question. Improving the LLM's input by injecting retrieved context alongside any custom instructions.
Generation
The LLM generates the final answer using the augmented prompt (user question + retrieved context + custom instructions).

A Concrete Example (from Sunny's class)

Sunny used this exact example throughout the class to make the concept stick:

Refund Policy Example — Step by Step
USER QUESTION
"What is the refund policy of our company?"
PROBLEM WITHOUT RAG
LLM doesn't have access to this private company document → may hallucinate: "ABC Company offers a 30-day refund policy" (WRONG)
WHAT RAG DOES:
1 Searches the company policy document (via similarity search — a mathematical operation on vectors)
2 Retrieves the relevant refund policy section from the vector database
3 Augments the prompt: Question: "What is the refund policy?" + Context: "Refunds are allowed within 7 days of purchase."
4 LLM generates the grounded answer: "The refund policy allows refunds within 7 days of purchase." ✓
"LLMs do not have access to the latest or private data → We retrieve relevant context from documents → We give the LLM the context + question → The LLM gives a grounded answer."
04 — Motivation

Why RAG? — The 4 Problems it Solves

Sunny explicitly covered 4 problems with plain LLMs in the class notes and the live session. These are the core justification for RAG:

Problem 1

LLMs Do Not Have Private Data

Company HR policies, internal documents, proprietary databases — LLMs were never trained on these. They cannot answer questions about your specific organisation's data.

Problem 2

LLMs May Not Have Latest Data

Training data has a cutoff date. Current news, recent regulations, new product releases — anything after the cutoff is unknown to the model. RAG lets you inject real-time information.

Problem 3

LLMs Can Hallucinate

Without ground truth context, LLMs generate confident but wrong answers. "ABC Company offers a 30-day refund policy" — stated confidently, completely fabricated. RAG anchors answers to retrieved facts.

Problem 4

Fine-Tuning Is Not Always the Right Solution

For every new document, you cannot fine-tune the model again. If HR policy changes every month, you update the documents in RAG — not retrain the model. RAG is better when data changes frequently.

"We always cannot do the fine-tuning. So for every new document, we cannot fine-tune the model again and again. RAG is better when data is changing very, very frequently. Fine-tuning is an expensive process also. What we do — we take the advantage of the reasoning capability of the LLM, we provide some additional context, and based on that only we generate the final answer."
💡

The RAG Logic Chain (from Sunny's notes): LLMs do not have access to latest/private data → We retrieve relevant context from documents → We give the LLM context + question → The LLM gives a grounded answer. This is the entire justification for RAG in one chain.

Phase 1 — Data Ingestion (Deep Dive)

Data ingestion is the offline pipeline that prepares your knowledge base. It runs once (or whenever documents are updated). The steps are:

🔶 Data Ingestion Components

1. Data Parsing (Document AI)
Extracting clean, structured content from raw source files. This is the hardest step — different parsers are needed for PDFs, DOCX, images, tables, web pages, etc.
2. Chunking
Dividing parsed text into smaller pieces (chunks). This step is marked as "optional" on the class diagram — for small documents you may not need it. We'll cover chunking strategies in detail in later classes.
3. Embedding
Converting each text chunk into a dense vector (using a sentence embedding model). This is mandatory — data cannot be stored in the vector database in raw text form.
4. Vector Database Storage
Storing all the chunk vectors in a vector database for fast similarity retrieval at query time.

Phase 2 — Retrieval (Query Time)

When a user asks a question, the retrieval pipeline runs in real time:

  • The user's question is embedded using the same embedding model used for document chunks
  • A similarity search runs against the vector database (cosine similarity — "a mathematical operation" as Sunny described)
  • The top-k most similar chunks are retrieved (typically top 3–5)

Phase 3 — Augmentation & Generation

The retrieved chunks, user question, and any custom instructions are combined into an augmented prompt and sent to the LLM. The LLM uses its reasoning capability — but grounds the answer in the retrieved context, dramatically reducing hallucination.

"We have three things: first is a user question, second is the context (that is my retrieved information), and the next is some custom instruction — do this, do that, something like this. This is only called the augmentation — where we are enriching this user question just by adding some context. Then this particular information is going to the LLM. LLM is generating a final output. This is called generation."

07 — Data Ingestion Step 1

Data Parsing

Data parsing is the process of fetching and arranging raw data — extracting clean text, images, tables, metadata, and layout information from source files. It's the first and often most complex step in RAG.

⚠️

Why parsing matters: A PDF is not just text — it contains images, tables, headers, footers, multi-column layouts, and scanned pages. Poor parsing = noisy chunks = bad retrieval = wrong answers. "Garbage in, garbage out" fully applies here.

Parsing Libraries & Tools

Sunny covered these tools in detail, marking which are free and which are paid:

Free

PyMuPDF (fitz)

Fast PDF text extraction, image extraction, layout info. One of the most popular Python libraries for PDF parsing.

Free

pdfplumber

Excellent for extracting tables from PDFs. Built on pdfminer, easier API. Great for structured PDF data.

Free

python-docx

Parse Microsoft Word (.docx) files. Extract paragraphs, tables, headers. Simple and reliable.

Free

Unstructured.io

Handles many file types (PDF, DOCX, HTML, images) with one API. Very popular in RAG pipelines. Open-source core.

Free

Docling

IBM's document parsing library. Handles complex layouts, tables, and multi-column PDFs with high accuracy.

Paid

LlamaParse

LlamaIndex's premium parser. Excellent at understanding complex PDFs. Has a free tier with limits.

Paid (Expensive)

Azure Document Intelligence (ADI)

Microsoft's enterprise-grade document AI. Handles OCR, layout parsing, table extraction. Costly but very powerful.

Paid

Google Document AI (GDAI)

Google Cloud's document understanding service. Supports OCR, form parsing, and specialised processors.

Paid

Amazon Textract

AWS service for extracting text and data from scanned documents. Strong for forms, tables, and handwriting.

Free

Parsio / Parser.io

Document parsing with templates. Good for structured extraction from standard document formats.

💡

Sunny's recommendation pattern: Free tools (PyMuPDF, pdfplumber, python-docx, Unstructured) are sufficient for most use cases. Paid services (ADI, GDAI, Textract) are expensive but worth it for enterprise-grade accuracy, scanned documents, or complex layouts. Docling and LlamaParse sit in the middle — free/cheap with high quality.

LangChain's Role — It's a Wrapper, Not a Parser

This was one of Sunny's key clarifications in the class. Many students assumed LangChain has its own parsing engine. It doesn't.

"LangChain is not having its own parser. It is providing you the wrapper on top of the different, different library — like PDF Plumber, like PyMuPDF, like Python-docx, like Unstructured.io. These are the actual libraries. LangChain is just a wrapper. LangChain is a framework which provides you the plug-and-play button from every other framework or every other library."
01

Document Loader / Parser

LangChain wraps PyMuPDF, pdfplumber, python-docx, Unstructured — uses them internally, returns a standard Document object (page_content + metadata)

02

Text Splitter / Chunking

Multiple chunking strategies: RecursiveCharacterTextSplitter, TokenTextSplitter, SemanticChunker. All accessible via LangChain.

03

Vector Database

Wrappers for FAISS, Chroma, Qdrant, Pinecone, Supabase, pgvector, Milvus — common interface for all.

04

Model / LLM / APIs

Connect to OpenAI, Claude, Gemini, Groq, HuggingFace, Ollama — all through the same LangChain interface.

05

Chains (LCEL)

LangChain Expression Language (LCEL) — compose the full RAG pipeline as a chain of components.

06

Memory Management

Conversation history, context windows, summary buffers — LangChain provides memory utilities for multi-turn RAG.

09 — Decision Guide

RAG vs Fine-Tuning

From the class notes table (RAG vs Fine-tuning Quick Difference):

Dimension🔍 RAG🧠 Fine-Tuning
Main Purpose Gives the model external knowledge/context Teaches the model new behaviour, style, or format
Model weights change? No — model is unchanged Yes — weights are updated
Cost Usually lower Usually higher (GPU required)
Data update Easy — update documents/vector DB Harder — retrain or fine-tune again
Frequency of data change Great for frequently changing data Better for static behaviour/style changes
GPU required? No — runs on CPU Yes — GPU training required
Hallucination reduction High — answers grounded in retrieved context Moderate — depends on training data quality
Private/proprietary data Excellent — no data leaves your system Possible but expensive
Typical use case Document Q&A, knowledge base, chatbot over company docs Style adaptation, domain vocabulary, instruction following
✅

Decision rule: Use RAG when your data changes frequently (weekly/monthly), is private/proprietary, or is large (thousands of docs). Use Fine-Tuning when you want to change the model's behaviour, writing style, output format, or teach it domain-specific reasoning patterns. In production, you often use both — a domain-fine-tuned model with a RAG pipeline on top.

11 — First Look at Code

Minimal RAG Pipeline in LangChain

While Class 29 was mainly conceptual, here is the foundational LangChain code structure that will be built upon in subsequent classes. This mirrors the pipeline structure taught in the session:

python · minimal RAG 
## ══════════════════════════════════════════════════════
## CLASS 29 — RAG Introduction
## Minimal end-to-end RAG pipeline using LangChain
## No GPU required — runs on CPU
## ══════════════════════════════════════════════════════

# !pip install langchain langchain-community langchain-openai
# !pip install chromadb pymupdf sentence-transformers

## ── PHASE 1: DATA INGESTION ──────────────────────────

from langchain_community.document_loaders import PyMuPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import Chroma
from langchain_community.embeddings import HuggingFaceEmbeddings

# Step 1: Data Parsing — LangChain wraps PyMuPDF internally
loader = PyMuPDFLoader("company_policy.pdf")
documents = loader.load()    # Returns list of Document objects
print(ff"Loaded {len(documents)} pages")
print(documents[0].page_content[:200])   # page_content + metadata

# Step 2: Chunking (optional but recommended)
splitter = RecursiveCharacterTextSplitter(
    chunk_size    = 500,   # characters per chunk
    chunk_overlap = 50,    # overlap between chunks
)
chunks = splitter.split_documents(documents)
print(ff"Total chunks: {len(chunks)}")

# Step 3: Embedding — convert text → vectors
# Using local HuggingFace model (no API key needed, runs on CPU)
embeddings = HuggingFaceEmbeddings(
    model_name = "sentence-transformers/all-MiniLM-L6-v2"
)

# Step 4: Vector Database — store vectors in Chroma (local)
vectordb = Chroma.from_documents(
    documents  = chunks,
    embedding  = embeddings,
    persist_directory = "./chroma_db"   # saves locally
)
print("✓ Data ingestion complete — vectors stored in ChromaDB")

## ── PHASE 2: RETRIEVAL ───────────────────────────────

user_query = "What is the refund policy of our company?"

# Similarity search — query embedded, top-k chunks retrieved
retriever = vectordb.as_retriever(search_kwargs={"k": 3})
relevant_chunks = retriever.invoke(user_query)

print(ff"\nRetrieved {len(relevant_chunks)} relevant chunks:")
for i, chunk in enumerate(relevant_chunks):
    print(ff"  Chunk {i+1}: {chunk.page_content[:100]}...")

## ── PHASE 3: AUGMENTATION + GENERATION ──────────────

from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# LLM — can also use Claude, Gemini, Groq, or local Ollama
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# Augmented prompt template — Question + Context + Custom Instruction
prompt = ChatPromptTemplate.from_template("""
You are a helpful assistant. Answer the question using ONLY
the provided context. If the answer is not in the context,
say "I don't know based on available documents."

Context:
{context}

Question: {question}

Answer:""")

# LCEL Chain — the RAG pipeline as a chain
def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

# Run the RAG pipeline
answer = rag_chain.invoke(user_query)
print(ff"\nFinal Answer: {answer}")
# "The refund policy allows refunds within 7 days of purchase."
🟢

No API key for embeddings: Use HuggingFaceEmbeddings with all-MiniLM-L6-v2 — it runs locally on CPU, costs nothing, and is perfect for learning. Switch to OpenAI embeddings (text-embedding-3-small) only for production where highest quality matters.

12 — Self-Check

Quiz — Test Your Understanding

📝 Concept Check (Based on Class 29 Content)

1. What does RAG stand for, and what does each word mean in one sentence?

▶ Show Answer
RAG = Retrieval-Augmented Generation. Retrieval = finding relevant information from documents using similarity search. Augmented = enriching the user's question by adding that retrieved information as extra context. Generation = the LLM generates the final answer using the augmented prompt.

2. Name the 4 problems with plain LLMs that RAG solves (as covered in class).

▶ Show Answer
Problem 1: LLMs do not have private data (company documents, internal policies). Problem 2: LLMs may not have the latest data (training cutoff issue). Problem 3: LLMs can hallucinate — giving confident but wrong answers. Problem 4: Fine-tuning is not always the right solution — for frequently changing data, RAG is more appropriate and practical.

3. What are the three phases of a RAG pipeline? Describe what happens in each.

▶ Show Answer
Phase 1 (Data Ingestion): Raw documents are parsed → chunked (split into pieces) → embedded (converted to vectors) → stored in a vector database. This happens offline, once. Phase 2 (Retrieval): The user's question is embedded, a similarity search runs against the vector database, and the top-k most relevant chunks are returned. Phase 3 (Generation): The retrieved chunks, user question, and custom instructions are combined into an augmented prompt. The LLM uses this prompt to generate the final grounded answer.

4. Sunny made a key point: LangChain is NOT a parsing library. What is it, and what does it actually do for parsing?

▶ Show Answer
LangChain is a framework that acts as a wrapper/integration layer. For parsing, it internally uses actual parsing libraries like PyMuPDF, pdfplumber, python-docx, and Unstructured.io — LangChain does not do the low-level parsing itself. It provides a common Document format (page_content + metadata) so that parsed documents plug easily into the rest of the RAG pipeline (chunking → embedding → vector store).

5. What is the key difference between RAG and Fine-Tuning in terms of model weights?

▶ Show Answer
RAG does NOT change the model's weights — the LLM remains unchanged. It simply receives more context at inference time. Fine-Tuning DOES change the model's weights — it updates the parameters during a training process. This is why RAG is cheaper, faster to update (just update the documents), and requires no GPU — while Fine-Tuning requires GPU training and is expensive to repeat whenever data changes.

6. A student asked Sunny: "Does the user need to have access to the vector database?" What was Sunny's answer and why?

▶ Show Answer
Sunny said: "No, no, no, no. Should not have the access altogether." The vector database is an internal backend component of the RAG system. Users interact only with the application interface (e.g. a chatbot UI or API). The application handles the retrieval from the vector database on the user's behalf. Exposing the vector database directly to users would be a security risk and is architecturally incorrect.

7. Name any 5 of the 8 data source types Sunny listed that can be used in RAG, and describe one parsing tool suitable for PDF documents.

▶ Show Answer
Any 5 from: PDF, DOCX, Internal DB, Database, Web, Internal Portal, Cloud Artifactory, Audio/Video. For PDFs: PyMuPDF (fitz) is a free, fast Python library that extracts text, images, and layout information from PDF files. pdfplumber is another excellent free option, particularly good at extracting tables from PDFs.
