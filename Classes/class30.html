03 — The Core Concept

The LangChain Document Object

This is the single most important concept of Class 30. Every LangChain loader — regardless of file type — returns data in the same standardised format: a Document object with exactly two fields.

LangChain Document Object — Standard Format
page_content
The actual extracted text content from the file.
PDF → full page text · CSV → key:value row string · JSON → JSON object string · HTML → clean text
metadata
Information about the data — source file path, page number, author, creation date, row number, etc.
Used for source citation, filtering, and traceability in RAG pipelines.
"In LangChain, parsed content comes in the document object. Inside the document object, basically, you will get the page content, and you will get the metadata. This format is useful for the RAG, because later we can show the source citation along with the final answer."
🎯

Why standardisation matters: Because every loader returns the same Document format, the rest of your RAG pipeline (text splitter → embedding → vector store) works identically regardless of whether the source was a PDF, CSV, or HTML file. The LangChain wrapper provides this unified interface — that is its primary value.

page_content — What You Get

The page_content field varies by file type:

File Typepage_content FormatOne Document per…
PDFFull raw text of the page (tables appear as raw data)Page
CSVcolumn1: value1\ncolumn2: value2\n...Row
JSONJSON object as stringJSON object in list
DOCXFull document textDocument
HTMLExtracted clean text (strips HTML tags)Page/file
TXTRaw text contentFile
⚠️

Tables in PDFs via LangChain loader: When you use the basic PDF loader, table data is extracted as raw text — it is NOT structured as a table. To get properly structured table data (Markdown or JSON), you need the complex parsing approach (PyMuPDF from scratch or Docling), which Sunny covered in Part 2.

metadata — PDF Metadata Fields

When loading a PDF, the metadata contains these fields (from Sunny's live demo):

source
Full file path of the PDF
page
Page index (0-based, so page 0 = first page)
page_label
Human-readable page number (1-based)
total_pages
Total number of pages in the PDF
author
Document author (if set, else "Anonymous")
title
Document title from PDF properties
subject
Document subject (if specified)
keywords
Keywords embedded in PDF properties
creator
Creator application (e.g. Word, Adobe)
creation_date
When the document was created
mod_date
Last modification date
trapped
PDF print color trapping info (rarely used)
"These all are the things coming inside the metadata. If you wanted to utilize any sort of information, you can utilize that. Going forward, I will show you basically how you can create your own custom document object."

Creating Custom Document Objects

You can manually create Document objects and attach any metadata you want. This is useful when your data comes from a database, API, or non-standard source.

python · custom document 
from langchain.schema import Document

# Creating a custom Document object from scratch
custom_doc = Document(
    page_content="Our refund policy allows returns within 7 days of purchase. "
                 "Items must be unused and in original packaging.",
    metadata={
        "source":      "company_policy_db",
        "department":  "Customer Service",
        "doc_type":    "policy",
        "version":     "v2.1",
        "last_updated":"2026-06-15",
        "priority":    "high"
    }
)

print(custom_doc.page_content)
print(custom_doc.metadata)

# Create a list of custom documents (e.g. from a database query)
db_records = [
    {"text": "Leave policy: 12 days per year.",       "dept": "HR"},
    {"text": "Travel reimbursement limit: ₹5000/month.", "dept": "Finance"},
]
docs = [
    Document(page_content=r["text"], metadata={"department": r["dept"], "source": "hr_db"})
    for r in db_records
]
print(ff"Created {len(docs)} custom documents")
04 — Part 1: Simple Loading

LangChain Data Loaders — All 6 Types

Sunny demonstrated these loaders live, each with the same .load() method call — the standardisation that makes LangChain a wrapper rather than a parser.

PyMuPDFLoader
Files: .pdf

Default PDF loader. Extracts text page by page. One Document per page.

Backend: PyMuPDF (fitz)
CSVLoader
Files: .csv

Loads CSV files. One Document per row. page_content is key:value string of all columns.

Backend: Python csv module
JSONLoader
Files: .json

Loads JSON files. Requires jq_schema to navigate the JSON structure. One Document per JSON object.

Backend: jq (JSON query)
Docx2txtLoader
Files: .docx

Parses Microsoft Word files. Extracts full text content. One Document per file.

Backend: docx2txt / python-docx
UnstructuredHTMLLoader
Files: .html

Strips HTML tags and extracts clean text. One Document per HTML file.

Backend: Unstructured.io
TextLoader
Files: .txt, .md

Simple raw text loader. One Document for the entire file. Also works for .md files.

Backend: Python open()

JSON Loader — jq_schema Explained

python · JSON loader 
# Sample JSON structure:
# [
#   {"id": 1, "title": "Leave Policy", "content": "12 days per year..."},
#   {"id": 2, "title": "Refund Policy", "content": "7 days return window..."},
#   {"id": 3, "title": "Travel Policy",  "content": "₹5000 limit per month..."}
# ]

json_loader = JSONLoader(
    file_path   = "data/sample.json",
    jq_schema   = ".[  ]",     # extract each item from the top-level list
    text_content = False      # content is a dict/object, not a plain string
)
json_docs = json_loader.load()

print(ff"JSON documents: {len(json_docs)}")   # 3 objects → 3 documents
print(json_docs[0].page_content)
# {'id': 1, 'title': 'Leave Policy', 'content': '12 days per year...'}
print(json_docs[0].metadata)
# {'source': 'data/sample.json', 'seq_num': 1}

# jq_schema explained:
# ".[]"         → extract each element from a top-level list
# ".records[]"  → extract each item from {"records": [...]} structure
# ".[].content" → extract only the 'content' field as text_content

05 — Key Distinction

Simple Loading vs Real/Complex Parsing

Sunny made this distinction very clearly during the class — calling the LangChain loaders "partial data parsing" or "data loading/extraction." The real definition of data parsing is more demanding:

"The definition of the data parsing is to fetch the important component, to arrange the data according to our requirement. That is the actual definition of the data parsing. Simply, we can say over here, it's a data loading, or data extraction — partial data parsing — it's a correct word for this one."
Simple / Partial

LangChain Document Loaders

Quick, standardised, plug-and-play. Returns raw text. Sufficient for clean, simple documents.

  • Raw text extraction only
  • Tables returned as plain text
  • No image extraction
  • No structural preservation
  • Good for: simple PDFs, CSVs, JSON, DOCX
Complex / Real

From-Scratch Parsing (PyMuPDF / Docling)

Full structural understanding. Required for production real-world documents.

  • Text per page with positions
  • Tables → structured Markdown + JSON
  • Images extracted as files (PNG/JPG)
  • Page screenshots for visual inspection
  • OCR on scanned images
  • Good for: real PDFs with charts, tables, images
💡

Sunny's real-world insight: "If you're going to be working in any real-time project, you will also have to do the same thing. In real time, you will see a lot of complexity inside the PDF and the data. So I have done this thing a lot before creating a RAG."

PyMuPDF from Scratch — Complete Parser

Sunny wrote a complete PDF parser from scratch using PyMuPDF (fitz) that extracts everything — text, tables (as Markdown and JSON), images, and page-level screenshots.

python · complex PDF parser from scratch 
## ═══════════════════════════════════════════════════════════════
## CLASS 30 — Complex PDF Parser (from scratch using PyMuPDF)
## Extracts: text, tables (MD + JSON), images, page screenshots, OCR
## ═══════════════════════════════════════════════════════════════

import fitz           # PyMuPDF
import json
import os
from pathlib import Path

PDF_PATH   = "data/complex_document.pdf"
OUTPUT_DIR = "parse_complex_pdf_output"
os.makedirs(OUTPUT_DIR, exist_ok=True)
os.makedirs(f"{OUTPUT_DIR}/images",      exist_ok=True)
os.makedirs(f"{OUTPUT_DIR}/page_images", exist_ok=True)

doc = fitz.open(PDF_PATH)
print(ff"Total pages: {len(doc)}")

page_records  = []
table_records = []
image_records = []
all_markdown  = []

for page_num, page in enumerate(doc):

    # ── 1. Extract Text ───────────────────────────────────────────
    page_text = page.get_text("text").strip()

    # ── 2. Extract Page as Screenshot ─────────────────────────────
    mat  = fitz.Matrix(2.0, 2.0)  # 2x zoom for better resolution
    clip = page.get_pixmap(matrix=mat)
    page_img_path = f"{OUTPUT_DIR}/page_images/page_{page_num+1}.png"
    clip.save(page_img_path)

    # ── 3. Extract Tables → Markdown + JSON ──────────────────────
    tables    = page.find_tables()
    md_tables = []
    for tbl_idx, table in enumerate(tables):
        md_table = table.to_markdown()   # Markdown format
        md_tables.append(md_table)

        # Store as JSON record too
        table_records.append({
            "page":        page_num + 1,
            "table_index": tbl_idx,
            "markdown":    md_table,
            "raw":         table.extract()   # list of lists
        })

    # ── 4. Extract Embedded Images ────────────────────────────────
    img_list = page.get_images(full=True)
    for img_idx, img_info in enumerate(img_list):
        xref     = img_info[0]
        base_img = doc.extract_image(xref)
        img_bytes = base_img["image"]
        img_ext   = base_img["ext"]       # "png", "jpeg", etc.
        img_path  = f"{OUTPUT_DIR}/images/page{page_num+1}_img{img_idx+1}.{img_ext}"

        with open(img_path, "wb") as f:
            f.write(img_bytes)

        # Optional: OCR text from image using pytesseract
        # from PIL import Image
        # import pytesseract
        # ocr_text = pytesseract.image_to_string(Image.open(img_path))

        image_records.append({
            "page":        page_num + 1,
            "image_index": img_idx,
            "image_path":  img_path,
            "format":      img_ext,
            "ocr_text":    ""  # fill with pytesseract if available
        })

    # ── 5. Build Markdown content for this page ───────────────────
    page_md = f"## Page {page_num+1}\n\n{page_text}\n\n"
    if md_tables:
        page_md += "\n\n### Tables\n\n" + "\n\n".join(md_tables)
    all_markdown.append(page_md)

    page_records.append({
        "page":        page_num + 1,
        "text":        page_text,
        "image_path":  page_img_path,
        "num_tables":  len(md_tables),
        "num_images":  len(img_list),
    })

# ── Save all outputs ──────────────────────────────────────────────
# 1. RAG-ready Markdown file
with open(f"{OUTPUT_DIR}/rag_ready.md", "w") as f:
    f.write("\n\n".join(all_markdown))

# 2. Page records JSON
with open(f"{OUTPUT_DIR}/page_record.json", "w") as f:
    json.dump(page_records, f, indent=2)

# 3. Table records JSON
with open(f"{OUTPUT_DIR}/table_record.json", "w") as f:
    json.dump(table_records, f, indent=2)

# 4. Image records JSON
with open(f"{OUTPUT_DIR}/image_record.json", "w") as f:
    json.dump(image_records, f, indent=2)

print(ff"\n✓ Parsing complete!")
print(ff"  Pages processed:  {len(page_records)}")
print(ff"  Tables extracted: {len(table_records)}")
print(ff"  Images extracted: {len(image_records)}")
print(ff"  Output: {OUTPUT_DIR}/")

Docling — The Unified Parsing Alternative

After the PyMuPDF demo, Sunny introduced Docling as a higher-level library that does the same thing with less boilerplate. It's IBM's open-source document parsing framework.

"Docling is a library. It is a library for parsing the data. Now guys, Docling is what — Docling is a unified framework. It is not only for the PDF, or not only for the DOCX, it is for the multiple formats. Multi-modal capability, multi-document capability. Many things it can do. Even we can embed the images also."
python · Docling parser 
# !pip install docling
from docling.document_converter import DocumentConverter
from docling.datamodel.base_models import InputFormat

# ── Option 1: Docling directly ────────────────────────────────────
converter = DocumentConverter()
result    = converter.convert("data/complex_document.pdf")

# Export to different formats
md_output   = result.document.export_to_markdown()   # Markdown string
json_output = result.document.export_to_dict()        # structured dict

# Save the RAG-ready markdown
with open("docling_output.md", "w") as f:
    f.write(md_output)

# ── Option 2: Docling via LangChain (wrapper) ────────────────────
# !pip install langchain-docling
from langchain_docling import DoclingLoader

langchain_loader = DoclingLoader(file_path="data/complex_document.pdf")
docling_docs     = langchain_loader.load()

# Returns standard LangChain Document objects!

1. What are the two fields in a LangChain Document object, and what does each contain?

▶ Show Answer
page_content: the actual extracted text content from the file (full page text for PDFs, key:value row string for CSV, JSON object string for JSON, etc.). metadata: information about the data — source file path, page number, author, row number, creation date, and any other contextual information. This metadata is useful for source citation in RAG answers and for filtering during retrieval.

2. Sunny said LangChain "is a wrapper, not a parser." What does this mean in context of data loading?

▶ Show Answer
LangChain's document loaders don't do the actual low-level parsing themselves. Instead, they call actual parsing libraries internally: PyMuPDF for PDF loading, docx2txt for DOCX, jq for JSON, Unstructured.io for HTML, Python's built-in csv module for CSV. LangChain just provides a common interface (Document object with page_content + metadata) so all these different loaders work the same way in a pipeline. This is standardisation, not parsing.

3. When you load a CSV with LangChain's CSVLoader, what format does the page_content come in? Give an example.

▶ Show Answer
The page_content comes in key:value format — one line per column with the column name and its value separated by a colon. For example, a row with columns policy_id, department, topic would become:
policy_id: 101\ndepartment: HR\ntopic: Leave Policy\ndetail: 12 casual leaves per year\nlast_update: 2026-01-01
Each row becomes a separate Document object. The metadata contains the source file path and the row index.

4. What is jq_schema in JSONLoader and why is it needed? Give an example.

▶ Show Answer
jq_schema tells the JSONLoader which part of the JSON structure to extract as documents. JSON files can have data nested at different levels — in a list, inside a key, etc. For example, if your JSON is a list at the top level: [{...}, {...}], you use jq_schema=".[]" to extract each item. If it's {"records": [{...}, {...}]}, you use jq_schema=".records[]". Without specifying this, the loader doesn't know which part of the JSON to turn into Documents.

5. What is the key difference between "simple loading" (LangChain loaders) and "real/complex parsing" (PyMuPDF from scratch)? Give two concrete differences.

▶ Show Answer
Simple loading: (1) Tables are returned as raw unstructured text — no table structure preserved. (2) Images embedded in PDFs are not extracted. Real/complex parsing: (1) Tables are extracted as proper Markdown tables (or JSON) — structure is preserved, LLMs can reason about them accurately. (2) Images are extracted as separate PNG/JPEG files that can be processed (OCR, passed to multimodal LLMs) or stored with the document. Complex parsing also extracts page-level screenshots, OCR text from scanned images, and allows fine-grained control of the entire document structure.

6. What output files does the PyMuPDF complex parser produce, and what is each used for in RAG?

▶ Show Answer
rag_ready.md: Complete document as clean Markdown (text + table structures) — directly fed into the vector database for text-based RAG. page_record.json: Per-page metadata including text content, image path, number of tables and images per page. table_record.json: All extracted tables in both Markdown and JSON formats — useful for structured data retrieval. image_record.json: Metadata for all extracted images including file path, format, and OCR text. images/ folder: Actual image files extracted from the PDF (PNG/JPEG) — can be passed to multimodal LLMs. page_images/ folder: Full-page screenshots at 2x resolution — fallback if text extraction misses content.

7. How is Docling different from PyMuPDF as a parsing library, and can it be used with LangChain?

▶ Show Answer
Docling (by IBM) is a unified, higher-level framework that handles multiple file formats (PDF, DOCX, HTML, PowerPoint) with one API, whereas PyMuPDF is specifically for PDFs. Docling includes built-in OCR capability, image embedding support, and can export to Markdown, JSON, or XML. PyMuPDF requires more manual code for complex extractions. Yes, Docling can be used with LangChain via the langchain-docling package (DoclingLoader class) — it returns the same standard LangChain Document format (page_content + metadata), making it a drop-in replacement in any LangChain RAG pipeline.
