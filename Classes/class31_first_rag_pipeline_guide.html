09 — Step 2

Chunking — Splitting Documents

Why Chunk? — Sunny's Phone Number Analogy

Sunny gave a brilliantly simple analogy for why chunking is needed:

"If someone is asking your number — so how you are telling your phone number? Are you giving all the 10 characters in one single go? No! You are saying: '877'… '020'… '3258'. Someone is saying in 2 digits, someone in 3 digits. So they are saying the number in the form of chunk. This is just a way of processing information. In the same way, let's say we have a PDF with 55 pages — we cannot provide all pages to the LLM in single go. LLM is having some context length — let's say 4096 tokens — it can only process that much of data."

Three reasons chunking is needed:

Context Length Limit

LLMs have a maximum number of tokens they can process at once. A 58-page PDF far exceeds any LLM's context window.

Better Retrieval

Smaller, focused chunks retrieve more precisely. A 200-char chunk about a specific topic is retrieved better than an entire page with many topics.

Cost Efficiency

Only the top-k most relevant chunks are sent to the LLM — not the whole document. Reduces tokens → reduces API cost.

📌

Chunking is optional for small docs: Sunny noted explicitly that "chunking is not always required." For a 1-2 page document that fits entirely in the LLM's context window, you can skip chunking and just pass the whole document. Chunking becomes necessary when documents exceed the context limit.

chunk_size and chunk_overlap Explained

How RecursiveCharacterTextSplitter works — chunk_size=500, overlap=200
Document text split into overlapping chunks:
Chunk 1
chars 0–500
← overlap
300–500
Chunk 2
chars 300–800
← overlap
600–800
Chunk 3
chars 600–1100
Overlap ensures information spanning a chunk boundary isn't lost. If a key sentence crosses the boundary, at least one chunk contains it fully.
python · chunking 
from langchain.text_splitter import RecursiveCharacterTextSplitter

# ── Experiment 1: chunk_size=500, overlap=200 ─────────────────────
splitter_v1 = RecursiveCharacterTextSplitter(
    chunk_size    = 500,   # max characters per chunk
    chunk_overlap = 200    # characters shared between adjacent chunks
)
chunks_v1 = splitter_v1.split_documents(pages)
print(ff"v1 chunks: {len(chunks_v1)}")   # 588 chunks

# ── Experiment 2: chunk_size=1000, overlap=300 ────────────────────
splitter_v2 = RecursiveCharacterTextSplitter(
    chunk_size    = 1000,
    chunk_overlap = 300
)
chunks_v2 = splitter_v2.split_documents(pages)
print(ff"v2 chunks: {len(chunks_v2)}")   # ~283 chunks (fewer, larger)

# ── Inspect a chunk ───────────────────────────────────────────────
first_chunk = chunks_v1[0]
print(first_chunk.page_content)       # actual text content
print(first_chunk.metadata)           # source, page, author, etc.

# Separators used by RecursiveCharacterTextSplitter (priority order):
# ["\n\n", "\n", ".", ""]
# → tries to split on double newline first (paragraph break)
# → then single newline (line break)
# → then full stop (sentence boundary)
# → finally, character by character (last resort)
# This preserves semantic coherence within chunks.

13 — Step 6

LCEL RAG Chain — Putting It All Together

LCEL = LangChain Expression Language. The pipe operator (|) chains components together. Sunny built the chain by identifying what inputs the prompt needs and where each comes from:

Chain Logic — How the pieces connect
{context} ← comes from retriever | format_docs()
{question} ← comes from RunnablePassthrough() (passes input directly through)
Full chain:
{"context": retriever|format_docs, "question": passthrough} | prompt | llm | StrOutputParser() → Final answer
python · LCEL RAG chain 
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables   import RunnablePassthrough

# ── Helper: format retrieved documents into a single string ───────
def format_docs(docs):
    """Join page_content of retrieved chunks into one context string."""
    return "\n\n".join(doc.page_content for doc in docs)

# ── Build the RAG chain (LCEL syntax) ────────────────────────────
rag_chain = (
    {
        "context":  retriever | format_docs,   # retrieve → format context
        "question": RunnablePassthrough()     # pass question unchanged
    }
    | prompt             # insert context + question into prompt template
    | llm                # send augmented prompt to the LLM
    | StrOutputParser() # extract text from LLM response object
)

# ── Invoke the RAG chain ──────────────────────────────────────────
question = "How many parameters are there in DeepSeek B4 Pro model?"
answer   = rag_chain.invoke(question)
print(ff"Answer: {answer}")
# → "1.6 trillion total parameters, with 419 billion active per token."

# ── Try another question ─────────────────────────────────────────
answer2 = rag_chain.invoke(
    "Which reinforcement learning method was used in DeepSeek B4?"
)
print(ff"Answer 2: {answer2}")
# → Mentions GRPO (Group Relative Policy Optimization)

# ── Compare with simple LLM (no RAG) ─────────────────────────────
simple_answer = llm.invoke(question).content
print(ff"\nSimple LLM: {simple_answer}")
# → "There is no such model as DeepSeek B4 Pro."  ← hallucination!

print(f"\n--- Comparison ---")
print(ff"RAG answer:    {answer}")
print(ff"Simple answer: {simple_answer}")

16 — Key Learnings

Lessons from the Live Demo

⚠ Lesson 1: Query wording matters enormously

When Sunny asked about "RLHF" in DeepSeek B4, the RAG returned no relevant result — because the paper uses "GRPO" and "Reinforcement Learning," not the acronym "RLHF." Changing the query to "reinforcement learning" immediately retrieved the correct chunks. The exact words in your query must match the vocabulary in the document.

💡 Lesson 2: k matters — more context vs more noise

Sunny increased k from 3 to 10 when certain questions didn't find the right answer. More chunks means more context, but also more noise. Finding the right k is a hyperparameter you tune per dataset and use case.

📝 Lesson 3: Prompt instructions help fill semantic gaps

When the query vocabulary doesn't match the document vocabulary, you can add custom instructions to the prompt: "If the user says RLHF, they mean reinforcement learning from human feedback — also look for GRPO and similar terms." Prompt engineering and RAG work together.

✅ Lesson 4: The pipeline is consistent across LLMs

Sunny mentioned you can swap Gemini for Groq, OpenAI GPT, Claude, or local Ollama — the pipeline code stays identical. Only the model class changes. This is LangChain's superpower: a unified interface across all LLM providers.

17 — From the Q&A

RAG vs MCP — Sunny's Explanation

A student asked an excellent question during the live Q&A. Sunny's answer is worth preserving:

Q — Student

"RAG and MCP — in the context of live data extraction, how are they the same or different? Can MCP replace RAG?"

A — Sunny

RAG = connecting an LLM to an external data source (knowledge base) to answer questions. The output is a knowledge-grounded answer.

MCP = Model Context Protocol — standardises how LLMs call tools and external software (GitHub, Slack, Google Drive, file system, database, browser) via client-server architecture. The output is a tool execution or action.

Key difference: "RAG is for knowledge-based retrieval. MCP is to make a standardised process to call a tool — which is called an action."

How they work together: You can wrap a RAG pipeline as a tool, expose it as an MCP server, and then an agentic system can invoke the RAG retrieval as one of many actions. "We can bind this particular retrieval process as a tool, and we can expose it as an MCP." → Covered in the Agentic AI chapter.

18 — Self-Check

Quiz — Test Your Understanding

📝 Class 31 Concept Check

1. What are the 2 models required for any RAG system, and what does each do?

▶ Show Answer
Model 1: Embedding Model — converts text (both document chunks during ingestion and user questions at query time) into dense numerical vectors. Used in both the ingestion and retrieval phases. Model 2: LLM (Chat Model) — generates the final answer from the augmented prompt (retrieved context + user question + instructions). Used in the generation phase only. Without the embedding model, you can't do similarity search. Without the LLM, you can't generate a final answer.

2. Using Sunny's phone number analogy, explain why chunking is needed.

▶ Show Answer
Just like when someone asks for your phone number, you say it in chunks ("877", "020", "3258") rather than 10 digits at once — because that's how humans process information — LLMs also process information in chunks. A 58-page PDF contains far more text than an LLM can handle in one go (e.g. 4096 token context limit). Chunking splits the PDF into manageable pieces that fit within the LLM's context window. At retrieval time, only the top-k most relevant chunks are sent to the LLM, not the entire document.

3. What does chunk_overlap do, and why is it useful?

▶ Show Answer
Chunk overlap means adjacent chunks share some characters. For example with chunk_size=500 and overlap=200: Chunk 1 covers chars 0–500, Chunk 2 covers chars 300–800, sharing chars 300–500. This ensures that information spanning a chunk boundary isn't lost — if a key sentence crosses the split point, at least one chunk contains the complete sentence. Without overlap, you might miss crucial information that straddles a chunk boundary.

4. What is the role of RunnablePassthrough() in the LCEL RAG chain?

▶ Show Answer
RunnablePassthrough() simply passes its input through unchanged — it's an identity function in the chain. In the RAG chain, the prompt template needs two inputs: "context" (from the retriever) and "question" (the user's question). The retriever processes the question and returns chunks, but the prompt also needs the original question text. RunnablePassthrough() takes whatever was passed to the chain's invoke() call (the user's question string) and passes it directly to the "question" key in the prompt, without modification.

5. Sunny demonstrated a case where RAG still failed to return the right answer. What was the root cause and how did he fix it?

▶ Show Answer
The root cause was vocabulary mismatch: Sunny asked about "RLHF" (Reinforcement Learning from Human Feedback) but the research paper uses "GRPO" and "reinforcement learning" — not the acronym "RLHF." Since RAG retrieval works by semantic similarity between the query vector and document chunk vectors, if the exact term isn't present in the document, the relevant chunks won't be retrieved. 6. What is the primary difference between RAG and MCP? Can they work together?

▶ Show Answer
RAG = connecting LLMs to knowledge bases (documents, PDFs) to answer questions with grounded, factual answers. It's about knowledge retrieval. MCP = Model Context Protocol — a standardised way for LLMs to call external tools and software (GitHub, Slack, databases, file systems) via client-server architecture. It's about tool execution and actions. They work together: you can wrap a RAG pipeline as a tool, expose it as an MCP server, and an agentic system can invoke RAG retrieval as one of many actions alongside other tools. This is covered in the Agentic AI chapter.
