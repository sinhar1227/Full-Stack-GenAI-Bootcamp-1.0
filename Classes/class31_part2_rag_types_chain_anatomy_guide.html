Step 2 — The Real Errors (Live Debugging)

Sunny hit two real errors back-to-back. These are documented here because they happen to real developers and the fixes are instructive:

Error 1 — Gemini Embedding Quota Exhausted

ResourceExhausted: 429 You have exceeded your current quota, please check your plan and billing details.

Cause: The free tier Gemini embedding model (models/embedding-002) has very low quota limits — cannot embed 588 chunks in one go. Fix: Switch to OpenAI embeddings (text-embedding-3-small), which has a paid tier with much higher limits. Alternatively: use HuggingFace local embeddings (no quota at all).

✅

Sunny's advice on embedding quota errors: "If you're getting this kind of error, change the model. Use a different model, test with a different model. Even you can create a smaller number of chunks — increase the chunk size, then this model might work. If you want good accuracy and money is not a constraint, use OpenAI or Anthropic-based embedding models."

Error 2 — FAISS Dimension Mismatch

add_documents not implemented / dimension mismatch error

Cause: Sunny created the FAISS index with dimension=384 (for HuggingFace all-MiniLM) but then switched to OpenAI embeddings which output 1536 dimensions (text-embedding-3-small). The FAISS index and the embedding model dimensions must match exactly. Fix: Recreate the FAISS index with the correct dimension.

python · dimension mismatch fix 
from langchain_openai import OpenAIEmbeddings
import faiss
from langchain_community.vectorstores import FAISS

# ── Step 1: Get the actual dimension from the model ───────────────
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")
test_vec = embedding_model.embed_query("test")
dim = len(test_vec)
print(ff"Actual embedding dimension: {dim}")
# text-embedding-3-small → 1536
# text-embedding-3-large → 3072
# all-MiniLM-L6-v2 (HuggingFace) → 384
# ALWAYS check before creating the FAISS index!

# ── Step 2: Create FAISS index with CORRECT dimension ─────────────
# This must match dim above — or you'll get a mismatch error
index = faiss.IndexFlatL2(dim)   # use actual dim, not hardcoded 384

vector_store = FAISS(
    embedding_function   = embedding_model,
    index                = index,
    docstore             = FAISS._InMemoryDocstore({}),
    index_to_docstore_id = {}
)

# ── Step 3: Add documents — each gets a UUID ─────────────────────
vector_store.add_documents(chunks)   # chunks from text splitter
# Returns list of UUIDs — one per stored chunk
# ["abc-123...", "def-456...", ...]
print(f"✓ Data ingestion complete — {len(chunks)} chunks stored")

04 — Blackboard Revision

LCEL RAG Chain — Every Component Explained

After the live demo, Sunny put the RAG chain on the blackboard and explained each component from first principles. This is the clearest explanation of what each piece does.

RAG Chain — Component by Component
{"context": retriever | format_docs,
"question": RunnablePassthrough()}
Builds the dict of inputs the prompt needs. Context comes from retriever → format_docs. Question passes straight through.
→
prompt
ChatPromptTemplate inserts context + question into the template string. Formats the final augmented prompt.
→
llm
The chat LLM (Gemini, GPT, Claude, Groq, Ollama). Receives the formatted prompt. Returns an output message object.
→
StrOutputParser()
Extracts the plain string text from the LLM's output message object. Returns a readable string answer.

format_docs() — What It Really Does

"Context is coming from the vector database. format_docs means what? So whatever context we are retrieving, it is a Document object. From this Document object, what we are doing — we are going to be extract the page content. That's the meaning of the format document. We are joining all the page_content strings of the retrieved chunks into one big string."
python · format_docs anatomy 
# What the retriever returns: a list of Document objects
retrieved_docs = retriever.invoke("some query")
# [Document(page_content="...", metadata={...}),
#  Document(page_content="...", metadata={...}),
#  Document(page_content="...", metadata={...})]

# format_docs extracts only page_content and joins them
def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

# Result: one big context string ready for the prompt
# "...text of chunk 1...\n\n...text of chunk 2...\n\n...text of chunk 3..."

# This string fills {context} in the prompt template
# The user's query fills {question} via RunnablePassthrough()

Output Parser Types

"If you want to convert that particular output into the JSON, then I will be using the JSON parser. If I wanted to convert that particular output into the HTML, into the YAML, so I'll be using that particular parser. As of now I wanted to show you that output in the final string format — that's why I'm using StrOutputParser."
StrOutputParser()

Extracts the text content from the LLM's AIMessage. Returns a plain Python string. Most common.

JsonOutputParser()

Parses LLM output as JSON. Use when you need structured data back from the LLM.

PydanticOutputParser()

Validates and parses output into a Pydantic model. Strong typing for structured LLM outputs.

XMLOutputParser()

Parses LLM output as XML. Useful when the LLM is instructed to generate structured XML responses.

LCEL vs Old Chain Methods

"In the LCEL, what we do, we use this pipe operator in the LangChain, and we are going to connect all the components of the RAG. Before that, basically, we were having the specific chaining method — sequential chaining, parallel chaining. Different, different chaining methods were there in the previous LangChain version. But now in the updated version, basically, we just have this LCEL method. Everything working in the backend."
Old LangChain (deprecated)
  • → LLMChain
  • → SequentialChain
  • → SimpleSequentialChain
  • → ConversationalRetrievalChain
Modern LangChain (LCEL)
  • → a | b | c | d (pipe operator)
  • → RunnablePassthrough()
  • → RunnableParallel()
  • → RunnableLambda()

Composable, lazy evaluation, streaming support, more Pythonic.

05 — Key Insight

RAG's "Moving Variables" — Why It's Complex

"RAG seems very simple. But if you will see the RAG — there are so many moving components in the RAG. So many variable things. The final output completely depends on all of these. This is where the real engineering skill in RAG comes in."
Moving VariableWhat it meansImpact on output quality
Data Parsing How well you extract clean text from source files — simple loader vs complex from-scratch parser High — garbage in, garbage out. Poor parsing → missing context → wrong answers
Chunking Whether to chunk, what chunk_size, what overlap, which splitter strategy High — too large = noisy context; too small = missing full sentences; wrong strategy = broken semantics
Embedding Model Which model to use, its dimension, its domain (general vs code vs multilingual) High — poor embedding = irrelevant chunks retrieved = wrong answer even if data is correct
Vector Database Which DB, which index type, similarity metric, hosting (local vs cloud) Medium — affects speed, scalability, and filtering capabilities
Retrieval (k, strategy) How many chunks to retrieve (k), similarity threshold, MMR, hybrid, reranking High — too few = missing info; too many = noise; wrong strategy = irrelevant chunks
Prompt Template System instructions, output format, vocabulary hints, persona, strictness High — poorly written prompt = hallucination even with correct context retrieved
LLM Model Which LLM, temperature, context window, reasoning capability Medium-High — some LLMs follow grounding instructions better; larger models reason better over context
06 — Architecture Types

The 3 Types of RAG

Sunny introduced this taxonomy during the blackboard revision — a framework for thinking about different RAG architectures.

Type 1

Vector DB RAG

The standard RAG. All retrieval is based on embedding similarity — cosine/dot/Euclidean distance in a vector database. Both documents and queries are embedded as dense vectors. Most RAG systems use this.

What we've been building

✓ Best accuracy · ✓ Most researched · ✓ Works for most use cases

Type 2

Vectorless RAG

Retrieval using keyword search, BM25, metadata filters — not embedding-based. No vector database needed. An old approach — keyword search is decades old. Not magic, just a different retrieval method.

Not as new as it sounds

✓ Works for small, structured docs · ✗ Misses semantic meaning · ✗ No research paper dominance

Type 3

Graph-Based RAG

Data is arranged as a knowledge graph — entities (nodes) and relationships (edges). Retrieval traverses the graph to find connected, relevant information. Requires entity extraction and relationship mapping from your data.

LangGraph chapter covers this

✓ Excellent for relationship-heavy data · ✗ Complex to build · ✗ Requires POC to validate

"Vectorless RAG — it is an old method of retrieving the information. Don't think that vectorless RAG is some magic, or it's a new thing. No. You will find very few research papers on it — and even those give more weightage to the vector-based system. In some small documents, it is working a little well compared to vector DB, but it's not completely magic."

07 — Infrastructure

4 Ways to Host a Vector Database

"In today's solution, what kind of database we have used? In-memory! Because that is going to be vanished once you stop the server. The data is not persistent — it is stored in RAM. Going forward, I will show you all the other types."
Vector Database Hosting — Full Map
🗄 Vector Database
📦 Local (on your machine)
1. In-Memory (Volatile) — data in RAM, lost on restart · FAISS default · ChromaDB no persist_directory
2. On-Disk (Persistent) — saved to local filesystem · FAISS save_local() · ChromaDB persist_directory
☁️ Cloud
3. Third-Party Managed (SaaS) — vendor manages everything · Pinecone · Qdrant Cloud · Weaviate
4. Cloud-Provider Managed — your cloud provider's service · AWS OpenSearch · Azure AI Search · Google Vertex AI

Local: In-Memory vs On-Disk

In-Memory (Volatile)

  • → Data lives in RAM
  • → Lost when process stops
  • → Fastest (no disk I/O)
  • → Today's class used this
  • → FAISS without save_local()

On-Disk (Persistent)

  • → Data saved to local files
  • → Survives restarts
  • → Single machine only
  • → vector_store.save_local()
  • → Chroma(persist_directory=...)

Cloud: Third-Party vs Provider

Third-Party Managed

  • → Dedicated vector DB vendors
  • → Best-in-class for vector search
  • → No infra management
  • → Pinecone, Qdrant Cloud, Weaviate

Cloud-Provider Managed

  • → Your cloud provider's service
  • → Integrated with existing infra
  • → Enterprise standard
  • → AWS OpenSearch, Azure AI Search

When you give an LLM too much context, you get: (1) higher API cost (more tokens), (2) potential dilution where relevant info gets buried in noise, and (3) hitting context window limits. Context condensing solves this by passing a shorter, denser representation. We'll cover this in the Prompting and Generation sessions."

09 — Self-Check

Quiz — Test Your Understanding

📝 Class 31 Part 2 — Concept Check

1. What causes a FAISS dimension mismatch error and how do you fix it?

▶ Show Answer
The error occurs when the FAISS index was created with a specific dimension (e.g. 384 for HuggingFace all-MiniLM-L6-v2) but the actual embedding model being used has a different output dimension (e.g. 1536 for text-embedding-3-small or 3072 for text-embedding-3-large). Fix: always check the actual embedding dimension first with len(embedding_model.embed_query("test")), then use that value when creating the FAISS index: faiss.IndexFlatL2(actual_dim). Never hardcode a dimension without verifying it against your specific model.

2. What exactly does format_docs() do in the RAG chain, and why is it needed?

▶ Show Answer
format_docs() takes a list of LangChain Document objects (returned by the retriever) and extracts the page_content field from each, then joins them into one single string separated by double newlines. It's needed because the prompt template expects a plain string for the {context} variable, but the retriever returns Document objects. Without format_docs, you'd be inserting a Python list representation into the prompt rather than readable text. The function is: def format_docs(docs): return "\n\n".join(doc.page_content for doc in docs)

3. What are the 3 types of RAG? For each, describe what makes it different.

▶ Show Answer
Type 1 — Vector DB RAG: Standard RAG using embedding models and vector databases. All retrieval is based on cosine/dot/Euclidean similarity between embedded query and stored chunk vectors. Most researched and most effective for most use cases. Type 2 — Vectorless RAG: Uses keyword search (BM25), metadata filtering, or lexical matching — no embeddings required. An older approach, not magic, works best for small structured documents but misses semantic meaning. Type 3 — Graph-based RAG: Data is structured as a knowledge graph with entities (nodes) and relationships (edges). Retrieval traverses the graph. Complex to build, best for relationship-heavy data, requires POC validation.

4. What are the 4 ways to host a vector database? Give one example for each.

▶ Show Answer
1. In-Memory (Local volatile): data lives in RAM, lost on restart. Example: FAISS without save_local(). 2. On-Disk (Local persistent): saved to local filesystem, survives restarts. Example: FAISS with save_local() or ChromaDB with persist_directory. 3. Third-Party Managed SaaS: dedicated vector DB vendors host everything. Example: Pinecone (hosted on AWS) or Qdrant Cloud. 4. Cloud-Provider Managed: your cloud provider's managed vector search service. Example: AWS OpenSearch or Azure AI Search.

5. Sunny said "RAG seems very simple, but there are so many moving variables." Name 4 of the key moving variables and briefly describe how each affects output quality.

▶ Show Answer
Any 4 from: (1) Data Parsing — quality of extracted text; poor parsing = noisy chunks = wrong answers. (2) Chunking — size and overlap; too large adds noise, too small breaks meaning. (3) Embedding Model — which model determines vector quality; wrong model = irrelevant chunks retrieved. (4) Retrieval strategy — k value, similarity metric, MMR; too few chunks = missing info, too many = noise. (5) Prompt Template — system instructions, vocabulary hints; poor prompt = hallucination even with correct context. (6) LLM — some models follow grounding instructions better than others.

6. A student mentioned using hybrid retrieval after pure semantic search failed. What is hybrid retrieval and when should you use it?

▶ Show Answer
Hybrid retrieval combines two retrieval methods: (1) semantic similarity search using embeddings (dense retrieval) and (2) keyword-based search like BM25 (sparse retrieval). Results from both are combined and ranked. Use it when: your query vocabulary doesn't match document vocabulary (semantic search misses relevant chunks), you have precise technical terms that benefit from exact matching, or you need better recall in production. The student's scenario — relevant chunk existed in pgvector but wasn't retrieved by semantic alone — is a classic case where hybrid retrieval helps. Adding query rewriting (which rewrites the query to better match document language) can also help with vocabulary mismatch.
