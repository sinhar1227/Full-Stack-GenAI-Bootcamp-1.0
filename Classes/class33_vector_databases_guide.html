02 — Core Concept

What is a Vector Database?

The Definition (from Sunny's Blackboard)

Definition
A Vector Database stores data as numerical vectors (embeddings)
and retrieves the most similar vectors using similarity search
"Vector Database store data as a numerical vector, which is called the embedding. And retrieve the most similar vector using the similarity search. So if two vectors are near to each other, then those vectors we are going to be retrieved. If the vector are not near to each other, the information is not similar — we are not going to retrieve that particular data."

Vector databases are used primarily for:

🔍 Semantic Search (RAG)
🎯 Recommendation Systems
🖼 Image Search
💬 Chatbot Memory

What is a Vector Index?

Sunny's definition from the blackboard:

Vector Index — a data structure that organises embeddings so that the vector database can find vectors quickly without comparing the query with every stored vector.

"Vector Index is nothing — it is just a way of organising the embedding. Vector Database stores the vectors. The Vector Index makes searching those vectors faster. Whenever we are going to store the data inside the Vector database, we are going to organise it in the form of index only."
💡

Think of it like a book's index. Without an index you'd read every page to find a topic. With an index, you jump to page 312. Vector indices do the same for embedding space — they let the database skip most vectors and go straight to the relevant ones.

03 — How Retrieval Works

Similarity Search — The 3 Methods

Similarity search is the process of finding stored vectors that are closest or most similar to a query vector. Sunny covered 3 methods:

📐

Cosine Similarity

Measures the angle between two vectors. Returns a score between -1 and 1. A score of 1 = identical direction (same meaning). Ignores magnitude, only cares about direction.

✓ Best for: text, RAG, most NLP tasks
📏

Euclidean Distance

Measures the straight-line geometric distance between two vector points. Smaller distance = more similar. Sensitive to vector magnitude (length).

✓ Best for: image search, spatial data
🔢

Dot Product

Multiplies corresponding elements and sums them. Higher dot product = more similar. Faster to compute than cosine. Affected by both angle and magnitude.

✓ Best for: when vectors are normalised
"Similarity search — example: search for 'how I can recover my account' — it may retrieve 'step to reset your password', because both have similar meaning, even though the words are different. This is called semantic search — results found by meaning rather than exact keyword matching."

How a Query is Processed

The step-by-step flow from Sunny's blackboard demonstration:

Query Processing Flow
User Query: "ML is future" → Embedding Model → [5, 6, 7, 8, 9, 10, 60, 55…]
↓
Cosine Similarity / Euclidean / Dot Product vs all stored vectors in the index
↓
Top-K Results → "AI is the future" (D1) is most similar ✓

The query "ML is future" retrieves "AI is the future" because both sentences have similar semantic meaning — vectors point in nearly the same direction in embedding space.

04 — How Data is Organised

Index Types in Vector Databases

Sunny covered 3 index types that determine how vectors are organised and searched. The choice of index directly determines search speed vs accuracy tradeoff.

Flat Index
aka IndexFlatL2 / IndexFlatIP

Exact Search

Stores all vectors as-is with no organisation. Every query compares against every stored vector. Always returns the exact best result — 100% accuracy.

Exact Nearest Neighbour (ENN)

✓ Best for: small datasets (POC/MVP). ✗ Slow on large datasets — O(n) comparison.

IVF Index
Inverted File Index

Cluster-Based ANN Search

Divides the vector space into clusters (like K-Means clustering). Similar vectors go into the same cluster. At query time, only the nearest cluster(s) are searched — skipping most data.

Approximate Nearest Neighbour (ANN)

✓ Faster than flat. ✓ Scales to large datasets. ✗ May occasionally miss the exact best result.

HNSW Index
Hierarchical Navigable Small World

Graph-Based ANN Search

Builds a multi-layer graph where nodes are vectors and edges connect similar ones. Traverses the graph hierarchically — top layers for coarse navigation, bottom layers for fine precision. Graph-based technique.

Approximate Nearest Neighbour (ANN)

✓ Fastest ANN method. ✓ Excellent accuracy-speed tradeoff. Default in Qdrant, ChromaDB.

Exact Search vs Approximate Nearest Neighbour (ANN)

MethodIndex TypeAccuracySpeedBest For
Exact Search (ENN) Flat Index 100% — always exact Slow on large data (O(n)) Small datasets, POC, MVP
Approximate Search (ANN) IVF / HNSW ~95–99% — very close Much faster (skip most data) Large-scale production search
"Exact search — check all the query against every stored vector, and return the nearest true match. ANN — only searches a selected part of the index, returns very close match, faster, but it may occasionally miss the exact best result. Accuracy-wise, exact is good. Speed-wise, ANN is good. If you have a lot of data, and you want to build the index — you can negotiate some sort of accuracy. In that case, go with approximate nearest search."
⚠️

Interview tip from Sunny: "In interviews, no one will ask you the in-depth mathematics of HNSW. They will just ask: what are the different types of index we have, and how does it work? That's it. Most people will not ask the deep mathematics — it's one case out of 100."

4 Categories of Vector Databases

Category 1

In-Memory

  • FAISS (in-memory mode)
  • ChromaDB (in-memory mode)

Data lives in RAM only. Lost when process restarts. Fastest. Best for POC and experimentation.

Category 2

Local Persistent (Disk)

  • FAISS (save_local)
  • ChromaDB (persist_directory)
  • Qdrant (local mode)
  • Milvus (local)

Data saved to local disk. Survives restarts. Still single-node. Good for dev/local projects.

Category 3

Vendor Managed (SaaS)

  • Pinecone
  • Qdrant Cloud
  • Milvus Cloud (Zilliz)
  • Weaviate Cloud

Fully managed by vendor. No infrastructure to manage. Paid. Best for production without DevOps overhead.

Category 4

Cloud Provider Managed

  • AWS OpenSearch
  • Azure AI Search
  • Google Vertex AI Vector Search
  • Google BigQuery Vector Search

Enterprise preference. Integrated with cloud services. Self-hosted is also possible for any of these.

Vector Database vs Vector Store — The Difference

Sunny made this distinction very clearly:

Vector Database

A complete system. Supports distribution, sharding (splitting large DB across multiple servers), replication, CRUD operations, backups. Like a proper database engine. Use for full production-grade systems.

Vector Store

A simple store — in-memory or persistent, but without distribution, sharding, or full database capabilities. FAISS and ChromaDB in local mode are vector stores. Use for POC, MVP, prototyping.

"Generally, for any basic prototype, POC, MVP — we can utilise the normal Vector Store. If we are going to create a full-scale production-grade solution — there we prefer the complete system. Both terms are used interchangeably in the industry, but technically there is this difference."

But dedicated vector databases (FAISS, Qdrant, Pinecone) remain the best choice when vector search is your primary workload.

07 — Hands-On Code

FAISS — Complete Practical (Class Demo)

Sunny built the FAISS vector store step by step in VS Code. Files created: Vector Database/faiss/faiss.ipynb. Here is everything Sunny demonstrated:

Step 1 — Setup: Create FAISS Index + Vector Store

python · FAISS setup 
# !pip install langchain langchain-community faiss-cpu sentence-transformers openai

import faiss
from langchain_community.vectorstores import FAISS
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain.schema import Document

# ── Embedding model ───────────────────────────────────────────────
# Using a local HuggingFace model — no API key needed, runs on CPU
embedding_model = HuggingFaceEmbeddings(
    model_name = "sentence-transformers/all-MiniLM-L6-v2"
)

# Check the embedding dimension (needed for FAISS index creation)
sample_embed = embedding_model.embed_query("test")
dimension = len(sample_embed)
print(ff"Embedding dimension: {dimension}")  # e.g. 384 or 3072

# ── Create FAISS Index manually (Flat Index = exact search) ───────
# IndexFlatL2  → Euclidean distance (L2 norm)
# IndexFlatIP  → Inner product / dot product (cosine if normalised)
faiss_index = faiss.IndexFlatL2(dimension)   # ← Flat index, exact search

# ── Create LangChain FAISS Vector Store ──────────────────────────
# This wraps the raw FAISS index with LangChain's document management
vector_store = FAISS(
    embedding_function = embedding_model,
    index              = faiss_index,
    docstore           = FAISS._InMemoryDocstore({}),  # in-memory!
    index_to_docstore_id = {}
)
print("✓ FAISS vector store created (in-memory, Flat Index)")

Step 2 — Add Documents to the Vector Store

python · add documents 
# ── Create Documents (LangChain Document objects) ─────────────────
# Sunny created these manually in the demo
docs = [
    Document(page_content="Donald Trump is the president of the USA.",
             metadata={"source": "news", "date": "2025-01-20"}),
    Document(page_content="Washington D.C. is the capital of the USA.",
             metadata={"source": "wiki"}),
    Document(page_content="The USA has 50 states.",
             metadata={"source": "wiki"}),
    Document(page_content="Python is a popular programming language.",
             metadata={"source": "tech"}),
    Document(page_content="Machine learning is a subset of artificial intelligence.",
             metadata={"source": "ai_blog"}),
]

# ── Add documents to vector store ────────────────────────────────
# LangChain automatically: embeds each doc → stores in FAISS index
vector_store.add_documents(docs)
print(ff"Added {len(docs)} documents to FAISS")

# ── Inspect: see the index-to-docstore mapping ────────────────────
print(vector_store.index_to_docstore_id)
# {0: 'some-uuid', 1: 'another-uuid', 2: '...', ...}
# Each FAISS index position maps to a document ID

# ── Fetch a specific document by FAISS index ID ───────────────────
faiss_idx = 1
doc_store_id = vector_store.index_to_docstore_id[faiss_idx]
retrieved_doc = vector_store.docstore.search(doc_store_id)
print(ff"Document at FAISS index {faiss_idx}:")
print(ff"  content: {retrieved_doc.page_content}")
print(ff"  metadata: {retrieved_doc.metadata}")

# ── View the raw embedding of a stored document ───────────────────
embedding_vector = vector_store.index.reconstruct(faiss_idx)
print(ff"Embedding shape: {embedding_vector.shape}")  # e.g. (384,)

Step 3 — Similarity Search

python · similarity search 
# ── Basic similarity search ───────────────────────────────────────
query = "Who is the president of the USA?"

# k = number of top documents to return
results = vector_store.similarity_search(query, k=1)
print(ff"Top 1 result: {results[0].page_content}")
# → "Donald Trump is the president of the USA."  ✓

# Return top 2 documents
results = vector_store.similarity_search(query, k=2)
for i, doc in enumerate(results):
    print(ff"  [{i+1}] {doc.page_content}")
# → [1] Donald Trump is the president of the USA.
# → [2] Washington D.C. is the capital of the USA.

# Return top 5 documents
results = vector_store.similarity_search(query, k=5)
print(ff"Top 5 results:")
for doc in results:
    print(ff"  - [{doc.metadata['source']}] {doc.page_content[:60]}")

# ── Similarity search with SCORE ─────────────────────────────────
# Returns (Document, score) tuples — lower score = more similar (L2)
results_with_scores = vector_store.similarity_search_with_score(query, k=3)
for doc, score in results_with_scores:
    print(ff"  Score: {score:.4f} | {doc.page_content[:50]}")
# Lower L2 distance = more similar
# Score: 0.3421 | Donald Trump is the president of the USA.
# Score: 0.8874 | Washington D.C. is the capital of the USA.

Step 4 — Metadata Filtering

python · metadata filtering 
# ── Filter by metadata WHILE doing similarity search ─────────────
# Only retrieve documents where metadata["source"] == "wiki"

results = vector_store.similarity_search(
    query  = "Tell me about the USA",
    k      = 3,
    filter = {"source": "wiki"}   # ← metadata filter
)
print("Results from 'wiki' source only:")
for doc in results:
    print(ff"  {doc.page_content}")
# → Washington D.C. is the capital of the USA.
# → The USA has 50 states.
# (Results from "news" or "tech" sources are excluded)

# ── Filter by "news" source ───────────────────────────────────────
results_news = vector_store.similarity_search(
    query  = "Who is the president?",
    k      = 3,
    filter = {"source": "news"}
)
for doc in results_news:
    print(ff"  {doc.page_content}")
⚠️

Sunny's warning on metadata filtering: "Pass metadata filters very, very carefully. If you're passing the metadata and you're not sure which metadata needs to be passed — don't pass it. Because with respect to a query, if I'm passing a wrong metadata value, it is giving the wrong result. Until you're sure, just skip the filter and let similarity search alone do the work."

Step 5 — Persist to Disk and Reload

python · save and load 
# ── Save FAISS index to local disk ───────────────────────────────
# Without saving: when you restart the notebook, all embeddings are GONE
vector_store.save_local("faiss_index")
# Creates: faiss_index/index.faiss  (the FAISS binary index)
#          faiss_index/index.pkl    (the docstore mappings)
print("✓ FAISS index saved to disk at ./faiss_index/")

# ── Load FAISS index from disk ────────────────────────────────────
loaded_vector_store = FAISS.load_local(
    folder_path = "faiss_index",
    embeddings  = embedding_model,
    allow_dangerous_deserialization = True  # required for pkl loading
)
print("✓ FAISS index loaded from disk")

# ── Verify loaded store works ─────────────────────────────────────
results = loaded_vector_store.similarity_search("Who is president?", k=1)
print(ff"Test query result: {results[0].page_content}")

# KEY POINT from Sunny:
# In-memory → data vanishes when notebook stops
# save_local() → persists to disk → data survives restarts
# This is the difference between in-memory and local persistent storage

09 — Self-Check

Quiz — Test Your Understanding

📝 Class 33 Concept Check

1. What 3 things are stored per document inside a vector database?

▶ Show Answer
Every document in a vector database stores: (1) Actual data — the original text content; (2) Embedded data — the numerical vector representation (embedding) of that text; (3) Metadata — additional information about the document such as source file, page number, author, date, or any other contextual key-value pairs.

2. What is a Vector Index, and why is it needed?

▶ Show Answer
A Vector Index is a data structure that organises embeddings inside a vector database so that vectors can be found quickly without comparing the query against every single stored vector. Without an index, every search requires O(n) comparisons. With an index like IVF or HNSW, the search space is reduced dramatically — like using a book's index instead of reading every page.

3. What are the 3 similarity search metrics? Which is typically best for text/RAG use-cases?

▶ Show Answer
The 3 similarity search metrics are: (1) Cosine Similarity — measures the angle between two vectors, returns -1 to 1, ignores magnitude. Best for text and NLP tasks (including RAG) because it measures semantic direction, not length. (2) Euclidean Distance (L2) — geometric straight-line distance between points, smaller = more similar. Best for image search and spatial data. (3) Dot Product — sum of element-wise products, faster to compute. Best when vectors are already normalised. Cosine similarity is typically recommended for RAG and text-based applications.

4. Explain the difference between Flat Index (ENN) and IVF Index (ANN). When would you choose each?

▶ Show Answer
Flat Index (Exact Nearest Neighbour): stores all vectors with no organisation. Every query compares against every stored vector — 100% accuracy but O(n) time complexity, very slow on large datasets. Choose for small datasets, POC, or MVP where accuracy is critical. IVF Index (Approximate Nearest Neighbour): divides the vector space into clusters using K-Means-like clustering. At query time, only the nearest cluster(s) are searched, skipping most data. Faster, but may occasionally miss the single best result. Choose for large-scale production systems where speed matters and you can accept ~99% accuracy instead of 100%.

5. What is the difference between a "Vector Store" and a "Vector Database" according to Sunny?

▶ Show Answer
A Vector Store is a simple in-memory or local persistent store — it stores and retrieves vectors but doesn't support database-level features like distribution across servers, sharding (splitting data across multiple servers), replication, or complex CRUD operations. FAISS and ChromaDB in local mode are vector stores. A Vector Database is a complete system that supports all the above — distribution, sharding, replication, backup, CRUD — making it suitable for full-scale production enterprise deployments. Pinecone, Qdrant Cloud, and AWS OpenSearch are proper vector databases.

6. What is HNSW and how does it work conceptually?

▶ Show Answer
HNSW stands for Hierarchical Navigable Small World. It's a graph-based ANN (Approximate Nearest Neighbour) index. It builds a multi-layer graph where nodes represent vectors and edges connect similar vectors. The top layer is sparse with long-range connections for fast coarse navigation; bottom layers are dense for fine-grained precision. When a query comes in, it starts at the top layer, finds the approximate nearest neighbour there, then descends to lower layers, refining the search at each level. This hierarchical traversal skips most vectors and returns results much faster than exact search, with very high accuracy. It's the default index in ChromaDB and Qdrant.

7. What does save_local() do in FAISS, and why is it important?

▶ Show Answer
save_local() persists the FAISS index to disk as two files: index.faiss (the FAISS binary index containing all the embedding vectors) and index.pkl (the docstore mapping from FAISS IDs to LangChain Document objects). This is important because by default FAISS is in-memory — when the notebook or application restarts, all stored embeddings are lost. With save_local(), the vector store survives restarts and can be reloaded with load_local(). This is the difference between Category 1 (in-memory) and Category 2 (local persistent) vector storage.

8. Sunny warned about metadata filtering — what was his advice?

▶ Show Answer
Sunny's advice: pass metadata filters very carefully. If you're not sure which metadata value to filter on, don't pass a filter at all — let similarity search alone determine the results. The reason: passing an incorrect or overly restrictive metadata filter can force the system to return results from a wrong source, even if those results are semantically unrelated to the query. This can make the retrieved context worse than no filter. Only use metadata filtering when you are confident about which subset of your knowledge base is relevant to the query.
