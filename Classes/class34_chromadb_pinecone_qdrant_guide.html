03 — FAISS Completion

FAISS — Completing the Practical

HNSW Index on Real Data

In Class 33 Sunny used toy data. In Class 34 he loaded the actual Llama 2 research paper (77 pages) using PyPDF, chunked it with RecursiveCharacterTextSplitter, and stored it in FAISS using the HNSW index. Key insight: he used OpenAI embeddings instead of local HuggingFace because the Gemini model was causing resource exhaustion errors.

python · FAISS with HNSW on real PDF 
import faiss
import os
from dotenv import load_dotenv
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings

load_dotenv()

# ── Embedding model — OpenAI (3072-dim for text-embedding-3-large)
embedding_model = OpenAIEmbeddings(
    model   = "text-embedding-3-large",
    api_key = os.getenv("OPENAI_API_KEY")
)
# Dimension check
dim = len(embedding_model.embed_query("test"))
print(ff"Embedding dimension: {dim}")   # 3072

# ── Load PDF ─────────────────────────────────────────────────────
loader = PyPDFLoader("../data/llama2_research_paper.pdf")
pages  = loader.load()
print(ff"Total pages: {len(pages)}")   # 77 pages

# ── Chunking ─────────────────────────────────────────────────────
splitter = RecursiveCharacterTextSplitter(
    chunk_size    = 2000,
    chunk_overlap = 200,
    separators    = ["\n\n", "\n", ".", ""]
)
chunks = splitter.split_documents(pages)
print(ff"Total chunks: {len(chunks)}")  # 175 chunks

# ── Create HNSW Index (Approximate Nearest Neighbour) ─────────────
# Parameters: dimension, M (connections per node)
# M = 32 means each node connects to 32 others in the graph
# Larger M = better accuracy, more memory
hnsw_index = faiss.IndexHNSWFlat(dim, 32)  # HNSW with M=32, L2 metric

# ── Create LangChain FAISS Vector Store with HNSW ─────────────────
vector_store = FAISS(
    embedding_function   = embedding_model,
    index                = hnsw_index,
    docstore             = FAISS._InMemoryDocstore({}),
    index_to_docstore_id = {}
)

# ── Store all chunks ──────────────────────────────────────────────
vector_store.add_documents(chunks)
print(ff"✓ {len(chunks)} chunks stored in FAISS (HNSW index)")

# ── Similarity search ────────────────────────────────────────────
query   = "What safety measures does Llama 2 have?"
results = vector_store.similarity_search(query, k=3)
for i, doc in enumerate(results):
    print(ff"[{i+1}] Page {doc.metadata.get('page', '?')}: {doc.page_content[:150]}...")

# ── Save to disk ──────────────────────────────────────────────────
vector_store.save_local("faiss_hnsw_index")
04 — Key Distinction

FAISS vs ChromaDB — The Core Difference

What Sunny Explained on the Blackboard

"FAISS is a library provided by Meta. On top of it, we are using the LangChain FAISS wrapper to convert it into a Vector Store. Originally, FAISS can only contain the embedding. But if you are using the LangChain wrapper, in that case, along with the embedding, we can store the metadata, document ID, and different other things as a Vector Store. ChromaDB is not like that — ChromaDB is not a library. It is behaving like a full-fledged Vector DB. No need to manage it from your end. ChromaDB itself will manage everything for you."
FAISS (Meta)

A search library. Stores only raw embedding vectors. You manually manage: index type, dimensions, similarity metric, docstore (ID → text mapping), persistence. LangChain wrapper adds document + metadata management on top.

→ Library + manual management + LangChain wrapper = Vector Store
ChromaDB

A full-fledged Vector Database. Natively manages vectors, documents, metadata, IDs, collections, index, and persistent storage — all out of the box. No need to create an index manually or use a LangChain wrapper to get document management.

→ Complete Vector DB = manages everything itself

Product Quantization (PQ) — What It Is

Sunny introduced PQ as an additional indexing technique he hadn't covered in Class 33:

"Product Quantization — we just compress the vector. If we have a large vector dataset and wanted to store it inside the memory for faster similarity search, we compress that vector. If we have a high-dimensional vector taking a lot of memory, instead of that, what we do — we convert to the quantized variant, and then we store it in memory. Use this when you have 1 million, 5 million, 10 million data points."
📦

PQ in practice: PQ reduces vector size by splitting each vector into sub-vectors and quantising each sub-vector independently. A 3072-dim vector might be compressed to ~1/8th its size with minimal accuracy loss. In FAISS: IndexIVFPQ(quantizer, dim, nlist, m, nbits). Works alongside IVF or HNSW, not as a standalone index. ChromaDB does not support PQ — this is FAISS-only.

05 — Database 1

ChromaDB — The POC Favourite

🟣

ChromaDB

Open-source · Local + Cloud · HNSW default · SQLite3 backend locally

What ChromaDB Is

"ChromaDB is an open-source vector database, designed for storing, managing, and retrieving the embedding. It is generally used inside the RAG pipeline, for normal semantic search, recommendation systems. ChromaDB can store the embedding, original document, metadata, and the unique ID. All this thing can be stored by ChromaDB."

ChromaDB Data Model

Unlike FAISS which stores only raw vectors, ChromaDB natively stores 4 things per record:

ChromaDB — What's Stored per Record
Field
Content
Example
id
Unique document identifier
"abc-123-def-456"
document
Original text content
"Llama 2 is a collection of..."
embedding
Dense vector representation
[0.12, -0.44, 0.78, ...] (3072d)
metadata
Custom key-value pairs
{"source": "llama2.pdf", "page": 3}

Locally, ChromaDB persists data as a SQLite3 database (chroma.sqlite3). This appears in your persist directory automatically when you add documents.

ChromaDB Setup & Code

python · ChromaDB complete 
# !pip install langchain-chroma chromadb

from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
import os
from dotenv import load_dotenv

load_dotenv()
embedding_model = OpenAIEmbeddings(model="text-embedding-3-large")

# ── Load and chunk PDF (same as FAISS) ───────────────────────────
pages  = PyPDFLoader("../data/llama2_research_paper.pdf").load()
chunks = RecursiveCharacterTextSplitter(
    chunk_size=2000, chunk_overlap=200
).split_documents(pages)
print(ff"Chunks ready: {len(chunks)}")   # 175

# ── Create ChromaDB Vector Store ─────────────────────────────────
# Key differences from FAISS:
# - No manual index creation needed
# - No LangChain docstore wrapper needed
# - ChromaDB manages everything internally
vector_store = Chroma(
    collection_name     = "llama2_rag",         # name your collection
    embedding_function  = embedding_model,
    persist_directory   = "./chroma_db",        # auto-persists to disk!
    collection_metadata = {"hnsw:space": "cosine"}  # similarity metric
)

# ── Add documents — ChromaDB handles embedding + storage ─────────
vector_store.add_documents(chunks)
print("✓ Documents stored in ChromaDB (./chroma_db/chroma.sqlite3)")

# ── Similarity Search ─────────────────────────────────────────────
results = vector_store.similarity_search(
    "What are the safety features of Llama 2?",
    k = 5
)
for doc in results:
    print(ff"Page {doc.metadata.get('page')}: {doc.page_content[:100]}...")

Creating a Retriever from ChromaDB

python · ChromaDB retriever 
# ── Convert to LangChain Retriever ───────────────────────────────
# search_type options: "similarity", "mmr", "similarity_score_threshold"
retriever = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 5}
)

# ── Invoke the retriever ──────────────────────────────────────────
query   = "What datasets were used to train Llama 2?"
results = retriever.invoke(query)

print(ff"Retrieved {len(results)} documents:")
for i, doc in enumerate(results):
    print(ff"\n[{i+1}] Page {doc.metadata.get('page', '?')}:")
    print(ff"     {doc.page_content[:200]}...")

# ── Retriever search types explained ─────────────────────────────
# "similarity"               → standard cosine/L2 similarity (default)
# "mmr"                      → Maximum Marginal Relevance
#                              balances relevance AND diversity
#                              avoids returning near-duplicate chunks
# "similarity_score_threshold" → only return docs above a score threshold
#                              e.g. search_kwargs={"score_threshold": 0.8}
# NOTE: MMR and score_threshold will be covered in the Retrieval chapter

Pinecone — Fully Managed SaaS

🌲

Pinecone

Managed SaaS · Hosted on AWS · Namespace-based · Paid (free tier available)

What Pinecone Is

"Pinecone is a managed vector database. It is a complete managed system — Pinecone is hosting the server over the AWS. If you are using it in a production system, in that case, you will get some billing. You can do CRUD operations — you can delete that document, delete the namespace, delete that index. Everything is possible. It is a complete managed system."
💳

Cost note: Pinecone has a free tier (1 index, 2GB storage) but is paid for production use. For POC/development, use the free tier. For large-scale production, budget accordingly. Sunny explicitly said: "Today I will show you how to configure Pinecone — if you are using it in a production system, you will get billing."

Pinecone Setup & Code

python · Pinecone setup + store + retrieve 
# !pip install langchain-pinecone pinecone-client

from langchain_pinecone import PineconeVectorStore
from pinecone import Pinecone, ServerlessSpec
from langchain_openai import OpenAIEmbeddings
from langchain.schema import Document
import os
from dotenv import load_dotenv

load_dotenv()

# ── Step 1: Initialize Pinecone client ───────────────────────────
# Get API key from: https://app.pinecone.io/ → API Keys
pc = Pinecone(api_key=os.getenv("PINECONE_API_KEY"))

# ── Step 2: Create or connect to an Index ────────────────────────
# An Index in Pinecone = a collection of vectors
index_name = "langchain-llama-index"
dimension  = 3072   # must match your embedding model output

if index_name not in [idx.name for idx in pc.list_indexes()]:
    pc.create_index(
        name      = index_name,
        dimension = dimension,
        metric    = "cosine",         # cosine / euclidean / dotproduct
        spec      = ServerlessSpec(   # serverless (no server to manage)
            cloud  = "aws",
            region = "us-east-1"
        )
    )
    print(ff"✓ Created Pinecone index: {index_name}")

# ── Step 3: Create LangChain Vector Store ────────────────────────
embedding_model = OpenAIEmbeddings(model="text-embedding-3-large")

vector_store = PineconeVectorStore(
    index     = pc.Index(index_name),
    embedding = embedding_model,
    namespace = "demo_documents"    # namespace = logical separation within index
)

# ── Step 4: Add documents ────────────────────────────────────────
# Same as FAISS and Chroma — just use add_documents()
docs = [
    Document("Llama 2 is a family of LLMs trained by Meta.",
             metadata={"source": "llama2.pdf", "page": 1}),
    Document("RLHF was used to align Llama 2 Chat models.",
             metadata={"source": "llama2.pdf", "page": 4}),
]
vector_store.add_documents(docs)
print("✓ Documents stored in Pinecone")
# Check Pinecone UI: app.pinecone.io → your index → namespace "demo_documents"
# You can see: embedding vector, metadata, text, ID for each stored record

# ── Step 5: Similarity search ────────────────────────────────────
results = vector_store.similarity_search(
    "How was Llama 2 trained?",
    k = 2
)
for doc in results:
    print(doc.page_content)

# ── Step 6: Use as retriever ─────────────────────────────────────
retriever = vector_store.as_retriever(search_kwargs={"k": 3})
results   = retriever.invoke("What is RLHF?")

# ── CRUD Operations ──────────────────────────────────────────────
# Delete specific documents by ID
# vector_store.delete(ids=["doc-id-1", "doc-id-2"])

# Delete an entire namespace
# pc.Index(index_name).delete(delete_all=True, namespace="demo_documents")

# Delete the entire index
# pc.delete_index(index_name)

07 — Database 3

Qdrant — Rust-Powered Open-Source

🔷

Qdrant

Open-source · Built in Rust · Cloud + Local (Docker) · HNSW default

What Qdrant Is

"Qdrant is a managed vector database. We can use it for a very huge amount of data, and it will work very fast, because it has been created on top of the Rust language. Rust is a programming language — everything in Qdrant is built on top of that SDK. It is an open-source vector database. It helps us quickly find semantic, similar information. It is working very fast, and that's why most of the people are using this Qdrant inside their solution."

Qdrant Data Hierarchy

Qdrant uses different terminology from other databases. Sunny explained this clearly:

Cluster

Cluster

The top-level grouping. You create one cluster (e.g. "GenAI Bootcamp"). Free tier: 1 cluster, 1GB storage, cloud-hosted.

Collection

Collection (= Index in FAISS / Pinecone)

Inside a cluster, you create collections. Each collection stores vectors of a fixed dimension. Similar to a "table" in a database. You configure: vector size, distance metric (Cosine/Dot/Euclidean).

Point

Point (= Document record)

Inside a collection, data is stored as "points." Each point has a unique ID, a vector, and a payload.

Payload

Payload (= Metadata + original text)

The data stored alongside each vector — page content, source, page number, any custom metadata fields. Queryable as metadata filters.

"Where the data is going to be stored inside the Qdrant? The data is going to be stored inside the collection. Inside the collection, it's going to be create multiple points. Inside the point only, it's going to be keep what? The payload. First, we'll have to create a collection. Inside that, we'll have to create a point. And inside the point only, the data will be available."

Qdrant Setup & Code

python · Qdrant cloud setup 
# !pip install langchain-qdrant qdrant-client

from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams
from langchain_qdrant import QdrantVectorStore
from langchain_openai import OpenAIEmbeddings
from langchain.schema import Document
import os
from dotenv import load_dotenv

load_dotenv()

# ── Qdrant Cloud credentials ──────────────────────────────────────
# 1. Go to: https://cloud.qdrant.io/
# 2. Sign in with Google or GitHub
# 3. Create a free cluster (e.g. "GenAI Bootcamp")
# 4. Copy: API Key + Cluster Endpoint URL
# 5. Add to .env: QDRANT_API_KEY and QDRANT_CLUSTER_ENDPOINT

QDRANT_API_KEY  = os.getenv("QDRANT_API_KEY")
QDRANT_URL      = os.getenv("QDRANT_CLUSTER_ENDPOINT")  # e.g. "https://xxx.qdrant.io"
COLLECTION_NAME = "llama2_collection"
DIMENSION       = 3072

# ── Step 1: Create Qdrant Cloud client ───────────────────────────
client = QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY)

# ── Step 2: Create Collection (if not exists) ─────────────────────
existing = [c.name for c in client.get_collections().collections]
if COLLECTION_NAME not in existing:
    client.create_collection(
        collection_name = COLLECTION_NAME,
        vectors_config  = VectorParams(
            size     = DIMENSION,
            distance = Distance.COSINE   # COSINE / DOT / EUCLID
        )
    )
    print(ff"✓ Collection '{COLLECTION_NAME}' created")

# ── Step 3: Embedding model ───────────────────────────────────────
embedding_model = OpenAIEmbeddings(model="text-embedding-3-large")

# ── Step 4: Create LangChain Vector Store ────────────────────────
vector_store = QdrantVectorStore(
    client          = client,
    collection_name = COLLECTION_NAME,
    embedding       = embedding_model,
)

# ── Step 5: Add documents ────────────────────────────────────────
# Using the real chunked data from the PDF (same as ChromaDB demo)
# chunks = split_documents(pages) → 175 chunks
# Each chunk gets a unique ID generated automatically
import uuid
chunk_ids = [str(uuid.uuid4()) for _ in chunks]
vector_store.add_documents(chunks, ids=chunk_ids)
print(ff"✓ Inserted {len(chunks)} chunks into Qdrant")
# Sunny's output: "Inserted 174 chunk"
# Check Qdrant dashboard → GenAI Bootcamp cluster → manage collection

# ── Step 6: Similarity search ────────────────────────────────────
results = vector_store.similarity_search(
    "What safety training was done for Llama 2?",
    k = 3
)
for doc in results:
    print(ff"Page {doc.metadata.get('page', '?')}: {doc.page_content[:150]}...")

# ── Step 7: Use as retriever ─────────────────────────────────────
retriever = vector_store.as_retriever(search_kwargs={"k": 5})
results   = retriever.invoke("Explain the RLHF process")

# ── Local Qdrant (Docker alternative) ────────────────────────────
# If you want to run Qdrant locally (not cloud):
# docker run -p 6333:6333 qdrant/qdrant
# Then use: QdrantClient(host="localhost", port=6333)
# NOTE: Windows users → Docker is recommended, not native install
🐳

09 — Practical Guidance

When to Use Which Database

Use FAISS when…
  • → Learning vector DB fundamentals
  • → Need full manual control over index type
  • → Exploring IVF or PQ quantisation
  • → Academic or research use-cases
  • → No cloud dependency desired
Use ChromaDB when…
  • → Building a POC or MVP quickly
  • → Local development (no API keys)
  • → Need rich metadata filtering locally
  • → Small to medium dataset (dev/staging)
  • → Plan to migrate later to Pinecone/Qdrant
Use Pinecone when…
  • → Need fully managed, zero-ops solution
  • → Building production systems on AWS
  • → Need namespace-based data segregation
  • → Team lacks DevOps for self-hosting
  • → Budget available for managed SaaS
Use Qdrant when…
  • → Need high performance on large data
  • → Want open-source + cloud flexibility
  • → Need rich payload filtering
  • → Self-hosting preferred (Docker/Kubernetes)
  • → Cost-efficiency at scale important

10 — Self-Check

Quiz — Test Your Understanding

📝 Class 34 Concept Check

1. What is the architectural difference between FAISS and ChromaDB? How does LangChain's role differ?

▶ Show Answer
FAISS is a vector search library (Meta) that natively stores only raw embedding vectors. LangChain's FAISS wrapper adds document and metadata management on top, turning it into a Vector Store — it's library + wrapper = vector store. ChromaDB is a full-fledged vector database that natively manages everything itself: vectors, original documents, metadata, unique IDs, collections, index, and persistence. No LangChain wrapper is needed to make ChromaDB a complete Vector Store — it already is one.

2. What is Product Quantization (PQ) and when should you use it?

▶ Show Answer
Product Quantization is a vector compression technique. It splits high-dimensional vectors into sub-vectors and quantises (compresses) each sub-vector independently, reducing memory usage significantly. Use PQ when you have very large datasets (1 million+ documents) where storing full-precision vectors would be too expensive in memory. PQ trades a small amount of accuracy for a large reduction in memory footprint and faster similarity search. It works alongside flat, IVF, or HNSW indexes in FAISS. ChromaDB does not support PQ.

3. What 4 things does ChromaDB store natively per record, and how does this differ from raw FAISS?

▶ Show Answer
ChromaDB stores: (1) id — unique document identifier, (2) document — the original text content, (3) embedding — the dense vector representation, (4) metadata — custom key-value pairs (source, page, date, etc.). Raw FAISS only stores the embedding vector — it has no concept of document text or metadata. To store these alongside embeddings in FAISS, you need LangChain's FAISS wrapper which adds a docstore (id → Document mapping) separately from the FAISS index.

4. What is a Pinecone Namespace, and give a practical example of when you'd use multiple namespaces?

▶ Show Answer
A Pinecone Namespace is a logical partition within a single Pinecone Index that separates data into groups while sharing the same infrastructure. Example: A company builds a single index "company-knowledge-base" with namespaces: "hr-policies" (all HR documents), "finance-docs" (financial reports), "tech-manuals" (technical documentation). When a query comes from the HR chatbot, you filter to the "hr-policies" namespace only — so retrieval is faster and doesn't return irrelevant results from finance or tech documents.

5. Explain the Qdrant data hierarchy: Cluster → Collection → Point → Payload.

▶ Show Answer
Cluster: Top-level grouping (e.g., "GenAI Bootcamp"). One cluster can host multiple collections. Collection: Like a "table" — stores vectors of a fixed dimension with a configured distance metric. Equivalent to an "Index" in Pinecone or FAISS. Point: A single record inside a collection. Has a unique ID and an embedding vector. Equivalent to a "document" in FAISS/ChromaDB. Payload: Data stored alongside each point — the original text content + any metadata fields (source, page, etc.). Equivalent to "metadata" in other databases.

6. Why is Qdrant fast, and how should Windows users run it locally?

▶ Show Answer
Qdrant is fast because its entire SDK and server are built in Rust — a systems programming language known for near-C performance with memory safety. This makes Qdrant significantly faster than Python-based alternatives for large-scale vector operations. Windows users should NOT try to install Qdrant natively — it gives many compatibility issues. The recommended approach is Docker: run docker run -p 6333:6333 qdrant/qdrant and connect with QdrantClient(host="localhost", port=6333). Alternatively, use Qdrant Cloud (free tier) which avoids local installation entirely.

7. What is the MMR search type in ChromaDB retriever, and why would you use it?

▶ Show Answer
MMR stands for Maximum Marginal Relevance. It's a retrieval strategy that balances two goals: relevance (documents should match the query) AND diversity (documents shouldn't be near-duplicates of each other). Without MMR, if your top-5 chunks all come from the same paragraph of a document, they're highly redundant — the LLM gets repetitive context. MMR penalises documents that are too similar to already-selected documents, so the retrieved chunks cover a broader range of relevant information. Configure with: as_retriever(search_type="mmr", search_kwargs={"k": 5, "fetch_k": 20}). Sunny mentioned this will be covered in depth in the upcoming Retrieval Techniques class.
