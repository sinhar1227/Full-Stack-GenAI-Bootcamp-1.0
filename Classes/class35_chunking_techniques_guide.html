Key position: Chunking always happens after parsing (extracting text from the source) and before embedding. Chunking is not embedding — it's the step that prepares text pieces to be embedded and stored individually. The order is: parse → chunk → embed → store → retrieve → generate.

03 — Definition

What Is Chunking?

Sunny's Definition (Blackboard)

"Chunking is a process of dividing large data into smaller, meaningful units called chunks."

In the RAG pipeline: each chunk is embedded separately, stored separately, retrieved separately, and sent to the LLM when it is relevant.

04 — Clarification

Parsing vs Chunking

Parsing

Extraction of data from a source — pulling text, tables, or images out of a PDF, DOCX, HTML, etc. The raw content is extracted first.

Chunking

Division of extracted content into smaller parts. Happens after parsing. The name says it all: you are creating "chunks" — small, small parts.

"Parsing means extraction of the data. Chunking means to divide it into the smallest, small part. The name is self-explanatory — chunks means small, small parts."
05 — Rationale

Why Do We Need Chunking?

1
LLM context window limitation. LLMs can only accept a fixed number of tokens at once. They cannot process millions of tokens of a full document. Passing too much data even within the limit causes hallucination.
2
Better retrieval accuracy. Storing large blocks in the vector DB reduces retrieval precision. Smaller, focused chunks mean the similarity search finds the exact relevant passage, not a large block that happens to contain it somewhere.
3
Lower token cost. Passing only the relevant chunk (not the whole document) to the LLM dramatically reduces the number of input tokens — and therefore the API cost.
4
Faster processing. A small, targeted chunk is processed by the LLM much faster than a large document. Latency is reduced.
5
Send only relevant information. In RAG, you retrieve only the chunk that matches the question. The LLM receives focused, on-topic context — not an entire 200-page document with mostly irrelevant content.
06 — Design Choice

Is Chunking Always Required?

"Is chunking always required? So the answer is no. Chunking is a design choice. It's not a compulsory step. Chunking is usually required whenever the document is large. But chunking may not be required in a couple of cases. Chunking is a very subjective thing. It completely depends on you — the AI engineer's decision — whether you have to do the chunking or not."

✅ DO chunk when…

  • → Document is large (multi-page)
  • → Content exceeds model context window
  • → Different sections discuss different topics
  • → Only a small section answers the query
  • → Source is a long PDF, manual, or policy doc
  • → Semantic retrieval accuracy is needed

✗ Skip chunking when…

  • → Input is already short (1–2 pages)
  • → Full document fits in model context
  • → Retrieving metadata or structured info
  • → Full document needed for the task
  • → Every page equally relevant to every query
07 — Key Parameters

Chunk Size & Chunk Overlap

Overlap — Sunny's Blackboard Example

Sunny wrote this example on the blackboard to explain overlap concretely:

Overlap Example — chunk_size=10 words, chunk_overlap=3 words
Original text: "Artificial intelligence helps machines learn patterns and make useful decisions."
Chunk 1 Artificial intelligence helps machines learn patterns and make useful decisions
Chunk 2 make useful decisions [next sentence begins…]
The highlighted 3 words "make useful decisions" appear in both Chunk 1 and Chunk 2. This is the overlap. It preserves the context so Chunk 2 isn't semantically orphaned from what came before.
"Why do we do this overlapping? To sustain the context of the data. Chunk 2 can have some meaning from Chunk 1. That's why we are doing this overlapping. Overlap helps to preserve the meaning when an important sentence is divided between two chunks."

Both Are Hyperparameters

⚙️

chunk_size and chunk_overlap are both hyperparameters. "Hyperparameter means we cannot decide the value of it. It is a subjective value — an experimental value." You choose these based on your data. There is no universally correct value. Always 300, always 500 — none of these are universal rules. First analyze the data, then define the chunk size, then evaluate whether retrieval is working.

Size/Overlap Tradeoffs

Tradeoff Rules
Smaller chunk size → more chunks created, higher precision, risk: loses context
Larger chunk size → fewer chunks, more context, risk: lower retrieval accuracy
Large overlap → preserves more cross-chunk context, risk: duplicated stored content, higher storage & token cost
Optimal: analyze your data first → set size based on meaningful unit → validate retrieval results
08 — The Landscape

Chunking Strategies — Full Map

Fixed Size Chunking
Simplest

Every chunk is the same size regardless of content boundaries. Fast, simple, but may cut sentences mid-thought. No LangChain awareness of document structure.

Recursive Character Text Splitting
Most Used

Tries multiple separators in priority order (\n\n → \n → . → space → char) until chunks meet the target size. Best general-purpose baseline for text documents.

Token Text Splitting
LLM-Aligned

Splits based on token count (using a tokenizer like cl100k_base) instead of character count. Aligns precisely with how LLMs measure input length.

Document Structure-Based
Structure-Aware

Splits on structural markers: Markdown headers (#, ##, ###), HTML tags, JSON keys, or code functions. Preserves document hierarchy inside chunks.

Content-Aware Chunking
Custom Logic

Custom Python code that understands the natural structure (paragraphs, sections, tables, lists) and preserves boundaries. Manual but precise — tailored to your specific data.

Semantic Chunking
Meaning-Based

Embeds sentences, measures cosine distance between adjacent pairs, and places chunk boundaries where semantic distance exceeds a threshold (topic change detected).

🎯

Sunny's real-world order: In production, first start with the simplest baseline (RecursiveCharacterTextSplitter). If retrieval quality is poor, move to document structure-based chunking or content-aware logic tailored to your data. Semantic chunking is advanced — only after simpler methods fail. Never use semantic chunking first without a baseline comparison.

10 — Practical 1

RecursiveCharacterTextSplitter

The most commonly used splitter. Its key feature: it tries separators in a priority chain, going finer-grained until it achieves the target chunk size.

Separator Priority Chain

PrioritySeparatorMeaningWhen Used
1st (highest) \n\n Double newline Split at paragraph boundaries first. If paragraph ≤ chunk_size → stop here.
2nd \n Single newline If paragraph still too large → split at line boundaries.
3rd . (period) Sentence end If line still too large → split at sentence boundaries.
4th " " (space) Word boundary If sentence still too large → split between words.
5th (fallback) "" (empty) Character level Final fallback → split character by character. No natural boundary possible.
"Recursive character text splitter splits text recursively by using multiple separators in the priority order. First it tries double-slash-n. If the paragraph is larger than 300 characters, it tries with single slash-n — split at line boundary. If the line is still too large, it uses dot — split at sentence boundary. Recursively, it is trying, until it is able to get the desired length."

Code & Output

python · RecursiveCharacterTextSplitter 
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain_community.document_loaders import PyPDFLoader

# Load document
loader = PyPDFLoader("data/document.pdf")
pages  = loader.load()

# Define splitter
splitter = RecursiveCharacterTextSplitter(
    chunk_size    = 300,   # max ~300 characters per chunk
    chunk_overlap = 50,    # ~50 chars from prior chunk repeat
    length_function = len, # measure size in characters
    add_start_index = True # store start position in metadata
)

# Split documents
chunks = splitter.split_documents(pages)
print(ff"Total chunks: {len(chunks)}")          # 11,107 for large PDF
print(ff"Chunk 1 length: {len(chunks[0].page_content)}")  # 257 chars
print(ff"Chunk 2 length: {len(chunks[1].page_content)}")  # 242 chars

# Inspect a chunk
print(chunks[0].page_content)
print(chunks[0].metadata)   # {source, page, start_index}

# ── Key notes ─────────────────────────────────────────────────────
# chunk_size = 300 chars → each chunk is at most ~300 characters
# chunk_overlap = 50 → 50 chars from previous chunk repeat in next
# add_start_index = True → metadata stores where the chunk starts
# length_function = len → size measured in character count
# To measure in tokens instead: length_function = tiktoken_len (custom)
11 — Practical 2

TokenTextSplitter

Splits text based on token count rather than character count. Uses a tokenizer (e.g. cl100k_base from OpenAI's tiktoken) to convert text to tokens, then splits at token boundaries. Critical distinction: a word is not always one token.

Code & Token Example

python · TokenTextSplitter 
from langchain.text_splitter import TokenTextSplitter

# cl100k_base = OpenAI's tokenizer (used by GPT-4, text-embedding-3-small)
# encoding_name controls which tokenizer converts text → tokens
splitter = TokenTextSplitter(
    encoding_name = "cl100k_base",
    chunk_size    = 100,   # 100 TOKENS per chunk (not 100 chars)
    chunk_overlap = 10    # 10 tokens overlap
)

chunks = splitter.split_documents(pages)
print(ff"Total chunks: {len(chunks)}")   # 1,112 chunks (different from char-based)
print(ff"Chunk size: {len(chunks[0].page_content)} chars")  # ~260 chars = 100 tokens

# ── Token example from Sunny's blackboard ────────────────────────
# Text: "AI helps machines learn from data and make better decisions for users."
#
# After tokenization (each word may be 1 or more tokens):
# tokens = [AI, helps, machines, learn, from, data, and, make, better, ...]

12 — Practical 3

Content-Aware Chunking (Custom Logic)

Instead of blindly splitting at a fixed character count, content-aware chunking understands the natural structure of the document (paragraphs, sections, lists) and splits at meaningful boundaries.

"Content-aware chunking splits the text by understanding its natural structure — instead of just cutting it blindly after a fixed number of characters or tokens. It tries to preserve the boundaries such as paragraphs, sentences, headings, lists, sections, or tables. It's a manual one — you write the custom logic for it."

Content-Aware Chunking Code

python · content-aware chunking 
## Content-Aware Chunking — splits at paragraph boundaries
## Custom logic: aware of document structure, not just character count

def content_aware_chunking(text: str, max_chars: int = 500) -> list[str]:
    """
    Splits text by preserving paragraph structure.
    Each paragraph that fits within max_chars becomes one chunk.
    Paragraphs larger than max_chars are further split by sentence.
    """
    if max_chars <= 0:
        raise ValueError("max_chars must be positive")

    chunks      = []
    current     = ""

    # Split on paragraph boundaries (double newline)
    paragraphs = text.split("\n\n")

    for paragraph in paragraphs:
        paragraph = paragraph.strip()
        if not paragraph:
            continue

        # If adding this paragraph stays within limit, accumulate
        if len(current) + len(paragraph) + 2 <= max_chars:
            current = (current + "\n\n" + paragraph).strip()
        else:
            # Save current chunk, start new one
            if current:
                chunks.append(current)
            # If single paragraph is too large, split by sentence
            if len(paragraph) > max_chars:
                sentences = paragraph.split(". ")
                temp = ""
                for sentence in sentences:
                    if len(temp) + len(sentence) <= max_chars:
                        temp += sentence + ". "
                    else:
                        if temp: chunks.append(temp.strip())
                        temp = sentence + ". "
                if temp: chunks.append(temp.strip())
                current = ""
            else:
                current = paragraph

    if current:
        chunks.append(current)

    return chunks

# Usage
text    = """Artificial intelligence enables machines to perform intelligent tasks.

Machine learning is part of AI. It allows systems to learn from data.

Employee leave policy: All employees are entitled to 20 days..."""

chunks = content_aware_chunking(text, max_chars=200)
for i, c in enumerate(chunks):
    print(ff"Chunk {i+1}: {c[:80]}...")
# Output: 3 chunks — one per paragraph (AI intro, ML, Leave policy)
# RecursiveCharacterTextSplitter might split mid-paragraph here
# Content-aware preserves full paragraph as chunk boundary

14 — Advanced

Semantic Chunking

The most sophisticated approach. Instead of splitting on characters, tokens, or structure markers, semantic chunking detects where the topic actually changes by comparing the semantic similarity of adjacent sentences using embeddings.

Semantic Chunking Pipeline

Semantic Chunking — 5-Step Pipeline (Sunny's Blackboard)
1

Create Sentence Window

Split the document into individual sentences. For each sentence, build a "window" of buffer_size neighbouring sentences to create context.

2

Create Local Embedding

Embed each windowed sentence using a local SentenceTransformer model (all-MiniLM-L6-v2 or similar). No paid API required. Fallback: TF-IDF vectors.

3

Compute Similarity & Distance

Compute cosine similarity between adjacent sentence embeddings. Convert to distance (1 − similarity). High distance = topic likely changed.

4

Detect Topic-Change Boundaries

Find all pairs where distance exceeds the breakpoint percentile threshold. These are the chunk boundaries — places where the topic changes.

5

Finalise Chunks

Group sentences between boundaries into final chunks. Each chunk discusses a coherent single topic. Return chunks with metadata.

Breakpoint Percentile — What It Controls

PercentileThreshold LevelEffectUse When
50Low (aggressive)Many breakpoints → smaller, more chunksDocument covers many distinct sub-topics
75Balanced (default)Moderate breakpoints → medium-sized chunksGeneral use — good starting point
90High (conservative)Few breakpoints → larger, fewer chunksDocument stays on one topic throughout
"Low semantic distance means sentences discuss a similar kind of topic — keep them in the same chunk. High semantic distance means the topic has probably changed — start a new chunk. The breakpoint percentile decides how large a semantic distance must be before starting a new chunk."

Semantic Chunking — Full Custom Code

python · semantic_chunking (custom, no paid API) 
## Semantic Chunking — custom implementation using SentenceTransformer
## pip install sentence-transformers scikit-learn numpy

import numpy as np
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity
import re

# ── Step 1: Create sentence window ────────────────────────────────
def create_sentence_window(text: str, buffer_size: int = 1) -> list[dict]:
    """
    Split text into sentences and create a context window around each.
    buffer_size=1 → include 1 sentence before and 1 after each sentence.
    """
    sentences = re.split(r'(?<=[.!?])\s+', text.strip())
    sentences = [s.strip() for s in sentences if s.strip()]
    windows   = []
    for i, sentence in enumerate(sentences):
        start  = max(0, i - buffer_size)
        end    = min(len(sentences), i + buffer_size + 1)
        window = " ".join(sentences[start:end])
        windows.append({"sentence": sentence, "window": window, "index": i})
    return windows, sentences

# ── Step 2: Create local embedding ───────────────────────────────
def create_local_embedding(
    windows: list, model_name: str = "all-MiniLM-L6-v2"
) -> tuple[np.ndarray, str]:
    model      = SentenceTransformer(model_name)
    window_texts = [w["window"] for w in windows]
    embeddings = model.encode(window_texts, convert_to_numpy=True)
    return embeddings, model_name

# ── Step 3+4+5: Detect boundaries and create chunks ───────────────
def semantic_chunking(
    text:                  str,
    breakpoint_percentile: float = 75.0,
    buffer_size:           int   = 1,
    model_name:            str   = "all-MiniLM-L6-v2"
) -> list[str]:
    """
    Full semantic chunking pipeline:
    sentences → windows → embed → cosine distance → breakpoints → chunks
    """
    windows, sentences = create_sentence_window(text, buffer_size)
    embeddings, _      = create_local_embedding(windows, model_name)

    # Compute cosine distance between adjacent sentence embeddings
    similarities = cosine_similarity(embeddings[:-1], embeddings[1:]).diagonal()
    distances    = 1 - similarities

    # Threshold: breakpoint_percentile of all distances
    threshold = np.percentile(distances, breakpoint_percentile)
    print(ff"Embedding model: {model_name}")
    print(ff"Distance threshold: {threshold:.3f}")

    # Mark breakpoints (True = new chunk starts after this sentence)
    breakpoints = [d > threshold for d in distances]

    # Build final chunks
    chunks, current = [], []
    for i, sentence in enumerate(sentences):
        current.append(sentence)
        if i < len(breakpoints) and breakpoints[i]:
            chunks.append(" ".join(current))
            current = []
    if current:
        chunks.append(" ".join(current))

    print(ff"Total semantic chunks: {len(chunks)}")
    return chunks

# ── Usage ─────────────────────────────────────────────────────────
with open("data/document.txt") as f:
    text = f.read()

chunks = semantic_chunking(
    text                  = text,
    breakpoint_percentile = 75,   # balanced — default
    buffer_size           = 1    # 1 sentence before + after for context
)
# Sunny's demo result: 709 semantic chunks from a large complex PDF
# Each chunk discusses one coherent topic
# Distance threshold was ~0.265 for that dataset
15 — Advanced Use Cases

Chunking Beyond Text

"Chunking is not limited to text, actually. We can also divide images, tables, code, audio, video, maps — any kind of data — into smaller, meaningful chunks. The chunking boundary depends on the type of the data. But always, guys, until it is not required, don't do image or table chunking. If your single image is working fine, you're good to go."

Image Chunking

When image chunking is needed:

  • → Image is very large (full-page scanned document)
  • → Small text would disappear or be unreadable after resizing the whole image
  • → Tiny objects need to be detected in specific regions
  • → The image contains many independent regions (floor plan, satellite image, medical scan, map)
  • → Region-level retrieval is needed (retrieve the "header section" or "table area" specifically)

How to divide images:

  • → Fixed tile (divide into equal grid tiles)
  • → Overlapping tile (adjacent tiles share region for context)
  • → Detected object (use YOLO or similar to detect regions)
  • → Document layout region (header, paragraph, table, chart, footer — for scanned docs)
  • → Semantic region (group visually similar areas)

Table Chunking

Real-world example from Sunny: "In one project, the table was spanning 5 pages of a PDF with more than 100 rows. That kind of table could be divided into multiple chunks."

How to divide tables:

  • → By rows (every N rows becomes a chunk — always keep the header row in each chunk)
  • → Overlapping rows (overlap preserves context across row boundaries)
  • → By column groupings (related columns go together)
  • → By category/entity (group by product type, date range, geography — if the table has a natural grouping)
⚠️

Critical mistake: Never split a table without preserving the header row. If the header row doesn't appear in each chunk, the LLM has no idea what the columns mean.

16 — Watch Out

Common Chunking Mistakes

✗
Chunk size without evaluating retrieval. Setting chunk_size=300 then never checking whether the retrieved chunks actually answer queries correctly. Always test retrieval quality after setting chunk size.
✗
Very small chunks. Lose context — a 30-character chunk is meaningless without surrounding sentences.
✗
Very large chunks. Contain irrelevant information — retrieval precision drops because every "match" includes a lot of noise.
✗
Excessive overlap. Creates duplicated stored content, inflates storage, increases token cost with repeated context.
✗
Splitting tables without preserving the header row. The LLM can't understand column values without the header.
✗
Splitting code in the middle of a function or class. The code loses its meaning and is unusable out of context.
✗
Removing useful metadata. Always keep source, page number, section, and other metadata alongside the chunk. It's needed for attribution and filtering during retrieval.
✗
Jumping to semantic chunking without baseline comparison. First test RecursiveCharacterTextSplitter. Only move to semantic if it fails. Semantic chunking is expensive and slower.
✗
Assuming one strategy works for all data types. A strategy that works on PDF reports may not work on JSON logs, code repositories, or scanned invoices. Always validate per data type.
17 — Career Prep

Interview Tips

"Whenever you are going in an interview, don't say directly: 'I have done the chunking using the recursive character text splitter.' If you are saying like that, the interviewer will not like that answer and might reject you. You need to say: 'First I analyzed the data. I found some meaningful pattern inside my data. Based on that, I wrote some rules inside my code, and then only I performed the chunking.' Otherwise you can say: 'I did semantic chunking. I understood the document structure, and based on that only I performed chunking of the data.'"
What a Strong Interview Answer Looks Like
❌ Weak: "We used RecursiveCharacterTextSplitter with chunk_size=500."
✅ Strong:
"First, I analyzed the data — it was a 30-page pharma report structured by sections. Each section discussed a distinct topic. So I decided to chunk by section rather than fixed character count. I wrote content-aware logic that splits on section boundaries. I then validated retrieval quality: for 20 sample queries, I checked whether the retrieved chunks contained the correct information. When some queries failed, I reduced chunk overlap and re-evaluated until retrieval accuracy reached our target."
💼

The key message: Chunking is not a recipe — it's an engineering decision. Interviewers want to see that you: (1) analyzed the data first, (2) chose a strategy based on the data structure, (3) experimented and evaluated retrieval quality, and (4) iterated until it worked. "There is no best method, guys — it is all about the experiments."

18 — Live Q&A

Q&A Highlights

Q — Student
Can we do chunking of video and audio data as well?
A — Sunny
Yes — if you are processing that type of data, you can do chunking of it. For video: split by scene, time window, or detected event. For audio: split by silence gaps, speaker changes, or fixed time windows (e.g. 30-second segments). Same principle — find the natural boundary in your data, then split there. But only do this if a single clip isn't working. If you can embed a 30-second audio segment as a single unit and retrieval works, don't over-complicate it.

A — Sunny
No. "HyDE is not a chunking technique — it is a retrieval technique." HyDE (Hypothetical Document Embeddings) works after chunking, during retrieval — it generates a hypothetical answer, embeds it, and uses that embedding to search the vector DB. Chunking happens at data ingestion time. HyDE happens at query time. Two completely different pipeline stages.
Q — Bala
If only chunk 3 is retrieved, the LLM doesn't have the context from chunks 1 and 2. How will it give a complete answer?
A — Sunny
The LLM only receives the retrieved chunk because that chunk is what's relevant to the query. If the user query matched chunk 3, it means chunk 3 contains the answer. The whole point of RAG is precision — don't send everything, send only the relevant part. If you need more context (e.g. surrounding sections), that's where retrieval strategies like Parent Document Retriever or Sentence Window Retriever help — they retrieve a small chunk for matching but return a larger parent context to the LLM. This was covered in Class 36.

📝 Class 35 Concept Check

1. What is the difference between parsing and chunking? When does each happen in the RAG pipeline?

▶ Show Answer
Parsing = extraction of content from a source (pulling text, tables, images out of a PDF, DOCX, etc.). Chunking = division of extracted content into smaller, meaningful units. Parsing comes first — you can't chunk what you haven't extracted. In the RAG pipeline: Data → Parsing → Chunking → Embedding → Vector DB → Retrieval → LLM. Chunking always sits between parsing and embedding. "Parsing means extraction of the data. Chunking means to divide it into the smallest, small part."

2. Why are chunk_size and chunk_overlap called "hyperparameters"? What's the correct approach to choosing their values?

▶ Show Answer
They are called hyperparameters because their optimal values cannot be determined theoretically — they must be discovered experimentally for each dataset. There is no universally correct value (not always 300, not always 500). The correct approach: (1) Analyze your data — understand its structure, how long meaningful sections are, whether there are natural boundaries. (2) Set initial values based on that analysis. (3) Evaluate retrieval quality — did the retrieved chunks contain the correct answers to test queries? (4) Adjust and iterate until retrieval meets your quality bar. Chunk size controls maximum content per chunk. Overlap controls how many characters repeat between adjacent chunks to preserve cross-boundary context.

3. Explain the RecursiveCharacterTextSplitter separator priority chain and why it's called "recursive."

▶ Show Answer
The RCTS tries separators in this priority order: (1) \n\n (paragraph) → (2) \n (line) → (3) . (sentence) → (4) space (word) → (5) "" (character). It first tries to split at double newlines (paragraph boundaries). If the resulting piece is still larger than chunk_size, it recursively tries the next separator — moving finer and finer until the chunk is small enough. It's "recursive" because it applies the same chunking logic recursively at each level of granularity. It tries to keep text at natural boundaries as long as those boundaries produce chunks small enough. Final fallback is character-by-character splitting. This makes it better than a simple fixed-size split because it preserves natural text structure wherever possible.

4. What is semantic chunking and how does the breakpoint_percentile parameter control it?

▶ Show Answer
Semantic chunking detects where the topic changes by measuring semantic similarity between adjacent sentences using embeddings. Pipeline: (1) Split into sentences + create windows, (2) Embed with SentenceTransformer, (3) Compute cosine distance between adjacent pairs, (4) Find pairs where distance exceeds a threshold = topic-change boundaries, (5) Group sentences between boundaries into chunks. breakpoint_percentile controls the threshold: 50th percentile = aggressive splitting (many breakpoints, smaller chunks, used when document covers many distinct sub-topics). 75th percentile = balanced (default). 90th percentile = conservative (few breakpoints, larger chunks, used when document stays on one topic). Low semantic distance = same topic → keep in one chunk. High semantic distance = topic changed → start new chunk. Note: LangChain's SemanticChunker class was removed from recent versions; use the custom implementation or AI21 API alternative.

5. What is content-aware chunking and when would you choose it over RecursiveCharacterTextSplitter?

▶ Show Answer
Content-aware chunking uses custom Python logic that understands the natural structure of the specific document — instead of blindly splitting at character counts. It preserves boundaries like paragraphs, sections, headings, lists, tables. It's "aware" of what the content is. Example: a document with clearly separated paragraphs → split at double newlines first; only split further if a paragraph exceeds max_chars, using sentence boundaries as a secondary split. Choose content-aware over RCTS when: your data has consistent, identifiable structure (e.g. pharma reports always split into section 1, 2, 3); when you need precise boundary control that RCTS doesn't provide; when retrieval quality with RCTS is poor and you know your data structure. Sunny's real project: "We had a pharma report with 30+ pages and multiple sections. We decided to chunk based on section. Not blindly applying any technique — we analyzed the data first."
