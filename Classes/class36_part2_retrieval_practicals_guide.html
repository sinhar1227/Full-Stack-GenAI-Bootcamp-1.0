def print_results(docs, title="Results", max_docs=4, max_chars=200):
    print(ff"\n{'='*60}\n{title} ({len(docs)} docs)\n{'='*60}")
    for i, doc in enumerate(docs[:max_docs]):
        print(ff"\n[{i+1}] Page {doc.metadata.get('page','?')} | "
              f"Section: {doc.metadata.get('section','?')}")
        print(ff"     {doc.page_content[:max_chars]}...")

# ── Utility: deduplicate results ─────────────────────────────────
def deduplicate_docs(docs):
    """Remove duplicate retrieved chunks while preserving order."""
    seen = set()
    unique = []
    for doc in docs:
        content_hash = hash(doc.page_content)
        if content_hash not in seen:
            seen.add(content_hash)
            unique.append(doc)
    return unique
04 — Sparse Retrieval

BM25 Sparse Retriever

What BM25 Is

BM25 (Best Match 25) is an advanced variant of TF-IDF — a classic information retrieval algorithm. It works on keyword matching and term frequency, not dense embeddings. Sunny covered TF-IDF in the Encoding & Embedding sessions early in the bootcamp.

BM25 — How it Works
  • Builds a sparse vector from vocabulary term frequencies
  • Scores documents by matching query keywords
  • No neural network, no embedding model required
  • Term importance weighted by IDF (rare terms = higher weight)
  • Document length normalisation built in
Dense Retriever — How it Works
  • Uses SOTA embedding model to create dense vectors
  • Semantic similarity — meaning, not keywords
  • Requires embedding model + vector database
  • Can retrieve semantically related text even without exact words
  • Standard RAG approach
⚠️

Key difference from dense retrieval: "In BM25, query embedding is not needed. In the Dense Retriever, we require that. In BM25, the embedding is not required — automatically it will handle that. Explicitly, we don't need to define any embedding model." BM25 goes directly to the chunks — not to the vector database. It operates on text directly.

When BM25 Wins vs When Dense Wins

BM25 wins when…

  • → Query contains specific technical terms, names, model names
  • → Exact keyword match matters (product codes, IDs)
  • → Domain vocabulary is specialised and sparse
  • → No GPU / embedding budget available

Dense wins when…

  • → Query is conversational / paraphrased
  • → Synonyms, related concepts matter
  • → Cross-lingual retrieval needed
  • → Semantic intent, not exact words
05 — Combined Retrieval

Hybrid Retriever — Best of Both

EnsembleRetriever in LangChain

LangChain's EnsembleRetriever combines multiple retrievers and merges their results using Reciprocal Rank Fusion. Sunny's implementation uses 50/50 weights between BM25 and Dense.

→

Reciprocal Rank Fusion (RRF) — How Merging Works

"This reciprocal rank fusion means we are giving the weightage to every Retriever — to which Retriever, how much weightage needs to be provided. So this you can provide inside the weight parameter. 50-50 is more balanced. Otherwise, you can try with 40-60 or 60-40. If you are more confident about semantic search, you can give more weight to the Dense Retriever."
How RRF Works — Intuition

Each retriever ranks its results 1 through k. RRF assigns a score to each document based on its rank position in each list: score = Σ 1/(rank + constant)

A document that appears highly in BOTH lists (BM25 rank 1 AND dense rank 2) scores higher than a document that only appears in one list at rank 1.

The weight parameter (0.5, 0.5) scales each retriever's contribution. More weight = that retriever's rankings matter more in the final merged order.

Full Hybrid Retriever Code

python · hybrid EnsembleRetriever 
from langchain.retrievers import EnsembleRetriever

# ── Create individual retrievers with same k ──────────────────────
bm25_retriever_h = BM25Retriever.from_documents(documents=chunks, k=8)
dense_retriever_h = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 8}
)

# ── Build Hybrid Retriever ────────────────────────────────────────
hybrid_retriever = EnsembleRetriever(
    retrievers = [bm25_retriever_h, dense_retriever_h],
    weights    = [0.5, 0.5]   # 50% BM25, 50% Dense — equal weight
    # Try [0.4, 0.6] if semantic search works better for your data
    # Try [0.6, 0.4] if keyword matching is more important
)

# ── Test hybrid retrieval ─────────────────────────────────────────
query = "Llama 2 70 billion grouped query attention and inference capability"

hybrid_results = hybrid_retriever.invoke(query)
# Automatically deduplicates — no duplicate chunks in results
print_results(hybrid_results, "Hybrid Retrieval Results")

# ── Compare all 3 on the same query ──────────────────────────────
sparse_r = bm25_retriever_h.invoke(query)
dense_r  = dense_retriever_h.invoke(query)
hybrid_r = hybrid_retriever.invoke(query)

print(f"\n{'='*50}")
print(ff"Query: {query[:60]}...")
print(f"\nSparse (BM25) pages: {[d.metadata.get('page') for d in sparse_r]}")
print(ff"Dense pages:         {[d.metadata.get('page') for d in dense_r]}")
print(ff"Hybrid pages:        {[d.metadata.get('page') for d in hybrid_r]}")
# Compare: which pages are unique to BM25? Which to dense? Which in both?
# Hybrid gives you the union — maximum coverage
✅

When does hybrid shine? When a user query has both specific technical terms (BM25 advantage) AND conversational phrasing (Dense advantage). For example: "How does grouped query attention help Llama 2 be faster?" — BM25 catches "Llama 2" and "grouped query attention" exactly; Dense catches "faster inference" via semantic similarity to "inference efficiency." Together they get the best chunks from both angles.

06 — Query Transformation

Query Rewriting / Decomposition

Why Rewrite the Query?

"Query expansion means we can rewrite the query, or we can basically divide the query into multiple parts, and then retrieve the information. HyDE Retriever, Multi-Query Retrieval, Multi-Hop Retrieval — they all work on the same concept. What we do inside query decomposition, query rewriting, query expansion — we transform our query. Whatever query we are going to ask, we transform that query."

The core problem query rewriting solves: a user's original question may be ambiguous, too short, contains pronouns ("it", "they", "that model"), or lacks vocabulary that matches the documents. By rewriting the query using an LLM — informed by chat history — you get a cleaner, standalone search query.

Query Rewriting — Before & After
ORIGINAL QUERY (from user)
"What did Meta do after that?"
⚠ Ambiguous — "after what?" — only makes sense with conversation history
REWRITTEN QUERY (from LLM chain)
"What step did Meta take after initiating supervised fine-tuning for the Llama Chat model?"
✓ Standalone, specific, uses document vocabulary — retrieves correctly

Query Rewriting Code

python · query rewriting chain 
from langchain.prompts         import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai          import ChatOpenAI

llm = ChatOpenAI(model="gpt-4.1-mini")

# ── Query Rewriting Prompt ────────────────────────────────────────
# Instructs the LLM to transform the user's query into a clean search query
query_rewrite_prompt = ChatPromptTemplate.from_template("""
You are a query rewriting assistant for a RAG system.
Your task: Rewrite the conversational question into a CLEAR standalone search query.

Rules:
- Do NOT answer the question
- Preserve important entities, dates, and technical terms
- Resolve pronouns using the conversation history
- Return only ONE rewritten query (no explanations)

Conversation History:
{chat_history}

Original Question: {question}

Rewritten Search Query:""")

# ── Build rewriting chain ─────────────────────────────────────────
query_rewriting_chain = query_rewrite_prompt | llm | StrOutputParser()

# ── Example: rewrite with conversation context ────────────────────
chat_history = [
    {"role": "user",      "content": "Tell me about Meta's Llama 2 training process."},
    {"role": "assistant", "content": "Meta trained Llama 2 using supervised fine-tuning "
                                               "followed by RLHF with human preference data."},
]
original_query = "What did Meta do after that?"

rewritten_query = query_rewriting_chain.invoke({
    "chat_history": chat_history,
    "question":     original_query
})

print(ff"Original:  {original_query}")
print(ff"Rewritten: {rewritten_query}")
# → "What step did Meta take after initiating supervised fine-tuning for the Llama Chat model?"

# ── Now retrieve using the rewritten query ────────────────────────
results = dense_retriever.invoke(rewritten_query)
print_results(results, "Results from Rewritten Query")

How This Powers Agentic RAG

"Whenever we are going to orchestrate our flow using LangGraph, this thing we are going to use a lot in our Agentic RAG system. If we are not going to retrieve the desired information from the given user query, then we'll rewrite that particular query again, and we'll try to retrieve our information based on that query. This is what we are going to do inside the Agentic flow — inside the Agentic RAG."

Reranking with HuggingFace Cross-Encoder

python · cross-encoder reranking 
# !pip install sentence-transformers

from langchain.retrievers                    import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders      import HuggingFaceCrossEncoder

# ── Step 1: Candidate retriever (wide initial pool) ───────────────
# Retrieve many candidates — cross-encoder will narrow them down
candidate_retriever = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 20}   # wide pool for reranker to work with
)

# ── Step 2: Load HuggingFace Cross-Encoder model ─────────────────
# This model uses cross-attention to score (query, document) pairs
# ms-marco-MiniLM-L-6-v2 is a popular, lightweight cross-encoder
cross_encoder_model = HuggingFaceCrossEncoder(
    model_name = "cross-encoder/ms-marco-MiniLM-L-6-v2"
)

# ── Step 3: Build reranker wrapper ───────────────────────────────
reranker = CrossEncoderReranker(
    model     = cross_encoder_model,
    top_n     = 5    # keep top 5 after reranking
)

# ── Step 4: Build ContextualCompressionRetriever ─────────────────
# This wraps the candidate retriever + reranker into one pipeline
reranking_retriever = ContextualCompressionRetriever(
    base_compressor = reranker,
    base_retriever  = candidate_retriever
)

# ── Step 5: Test ─────────────────────────────────────────────────
query = "What is the safety evaluation methodology used in Llama 2?"

# Show candidate count before reranking
candidates = candidate_retriever.invoke(query)
candidates = deduplicate_docs(candidates)
print(ff"Initial candidates: {len(candidates)}")   # 21

# Run through reranking pipeline
reranked = reranking_retriever.invoke(query)
print(ff"After reranking:    {len(reranked)}")    # 5
print_results(reranked, "Reranked Top 5 Documents")

Most Powerful: Hybrid + Cross-Encoder Reranking

"This is going to be a more powerful retrieval, because here we are going to retrieve information — first we retrieve the 15 documents with the hybrid technique, and then we are re-ranking those documents using the cross-encoder. User query → BM25 search → Dense search → Weighted RRF → 15 candidate documents → cross-encoder re-ranker → final top 5 documents. This is the overall process."
python · hybrid + cross-encoder reranking 
# ── Most powerful retrieval: Hybrid + Reranking ───────────────────

# Step 1: BM25 retriever (wider pool for hybrid)
bm25_r15 = BM25Retriever.from_documents(documents=chunks, k=15)

# Step 2: Dense retriever (wider pool)
dense_r15 = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 15}
)

# Step 3: Build Hybrid retriever with equal weights
hybrid_base = EnsembleRetriever(
    retrievers = [bm25_r15, dense_r15],
    weights    = [0.5, 0.5]
)

# Step 4: Cross-encoder reranker (top 5 from hybrid's candidates)
cross_encoder = HuggingFaceCrossEncoder(
    model_name = "cross-encoder/ms-marco-MiniLM-L-6-v2"
)
reranker_5 = CrossEncoderReranker(model=cross_encoder, top_n=5)

# Step 5: Combine hybrid + reranker
hybrid_reranking_retriever = ContextualCompressionRetriever(
    base_compressor = reranker_5,
    base_retriever  = hybrid_base   # hybrid is the base, not just dense!
)

# Step 6: Test
query = "What safety measures and red-teaming were used in Llama 2?"
final_docs = hybrid_reranking_retriever.invoke(query)

print(ff"\nHybrid + Reranking → top {len(final_docs)} documents:")
print_results(final_docs, "Hybrid + Cross-Encoder Reranked")

# Flow summary:
# Query → BM25 (15 docs) + Dense (15 docs) → RRF merge → 15 candidates
# → Cross-Encoder scores each (query, doc) pair via cross-attention
# → Returns top 5 most accurately relevant documents
# → LLM receives these 5 highly accurate, diverse chunks
08 — Decision Guide

Choosing the Right Retriever Strategy

Strategy Complexity Accuracy Best For
BM25 only Low Moderate Keyword-heavy docs, no embedding budget
Dense only Low–Medium Good General RAG, conversational queries
Hybrid (BM25 + Dense) Medium Better Most production RAG systems
Hybrid + Reranking High Best ★ High-accuracy requirements, large datasets
Dense + Query Rewriting Medium Better Multi-turn conversations, Agentic RAG

11 — Self-Check

Quiz — Test Your Understanding

📝 Class 36 Part 2 — Concept Check

1. What is the key difference between BM25 and Dense retrieval? Does BM25 need an embedding model?

▶ Show Answer
BM25 is a sparse keyword-based retrieval algorithm (advanced variant of TF-IDF) that works by scoring documents based on term frequency and inverse document frequency — it does NOT need an embedding model. It operates directly on text chunks using vocabulary matching. Dense retrieval uses a state-of-the-art embedding model to generate dense vectors; retrieval is based on cosine/dot/Euclidean similarity between vector representations. BM25 is faster and simpler but misses semantic meaning; dense retrieval understands meaning but needs embedding infrastructure.

2. What is EnsembleRetriever and how does Reciprocal Rank Fusion (RRF) combine results?

▶ Show Answer
EnsembleRetriever is LangChain's class for hybrid retrieval — it takes multiple retrievers (e.g. BM25 + Dense) and combines their results using Reciprocal Rank Fusion. RRF works by: each retriever ranks its results 1 through k; each document gets a score = Σ 1/(rank + constant) across all retrievers; documents appearing highly ranked in BOTH retrievers score higher than those appearing in only one. The weights parameter ([0.5, 0.5]) scales each retriever's contribution to the final score. Equal weights (50/50) is a balanced baseline; you can experiment with [0.4, 0.6] to weight semantic search more, or [0.6, 0.4] to weight keyword matching more.

3. What problem does query rewriting solve, and how is it built in LangChain?

▶ Show Answer
Query rewriting solves the problem of ambiguous, context-dependent, or pronoun-heavy user queries that don't match document vocabulary well. For example: "What did Meta do after that?" cannot be retrieved well because "that" needs conversation context, and "Meta" may not match the vocabulary. A query rewriting chain: creates a prompt instructing the LLM to rewrite the query into a standalone search query; provides chat history as context; the LLM generates a clear, specific query like "What step did Meta take after initiating supervised fine-tuning for the Llama Chat model?" — which retrieves correctly. Built as: ChatPromptTemplate | ChatOpenAI | StrOutputParser().

4. Walk through the complete Hybrid + Cross-Encoder Reranking pipeline step by step.

▶ Show Answer
Step 1: User query goes to both BM25 (k=15 chunks) AND Dense retriever (k=15 chunks) in parallel. Step 2: EnsembleRetriever merges both result sets using Reciprocal Rank Fusion with equal weights — produces ~15 deduplicated candidate documents. Step 3: The ContextualCompressionRetriever takes these 15 candidates and passes each (query, document) pair to the HuggingFace CrossEncoder. Step 4: Cross-Encoder uses cross-attention (not simple cosine similarity) to deeply score how relevant each document is to the query. Step 5: Reranker returns the top N (e.g. top_n=5) documents sorted by cross-encoder score. Step 6: These 5 highly accurate, diverse documents go to the LLM as context. Sunny called this "the most powerful retrieval" because it combines keyword precision (BM25) + semantic understanding (dense) + deep relevance scoring (cross-encoder).

5. How does query rewriting power Agentic RAG differently from standard RAG?

▶ Show Answer
In standard RAG, the user's original query is passed directly to the retriever — if it retrieves poor results, the LLM answers poorly, and the flow ends. In Agentic RAG (built with LangGraph), the system includes a retry loop: if the retriever returns no relevant documents or the answer quality is poor, the agent triggers the query rewriting step to generate a better search query, then retrieves again. This self-correcting loop makes the system far more robust for complex questions, ambiguous queries, and multi-turn conversations where context matters. Sunny explicitly said: "Whenever we orchestrate our flow using LangGraph, this thing we are going to use a lot in our Agentic RAG system."
