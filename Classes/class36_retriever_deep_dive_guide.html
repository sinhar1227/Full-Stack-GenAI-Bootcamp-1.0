03 — Core Concept

What is a Retriever?

Sunny's Class Definition
A Retriever takes a user query and returns the most
relevant documents / chunks from the knowledge source (Vector DB)
🔑

Critical distinction: "A retriever normally does not generate the final answer itself. It collects the relevant context which is required to generate the answer. Retriever answer is not a final answer — it is going to collect the relevant context from the vector database, and then LLM is going to generate the final answer."

The Retriever's 3-Step Job

1
Takes a query. The user's natural language question arrives at the retriever.
2
Searches the knowledge source. Embeds the query and runs similarity search inside the vector store.
3
Returns the most relevant chunks. Top-k Document objects are returned for the LLM to use as context.
🟢

Framework independence: "Most of the time in the industry — 95–99% — we use LangChain. But if you're using LlamaIndex or Haystack, the concept is the same. Only the function or class name changes according to the framework."

04 — Configuration

Retriever Parameters — All of Them

Sunny walked through every parameter you encounter when creating a LangChain retriever. Know these before any interview or production work.

ParameterTypeDescriptionDefault
k int Number of documents to retrieve. If k=10, the retriever returns the top 10 most similar chunks. Directly passed in search_kwargs. 4
filter dict Metadata pre-filter. Only documents matching these metadata key-value pairs are considered. e.g. {"section": "fine-tuning", "year": "2023"}. Use carefully — wrong filter = wrong results. None
score_threshold float Minimum cosine similarity score (0.0–1.0) a document must meet to be returned. Documents below this threshold are discarded. Used with search_type="similarity_score_threshold". None
fetch_k int MMR-specific. Fetch this many candidate documents first (wider pool), then MMR selects k most relevant+diverse from these candidates. fetch_k ≥ k always. 20
lambda_mult float (0–1) MMR-specific. Controls the trade-off: 1.0 = pure similarity (ignore diversity), 0.0 = pure diversity (ignore relevance). Recommended: 0.5 (balanced). Covered in depth in next class. 0.5
search_type str "similarity" (default) or "mmr" or "similarity_score_threshold". Controls which retrieval algorithm runs. Passed to as_retriever(). "similarity"

05 — Similarity Metrics

The 3 Similarity Search Methods

Cosine Similarity
cos(A,B) = (A·B) / (‖A‖ × ‖B‖)

Normalised dot product. Measures the angle between two vectors regardless of their magnitude. Range: −1 to +1. Higher = more similar.

✓ Best for: text, RAG, all NLP tasks
Standard choice — used 95% of the time in production
Dot Product
A · B = Σ (Aᵢ × Bᵢ)

Multiply corresponding elements and sum them. No fixed range — depends on vector magnitudes. Cosine = normalised version of dot product.

✓ Best for: normalised vectors
After normalising dot product values = cosine similarity values
Euclidean Distance (L2)
d(A,B) = √Σ(Aᵢ − Bᵢ)²

Geometric straight-line distance between two points. Lower = more similar. Range: 0 to ∞. Sensitive to magnitude differences.

✓ Best for: image search, spatial data
Used in FAISS IndexFlatL2 by default
"Cosine similarity is normalised distance — normalised similarity between A and B vector. What is this dot product between them divided by the distances — so it's a normalised value. Most of the time, you are going to use cosine similarity in real time. Generally, we use the cosine similarity, which is a more normalised one."

MMR — Maximum Marginal Relevance

MMR Definition

An advanced type of similarity search that balances relevance AND diversity

It is NOT a separate formula — it is an updated version of cosine similarity where the selection algorithm also penalises near-duplicate results.

"MMR is an advanced kind of similarity search. In MMR also, are we using any different concept? No. We are using cosine similarity only. But it is in a different way — we are going to check the similarity along with the diversification. MMR is really useful — even I have used it in one of my real-time projects and it was working good. It will give you quite good results compared to normal cosine, dot product, or Euclidean distance."

MMR's two-stage selection:

1
Stage 1 (fetch_k): Retrieve a larger candidate pool (e.g. 20 documents) using standard cosine similarity.
2
Stage 2 (k, lambda_mult): From those 20, iteratively select k documents that are both relevant to the query AND different from already-selected documents. lambda_mult controls the balance (1.0 = pure relevance, 0.0 = pure diversity).
📌

When to use MMR: Use when you notice your top-k results are near-duplicates (chunks from the same paragraph returning 4 times). MMR ensures the LLM gets diverse context from across the document, not the same information repeated. Particularly useful with large documents and high-overlap chunks. fetch_k and lambda_mult formula will be covered in detail in the next class.

06 — Architecture Types

3 Types of Retriever

Sunny placed sparse retrieval in historical context: the original RAG paper (Facebook, 2020) used sparse retrieval — it predated modern dense embedding models. The RAG chapter started specifically because strong embedding models emerged, making dense retrieval the dominant approach.

Type 1

Sparse Retriever

Old, reliable technique. Predates dense LLM embeddings. Uses sparse vectors (most elements = 0) built from vocabulary matching.

  • TF-IDF (Term Frequency–Inverse Document Frequency)
  • BM25 (Best Match 25)
  • Keyword search, term matching
  • No neural embeddings needed

∷ The original RAG paper used this · Still reliable · Used in "vectorless RAG"

Type 2

Dense Retriever

Modern approach — uses state-of-the-art LLM embedding models to generate dense vectors (every element is a float). Performs semantic search.

  • Bi-encoder architecture (query and doc encoded separately)
  • Semantic similarity, not keyword matching
  • Requires an embedding model + vector store
  • What we've been building in this bootcamp

∷ Standard RAG approach · 95%+ of modern RAG systems

Type 3

Hybrid Retriever

Combines both sparse (keyword) and dense (semantic) retrieval. Results from both are merged using fusion techniques.

  • Sparse + Dense running in parallel
  • Results merged via Reciprocal Rank Fusion (RRF) or Weighted Fusion
  • Gets exact keyword matches AND semantic matches
  • Best coverage for production systems

∷ Production best practice · Handles vocabulary mismatch · Code in next class

"Hybrid retriever means we are going to combine both — keyword and the vector search. Then we'll get the combined result. TF-IDF, BM25 keywords — it's a very old technique for retrieving information, but it is an old and reliable technique. When the strong embedding model came, RAG became popular. But before that, everyone was already retrieving — just differently."
07 — Production Technique

Pre-Filtering vs Post-Filtering

Metadata filtering is how you restrict retrieval to specific subsets of your knowledge base. Two approaches — and Sunny shared which one he uses in production.

✅ Pre-Filtering (Recommended)
1

Apply metadata filter first — restrict the vector database to only the documents matching your metadata criteria

2

Run similarity search — query embedding is compared ONLY against the filtered (smaller) document set

3

Return top-k results from the filtered space

✓ Faster · ✓ More precise · ✓ Tenant isolation · ✓ Security
⚠ Post-Filtering (Use carefully)
1

Run similarity search first — query embedding compared against ALL documents in the vector database

2

Apply metadata filter to the retrieved results — filter out documents that don't match criteria

3

Return remaining results (may be fewer than k)

✗ Slower · ✗ May miss relevant docs · ✗ Unauthorized docs enter intermediate set
"I have also applied pre-filtering in real-time projects where I was having so many documents. Based on the pre-filtering only, I was filtering out the data. Later on, when I was delivering my solution, I changed the post-filtering to pre-filtering, and with that I was able to speed up the retrieval significantly. Pre-filtering is recommended — it is the faster of the retrieval process."

Tenant Isolation via Pre-Filtering

One of the most important production use cases for pre-filtering:

"Tenant isolation means multi-tenant RAG application. Tenant A can retrieve only Tenant A documents, and Tenant B can retrieve only Tenant B documents. Let's say Tenant A is Company A, or Department A. So, Department A can only retrieve Department A documents after putting the pre-filtering. Department B can only retrieve Department B documents after putting the pre-filtering. But this is NOT possible with post-filtering."
Multi-Tenant RAG Architecture
Company Knowledge Base (one VDB)
├── tenant: "hr_dept" → HR policies, leave docs, compensation data
├── tenant: "finance" → P&L reports, budgets, invoices
└── tenant: "engineering" → tech specs, architecture docs, runbooks
HR employee query → filter={"tenant":"hr_dept"} → only HR docs retrieved
Finance employee query → filter={"tenant":"finance"} → only finance docs retrieved
Cross-department leakage: impossible with pre-filtering
08 — Advanced Retrieval

Re-Ranking

Re-ranking is a second-stage process applied after initial retrieval. Sunny's classroom analogy made it clear:

"In the classroom, let's say we have 50 students. I filter based on IQ — I find 10 students. These are the excellent ones. Now, again, I put one more parameter: reasoning or logical thinking. In that case, I found the top 3 students. These 3 students are extraordinary. So — the 10 students are filtered data, but the 3 students are MORE filtered data. This is re-ranking."
Re-Ranking Pipeline
User Query
→
Initial Retriever
(BM25 / Dense / Hybrid)
→
Top Candidate Docs
k=20 (wider pool)
→
Re-Ranker
(Cross-Encoder)
→
Top-k Reordered
k=5 most relevant
→
LLM

Re-ranking — Key Facts

  • → Definition: A second-stage retrieval process that takes initially retrieved documents, scores them more accurately against the user query, and reorders them so the most relevant go to the LLM
  • → Not the same as metadata filtering: Re-ranking uses a semantic model (not metadata values) to re-score and reorder
  • → Not mandatory: Use when you have a lot of data and want to filter more precisely before sending to LLM
  • → Benefits: Improved ordering of retrieved documents, removes weak candidates, reduces irrelevant context, reduces input tokens, improves evidence quality
  • → Limitations: Adds latency, additional inference cost, adds complexity

Cross-Encoder — The Reranking Model

"What algorithm can we use for reranking? In the industry, we are basically using the cross-encoder. Cross-encoder is nothing — it's just an LLM model which is primarily using the cross-attention mechanism between the user query and the given document. You remember, in the transformer architecture, I explained 3 kinds of self-attention: normal self-attention, cross-attention, and masked attention. The cross-encoder works on the cross-attention technique."

Bi-Encoder (Dense Retriever)

Query and document encoded SEPARATELY by the same model. Fast — embeddings can be pre-computed. Used for initial retrieval across millions of docs. Cosine similarity between two independent vectors.

Cross-Encoder (Re-Ranker)

Query and document passed TOGETHER through a model. Uses cross-attention to check deep query-document relationship. Much slower but far more accurate. Used only on top-k candidates, not full dataset.

import numpy as np
from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS

# ── Setup: Load existing vector store ────────────────────────────
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")
# Assume we have a vector store built from a PDF with metadata:
# {"section": "fine-tuning", "year": "2023", "page": 5, ...}

# ── Run similarity search and get candidate chunks ───────────────
query        = "What are the different metrics in the RAG pipeline?"
candidate_docs = vector_store.similarity_search(query, k=6)

print(ff"Candidate chunks selected: {len(candidate_docs)}")

# ── Extract text and embed manually ──────────────────────────────
candidate_texts = [doc.page_content for doc in candidate_docs]

# Embed query and all candidate texts
query_vec     = np.array(embedding_model.embed_query(query))
doc_vecs      = np.array(embedding_model.embed_documents(candidate_texts))

print(ff"Query vector shape:    {query_vec.shape}")   # (1536,)
print(ff"Doc vectors shape:     {doc_vecs.shape}")    # (6, 1536)

# ── Compare all 3 metrics for each candidate ─────────────────────
results = []
for i, (doc_vec, text) in enumerate(zip(doc_vecs, candidate_texts)):

    # 1. Cosine Similarity (normalised, range −1 to +1)
    cosine = np.dot(query_vec, doc_vec) / (
        np.linalg.norm(query_vec) * np.linalg.norm(doc_vec)
    )

    # 2. Euclidean Distance (geometric, lower = more similar)
    euclidean = np.linalg.norm(query_vec - doc_vec)

    # 3. Dot Product (no fixed range)
    dot_product = np.dot(query_vec, doc_vec)

    results.append({
        "chunk_idx":   i,
        "cosine":      round(float(cosine),      4),
        "euclidean":   round(float(euclidean),   4),
        "dot_product": round(float(dot_product), 4),
        "preview":     text[:80]
    })

# ── Print comparison table ────────────────────────────────────────
print(f"\n{'Chunk':5} {'Cosine':10} {'Euclidean':12} {'Dot Prod':12} Preview")
print("-" * 80)
for r in results:
    print(ff"{r['chunk_idx']:5} {r['cosine']:10.4f} {r['euclidean']:12.4f} {r['dot_product']:12.4f} {r['preview'][:40]}")

# Proof: after normalising dot product → same value as cosine
q_norm = query_vec / np.linalg.norm(query_vec)
d_norm = doc_vecs[0] / np.linalg.norm(doc_vecs[0])
print(ff"\nNormalised dot product: {np.dot(q_norm, d_norm):.4f}")
print(ff"Cosine similarity:      {results[0]['cosine']:.4f}")
# → These values are identical! Proving cosine = normalised dot product

Metadata Pre-Filtering and Post-Filtering

python · pre and post filtering 
# ── PRE-FILTERING (recommended) ──────────────────────────────────
# filter applied BEFORE similarity search, inside vector store
retriever_pre = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {
        "k":      4,
        "filter": {
            "section": "fine-tuning",
            "year":    "2023"
        }
    }
)
pre_results = retriever_pre.invoke("Tell me about fine-tuning techniques")
print(ff"Pre-filter results: {len(pre_results)}")
# All returned documents will be from section="fine-tuning" AND year="2023"

# ── Verify pre-filtering type ────────────────────────────────────
for doc in pre_results:
    print(ff"  section: {doc.metadata.get('section')} | year: {doc.metadata.get('year')}")

# ── POST-FILTERING (manual, use with caution) ─────────────────────
# step 1: retrieve wide candidate set (no filter, k=15)
all_candidates = vector_store.similarity_search(
    "Tell me about fine-tuning techniques",
    k = 15   # retrieve more docs since we'll filter some out
)

# step 2: apply metadata filter manually after retrieval
post_results = [
    doc for doc in all_candidates
    if doc.metadata.get("section") == "fine-tuning"
    and doc.metadata.get("year")    == "2023"
]
print(ff"Post-filter results: {len(post_results)}")

# ── PRODUCTION VERDICT ───────────────────────────────────────────
# Pre-filtering: faster, smaller search space, enables tenant isolation
# Post-filtering: slower, may miss docs, unauthorized docs enter pool
# → In production: ALWAYS prefer pre-filtering
10 — Self-Study

Terms to Explore Further

Sunny shared these as additional retrieval topics to research independently. Some will be covered in subsequent classes:

Weighted Fusion

Merge sparse + dense results by assigning weights to each. Tunable for your dataset.

RRF (Reciprocal Rank Fusion)

Standard algorithm to combine ranked lists from sparse and dense retrievers.

Multi-Query Retriever

Generate multiple rephrasings of the user query; retrieve for each; merge results.

HyDE

Hypothetical Document Embeddings — generate a hypothetical answer, embed it, use it as query.

Parent Document Retriever

Store large chunks; retrieve small child chunks; return parent context to LLM.

Sentence Window Retriever

Index sentences; retrieve individual sentences; expand to surrounding window for context.

Contextual Compression

Compress/summarise retrieved chunks before sending to LLM to reduce tokens.

Multi-Hop Retriever

Answer complex questions by chaining multiple retrieval steps.

11 — Self-Check

Quiz — Test Your Understanding

📝 Class 36 Concept Check

1. What does a retriever do, and what does it NOT do? Give a one-line definition.

▶ Show Answer
A retriever takes a user query and returns the most relevant document chunks from the knowledge source (vector database). It does NOT generate the final answer — that is the LLM's job. The retriever's sole purpose is to collect relevant context; the LLM then uses that context to generate a grounded answer.

2. Explain the 5 retriever parameters: k, filter, score_threshold, fetch_k, and lambda_mult.

▶ Show Answer
k: number of documents to retrieve (top-k results). filter: metadata dictionary for pre-filtering — only documents matching these metadata values are considered before similarity search. score_threshold: minimum cosine similarity score (0–1) a document must have to be returned; used with search_type="similarity_score_threshold". fetch_k: MMR-specific — fetch this many candidate documents first (wider pool) before MMR selection. lambda_mult: MMR-specific (0–1) — controls relevance vs diversity balance; 1.0 = pure relevance, 0.0 = pure diversity, 0.5 = balanced.

3. What is the mathematical relationship between cosine similarity and dot product?

▶ Show Answer
Cosine similarity is the normalised version of dot product: cos(A,B) = (A·B) / (‖A‖ × ‖B‖). You divide the raw dot product by the product of the magnitudes (norms) of both vectors. When vectors are already normalised (unit vectors, magnitude=1), the dot product equals cosine similarity. Sunny proved this live: computing normalised dot product and cosine similarity on the same vectors gives identical values. This is why cosine similarity is range-bounded (−1 to +1) while raw dot product has no fixed range.

4. What is MMR (Maximum Marginal Relevance) and how does it differ from standard cosine similarity search?

▶ Show Answer
MMR (Maximum Marginal Relevance) is an advanced type of similarity search that balances relevance AND diversity. It is NOT a separate formula — it is an updated version of cosine similarity with an additional diversity penalty. Standard cosine search: just return the k most similar documents. MMR: first fetch fetch_k candidates using cosine similarity; then iteratively select k documents that are both relevant to the query AND different from already-selected documents. lambda_mult controls the balance. This prevents returning near-duplicate chunks and ensures the LLM gets diverse coverage of the document. Use when you see repetitive chunks in your top-k results.

5. Explain pre-filtering vs post-filtering. Which is recommended in production and why?

▶ Show Answer
Pre-filtering: Apply metadata filter FIRST (inside the vector database), then run similarity search on the smaller filtered document set. Post-filtering: Run similarity search on all documents FIRST, then apply metadata filter to the results. Pre-filtering is strongly recommended in production because: (1) faster — searches a smaller space, (2) more precise — no irrelevant documents enter the candidate pool, (3) enables tenant isolation — Department A's users can only retrieve Department A's documents, which is impossible with post-filtering, (4) better security — unauthorized documents never enter the intermediate candidate set. Post-filtering has limitations: may miss relevant documents if they weren't in the initial top-k, and unauthorized documents can enter the intermediate retrieval pool before being filtered out.

6. What is re-ranking, and how does a cross-encoder work for re-ranking?

▶ Show Answer
Re-ranking is a second-stage retrieval process that takes the initial top-k retrieved documents, scores them more accurately against the user query, and reorders them so the most relevant documents go to the LLM. It's like filtering 50 students by IQ to get 10, then further filtering by reasoning to get 3 extraordinary ones. A cross-encoder is an LLM model used as a re-ranker. Unlike a bi-encoder (which embeds query and document separately), a cross-encoder receives (query, document) pairs together and uses cross-attention mechanism to deeply check how relevant each document is to the query. Cross-attention examines token-level interactions between query and document, making it much more accurate than simple cosine similarity — but slower, so it's only applied to the top-k candidates, not the full dataset.

7. What are the 3 retriever types and when was sparse retrieval introduced relative to dense retrieval?

▶ Show Answer
Type 1 (Sparse): Uses TF-IDF, BM25, keyword/term matching — sparse vectors. Old technique that predated dense LLM embeddings. The original RAG research paper (2020, Facebook) used sparse retrieval before modern embedding models existed. Type 2 (Dense): Uses state-of-the-art LLM embedding models to generate dense vectors. Semantic search based on meaning, not keywords. The dominant approach since strong embedding models emerged. Type 3 (Hybrid): Combines both sparse and dense retrieval. Results merged using Reciprocal Rank Fusion (RRF) or Weighted Fusion. Best coverage — gets exact keyword matches AND semantic meaning. ChatGPT came in December 2022; before that, most people hadn't heard of LLMs, but RAG research had already begun with sparse approaches in 2020.
