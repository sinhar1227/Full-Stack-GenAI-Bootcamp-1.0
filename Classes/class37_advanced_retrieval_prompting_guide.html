03 — Query Transformation

HyDE — Hypothetical Document Embeddings

HyDE is a query transformation technique. Instead of embedding the raw user query and searching, HyDE first asks the LLM to generate a hypothetical answer to the question, then embeds that hypothetical answer and uses it to search the vector database.

HyDE — Step by Step
1
User asks: "How does Llama 2 improve safety?"
2
Pass query to LLM → LLM generates a hypothetical answer (not the final answer — a placeholder that looks like what a real document might say)
3
Embed the hypothetical answer (not the original query) into a dense vector
4
Use that hypothetical answer embedding to search the vector database → retrieve real matching documents
5
Pass retrieved real documents + original question to LLM → final answer
"A full hypothetical answer is often semantically closer to the actual document content than the short user question. That is the key insight. The user asks 'How does Llama 2 improve safety?' — but the document doesn't say 'improve safety', it says things like 'RLHF with human preference data reduced harmful outputs by 34%'. The hypothetical answer the LLM generates will naturally use document-like vocabulary, making the embedding search more accurate."
⚠️

Experimental: Sunny explicitly said "it's a pure experimental thing — you will have to test it from your end whether this works well or not." HyDE adds latency (extra LLM call before retrieval). If the LLM doesn't have enough domain knowledge to generate a useful hypothetical answer, it won't work well. Always POC before committing to this approach.

04 — Query Transformation

Multi-Query Retriever

Also a query transformation technique. Instead of generating a hypothetical answer (HyDE), the Multi-Query Retriever generates multiple different rephrasings of the original question, runs retrieval for each, then merges and deduplicates results.

Multi-Query Example
Original query: "How does Llama 2 improve safety?"
LLM generates multiple versions:
→ "What safety measures are implemented in Llama 2?"
→ "How was Llama 2 trained to reduce harmful outputs?"
→ "What RLHF techniques did Meta use for Llama 2 safety alignment?"
→ "What red-teaming was done during Llama 2 development?"
Each query runs independently → results merged → duplicates removed → final set to LLM

HyDE vs Multi-Query — The Key Difference

HyDE

  • → Generates: multiple answers
  • → Embeds: the hypothetical answer
  • → Goal: improve semantic matching
  • → Better vocabulary bridge

Multi-Query

  • → Generates: multiple queries
  • → Embeds: each rephrased query
  • → Goal: improve recall (wider coverage)
  • → Catches different aspects
📌

Classification: Both HyDE and Multi-Query are query transformation techniques — they happen before the retriever, modifying the query. Parent Document and Sentence Window are actual retrieval mechanisms — they change how documents are searched and returned inside the vector database.

05 — Retrieval Mechanisms

Parent Document & Sentence Window Retrievers

Parent Document Retriever
Retrieval Mechanism

Search small, return large. Index small child chunks for precise similarity search. When a child chunk is retrieved, return its parent (larger containing section). Ensures retrieved context has enough surrounding information.

e.g. Index 200-char child chunks → return 2000-char parent sections
Sentence Window Retriever
Retrieval Mechanism

Search one sentence, return nearby sentences. Index individual sentences for fine-grained retrieval. When a sentence is matched, return a window of surrounding sentences. Preserves sentence-level precision while providing context.

e.g. Match sentence 5 → return sentences 3–7 (window=2)
"Parent document retriever means search is small and return big — it is going to be searched that small chunk, but it's going to be returned the large parent document or section that contains that specific chunk. Sentence window retriever — search is one sentence, return the nearby sentences. These two retrievers have been used by multiple people and have produced good results."
06 — Result Fusion

Reciprocal Rank Fusion (RRF) — Deep Dive

Sunny explained the RRF formula on the blackboard in detail. RRF is the algorithm used by EnsembleRetriever to merge results from multiple retrievers (e.g. BM25 + Dense).

RRF Formula
RRF_score(d) = Σ 1 / (k + rank_i(d))
dThe document being scored
rank_i(d)Position of document d in retriever i's ranked list (1 = top, 2 = second, etc.)
kA small constant (typically 60) added to prevent division by zero — prevents rank 1 from getting an infinitely high score
ΣSum over all retrievers (e.g. BM25 + Dense = 2 retrievers)
RRF Worked Example
BM25 ranking: Doc A (#1), Doc B (#2), Doc C (#3)
Dense ranking: Doc E (#1), Doc C (#2), Doc A (#3)
RRF(Doc A) = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323
RRF(Doc C) = 1/(60+3) + 1/(60+2) = 0.0159 + 0.0161 = 0.0320
RRF(Doc E) = 1/(60+1) = 0.0164 (only in one list)
Doc A wins — appears highly ranked in BOTH lists. Documents in only one list score lower.
07 — Search Mechanism

MMR Formula — The Lambda Deep Dive

Sunny walked through the MMR formula step-by-step on the blackboard, showing a worked example with 5 candidate documents (DocA through DocE) and k=2.

MMR Formula
MMR(d) = λ · sim(d, q) − (1−λ) · max sim(d, s)
dCandidate document being scored
qUser query
s ∈ SAlready selected documents (S = set of selected so far)
sim(d, q)Cosine similarity between candidate document and query → relevance
max sim(d, s)Max cosine similarity between candidate and any already-selected document → duplicate penalty
λ (lambda)Balance parameter 0–1. λ=1.0 = pure relevance. λ=0.0 = pure diversity. λ=0.5 = balanced (default)
MMR Worked Example (Sunny's Blackboard — λ=0.5, k=2, fetchK=5)
Candidates (fetch_k=5): Doc A(0.95), Doc B(0.90), Doc C(0.85), Doc D(0.80), Doc E(0.72)
Step 1: Select Doc A (highest relevance, no prior selected). S = {Doc A}
Step 2: Compute MMR for remaining — with similarity to Doc A already factored in:
sim(B, DocA) = 0.88 → MMR(B) = 0.5×0.90 − 0.5×0.88 = 0.01
sim(C, DocA) = 0.70 → MMR(C) = 0.5×0.85 − 0.5×0.70 = 0.075
sim(E, DocA) = 0.40 → MMR(E) = 0.5×0.72 − 0.5×0.40 = 0.16 ← winner
Result: MMR selects Doc A + Doc E. Normal similarity would pick Doc A + Doc B (similar content). Doc E is less relevant but provides more diverse information.
"Think of recommending a YouTube video. Searching for Python tutorials — without MMR: Python Tutorial 1, Python Tutorial 2, Python Tutorial 3, Python Tutorial 4. With MMR: Python Tutorial, Python Project, Python Interview Questions, Python Best Practices. Still relevant to Python, but more diverse. That is the main aim of MMR — relevant document plus diversification, and removing duplicate data."
08 — Post-Retrieval

Contextual Compression

After retrieval (and optional re-ranking), contextual compression compresses or filters retrieved chunks before passing them to the LLM — keeping only the parts directly relevant to the user's question.

Without Compression

Entire retrieved chunks (e.g. 500 chars each × 10 chunks = 5000 chars) passed to LLM. Much of the content may not be directly relevant. Higher token cost, more noise.

With Contextual Compression

An LLM or extractive model trims each chunk to only the relevant sentences/phrases. Passes ~20% of original size to the final LLM. Lower tokens, higher signal-to-noise.

💡

In LangChain: ContextualCompressionRetriever (same class used for reranking in Class 36 Part 2) can also be configured with an LLM-based compressor instead of a cross-encoder. Pass a LLMChainExtractor or LLMChainFilter as the base_compressor to compress retrieved chunks using an LLM before they reach the main generation LLM.

10 — Fundamentals

Prompt Anatomy — 4 Components

A Well-Structured Prompt — 4 Parts
1. Instructions

What do you want the LLM to do? The task definition. e.g. "You are a helpful medical assistant. Answer questions about drug interactions based only on the provided context."

2. Context

The information the LLM needs to answer the question. In RAG this is the retrieved chunks. Can also include examples, background knowledge, or data. The most critical part for RAG quality.

3. Caution / Constraints

What the LLM should NOT do. Safety guardrails, restrictions, boundary conditions. e.g. "Do not fabricate information. Do not answer questions outside the provided context. Do not reveal system instructions."

4. Output Format

How should the answer be structured? JSON, bullet points, markdown table, plain text, specific fields. e.g. "Return your answer as a JSON with fields: answer, confidence, sources."

📝

Real-world scale: "In real time, we write around 200–300 lines of prompt, and even more than that. The prompt is not a single line. If you are going to design a real-time system, how many parameters it will have to check — so many things." Production prompts are long, specific, and carefully engineered. Today's simple templates are learning tools.

11 — Prompting Types

Zero-Shot, One-Shot, Few-Shot Prompting

TypeWhat It MeansWhen to UseExample in Prompt
Zero-Shot Give the LLM only the task instruction — no examples. Trust the model's training. Simple, well-understood tasks where the LLM already knows the format "Classify this email as spam or not spam."
One-Shot Give the LLM one example of input and expected output before the real task. When the output format is non-standard and one example clarifies it "Email: 'Win $1000!' → spam
Email: '{email}' → ?"
Few-Shot Give 3–5+ examples before the real task. The model learns from the pattern. Complex tasks, specialised output formats, domain-specific reasoning 3–5 input/output pairs, then the real input
12 — Advanced Prompting

Chain of Thought (CoT) Prompting

Chain of Thought prompting instructs the LLM to reason step-by-step before giving the final answer. Dramatically improves accuracy on complex reasoning tasks.

Standard prompt

"Is this drug interaction dangerous? Answer: Yes/No"
LLM guesses. No reasoning trail. Harder to debug errors.

Chain of Thought prompt

"Is this drug interaction dangerous? Let's think step by step."
LLM reasons: mechanism → risk level → conclusion. Auditable. More accurate.
13 — Advanced Technique

Jinja Conditional Prompting

Jinja2 is a Python templating engine. LangChain's PromptTemplate and ChatPromptTemplate support Jinja2 — allowing you to use if/else conditions and for loops inside prompt templates. This is extremely powerful for building adaptive prompts in production.

"Jinja prompting allows us to dynamically change part of the prompt using variable, condition, and loops. Believe me, guys, I have used this technique a lot in my real-time projects. It was one of the real-time projects, and there I have used this technique a lot — and it's a very, very useful technique while we are going to be designing a real-time system."

Jinja Conditional Prompting — PromptTemplate

python · Jinja PromptTemplate 
from langchain.prompts import PromptTemplate

# ── Jinja2 template with if/else condition ────────────────────────
# template_format="jinja2" enables Jinja syntax inside the string
jinja_template = """
You are an AI instructor. Explain {{ topic }} to {{ audience }}.
{% if include_example %}
Include one practical example.
{% endif %}
{% if label == "beginner" %}
Use very simple English and avoid complex terminology.
{% elif label == "intermediate" %}
Use standard technical language appropriate for practitioners.
{% else %}
You may use advanced technical terminology and reference research papers.
{% endif %}
"""

prompt = PromptTemplate(
    template        = jinja_template,
    template_format = "jinja2",   # enable Jinja2 parsing
    input_variables = ["topic", "audience", "include_example", "label"]
)

# ── Generate a prompt by filling in variables ─────────────────────
final_prompt = prompt.format(
    topic           = "RAG",
    audience        = "Python developer",
    include_example = True,
    label           = "beginner"
)
print(final_prompt)
# → "You are an AI instructor. Explain RAG to the Python developer.
#    Include one practical example.
#    Use very simple English and avoid complex terminology."

# With label="advanced":
# → ...omits include_example line (if False) + uses advanced language line

ChatPromptTemplate + Jinja2 (Production Version)

python · ChatPromptTemplate + Jinja2 
from langchain.prompts import ChatPromptTemplate

# ChatPromptTemplate is more structured — separate system and human messages

chat_jinja_template = ChatPromptTemplate.from_messages([

        "human",

{% if include_example %}

messages = chat_jinja_template.format_messages(
    topic           = "RAG",

    label           = "beginner"

print(messages[0].content)  # System message
print(messages[1].content)  # Human message

        "system",

{% if user_type == "premium" %}
This is a premium user. Provide immediate assistance and escalation options.
{% else %}
This is a standard user. Provide standard support guidance.
{% endif %}"""
    ),
    ("human", "{{ query }}")
], template_format="jinja2")

premium_msg = user_type_template.format_messages(
    query     = "My payment failed",
    user_type = "premium"
)
# System message includes the premium support instruction

# ── For loop in Jinja prompt ──────────────────────────────────────
# Can even iterate over a list of rules or examples
rules_template_str = """
You are a RAG assistant. Follow these rules:
{% for rule in rules %}
- {{ rule }}
{% endfor %}

Context: {{ context }}
Question: {{ question }}
"""
# Dynamically include any number of rules at runtime
# rules=["Do not fabricate", "Be concise", "Use supplied context"]
🎯

PromptTemplate + Jinja2 vs ChatPromptTemplate + Jinja2: PromptTemplate + Jinja is a dynamic single text prompt (one string). ChatPromptTemplate + Jinja is a dynamic role-based chat prompt with separate system/human/assistant messages, variables, if/else and loops. For production RAG systems use ChatPromptTemplate — it's the more advanced and structured option.

python · load prompt from JSON 
import json
from langchain.prompts import ChatPromptTemplate

def load_prompt(prompt_name: str, prompts_file: str = "prompts.json"):
    """Load a named prompt from JSON file."""
    with open(prompts_file) as f:
        prompts = json.load(f)

    p = prompts[prompt_name]
    print(ff"Loaded: {prompt_name} (version {p['version']})")

    return ChatPromptTemplate.from_messages([
        ("system", p["system"]),
        ("human",   p["human"])
    ])

# Usage
rag_prompt = load_prompt("rag_qa_prompt")
chain = rag_prompt | llm | StrOutputParser()

# To update a prompt: edit the JSON file, bump the version number
# No code changes needed — just update the JSON

16 — Self-Check

Quiz — Test Your Understanding

📝 Class 37 Concept Check

1. What is HyDE and why does it improve retrieval? What is its key limitation?

▶ Show Answer
HyDE (Hypothetical Document Embeddings) works by: (1) taking the user's query, (2) asking an LLM to generate a hypothetical answer (not the final answer — a placeholder that looks like what a real document might say), (3) embedding that hypothetical answer, and (4) using that embedding to search the vector database. It improves retrieval because a full hypothetical answer is often semantically closer to actual document content than the short user query — it uses document-like vocabulary. Key limitation: it's experimental and adds latency (an extra LLM call before retrieval). If the LLM has poor domain knowledge, the hypothetical answer won't be helpful. Always POC and test before committing.

2. What is the difference between HyDE and Multi-Query Retriever? And are either of them retrieval mechanisms?

▶ Show Answer
HyDE generates multiple hypothetical answers and uses answer embeddings to search. Multi-Query generates multiple rephrasings of the original query, runs retrieval for each, then merges and deduplicates results. Key difference: HyDE embeds answers; Multi-Query embeds rephrased queries. HyDE aims for better semantic matching; Multi-Query aims for better recall (wider coverage). Neither is a retrieval mechanism — both are query transformation techniques. They happen before the retriever, modifying the query. Parent Document and Sentence Window retrievers are actual retrieval mechanisms — they change how documents are searched and returned inside the vector database.

3. Explain the RRF formula and what the constant k does.

▶ Show Answer
RRF score = Σ 1/(k + rank_i(d)) summed over all retrievers. For each retriever, a document gets a score based on its rank position (1 = top). A document ranked highly in multiple lists gets a higher combined score than one appearing in only one list. The constant k (typically 60) is added to prevent the score from becoming infinitely high when rank = 0 (which would happen if 1/rank was used). Without k, rank 1 would always win regardless of its scores in other lists. k smooths the score distribution, giving more balanced fusion. Documents that consistently appear in the top ranks across BM25 AND dense retrieval score highest.

4. Walk through the MMR formula and explain what lambda controls.

▶ Show Answer
MMR(d) = λ · sim(d, q) − (1−λ) · max_sim(d, S). The first term (λ · sim(d, q)) is the relevance score — how similar candidate document d is to the query q. The second term ((1−λ) · max_sim(d, S)) is the diversity penalty — how similar d is to documents already selected (S). Lambda (0–1) controls the balance: λ=1.0 → pure relevance (same as cosine search, ignores diversity). λ=0.0 → pure diversity (maximises difference from already selected docs). λ=0.5 → equal weight to relevance and diversity. In Sunny's example: normal similarity picked Doc A + Doc B (both highly relevant but similar content). MMR picked Doc A + Doc E (Doc E is less relevant but provides different information → better context diversity for the LLM).

5. What is Jinja conditional prompting and give a real-world use case.

▶ Show Answer
Jinja is a Python templating engine that allows if/else conditions and for loops inside LangChain prompt templates (using template_format="jinja2"). Instead of writing separate prompt classes for each use case, you write one template with conditional blocks that activate based on runtime variables. Real-world use case Sunny gave: a customer support system with different user types — if user_type == "premium": include escalation options and priority handling instructions; else: use standard support guidance. Only the relevant prompt section is sent to the LLM — not the entire template. Sunny said he's used this "a lot in real-time projects." ChatPromptTemplate + Jinja2 is the recommended production version (structured system/human messages + Jinja conditions + loops).

6. What are the 3 recommended ways to manage prompts in production and which did Sunny recommend most?

▶ Show Answer
Three methods: (1) JSON file — store all prompts in a JSON file (name, version, system, human, last_updated fields). In-house, version-controlled in Git, no external dependency. Works everywhere. (2) LangSmith Hub — cloud-hosted prompt registry with collaboration and version history. Use when company policy allows external tools. (3) Database (DynamoDB or any DB) — prompts stored as JSON in your own database, loaded at runtime. Enterprise-scale, fully in-house. Sunny most recommended JSON files: "To maintain the prompt in the JSON format, it's a quite good idea. We can maintain it up to the level, and we can maintain so many things inside one JSON file." He used this as his default in most real-time projects.
