## File: retriever_advanced.ipynb
## Data: Llama 2 research paper PDF → ChromaDB

import os
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma
from langchain.retrievers import HypotheticalDocumentEmbedder
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
import shutil

load_dotenv()
embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")
llm             = ChatOpenAI(model="gpt-4.1-mini")

DATA_DIR           = "./data"
VECTOR_STORE_DIR   = "./data/vector_store"
PDF_PATH           = "./data/llama2_research_paper.pdf"

# ── Build ChromaDB vector store ───────────────────────────────────
rebuild_index = True
if rebuild_index:
    if os.path.exists(VECTOR_STORE_DIR):
        shutil.rmtree(VECTOR_STORE_DIR)
    pages = PyPDFLoader(PDF_PATH).load()
    for i, page in enumerate(pages):
        page.metadata["page_number"] = i + 1
        page.metadata["source"]      = "llama2_research_paper.pdf"
    chunks = RecursiveCharacterTextSplitter(
        chunk_size=1000, chunk_overlap=200
    ).split_documents(pages)
    vector_store = Chroma.from_documents(
        documents          = chunks,
        embedding          = embedding_model,
        collection_name    = "llama2_collection",
        persist_directory  = VECTOR_STORE_DIR
    )
    print("✓ Vector store created")
else:
    vector_store = Chroma(
        collection_name   = "llama2_collection",
        embedding_function= embedding_model,
        persist_directory = VECTOR_STORE_DIR
    )

# ── Simple baseline retrieval (no HyDE) ──────────────────────────
query           = "How does Llama 2 improve safety?"
baseline_results = vector_store.similarity_search(query, k=4)
print(ff"Baseline: {len(baseline_results)} docs retrieved")

# ── HyDE Setup ───────────────────────────────────────────────────
# HypotheticalDocumentEmbedder.from_llm() — LangChain's built-in class
# prompt_key options:
#   "web_search" → if LLM doesn't know, it may incorporate web-search-like behavior
#   "sci_fact"   → generate a scientific hypothesis-style hypothetical doc
#   "fiqa"       → finance-domain focused
#   "arguana"    → argument-style hypothetical doc
#   "trec_news"  → news article style
hyde_embedder = HypotheticalDocumentEmbedder.from_llm(
    llm        = llm,
    embeddings = embedding_model,
    prompt_key = "web_search"   # style of hypothetical doc generated
)
print("✓ HyDE embedding model created")

# ── Generate and inspect the hypothetical document ────────────────
hypo_doc = hyde_embedder.llm_chain.invoke(query)
print("\n--- Hypothetical Document ---")
print(hypo_doc[:500])
# → LLM generates a passage that looks like it came from a paper
# → This hypothetical text is then embedded and used for search

# ── Use HyDE embedder for retrieval ──────────────────────────────
# Embed using HyDE (it internally generates hypothetical doc, then embeds it)
hyde_query_vector = hyde_embedder.embed_query(query)

# Search using the hypothetical doc's embedding
hyde_results = vector_store.similarity_search_by_vector(
    embedding = hyde_query_vector,
    k         = 4
)
print(ff"\nHyDE: {len(hyde_results)} docs retrieved")
for i, doc in enumerate(hyde_results):
    print(ff"[{i+1}] Page {doc.metadata.get('page_number')}: {doc.page_content[:120]}...")

# ── Compare baseline vs HyDE results ─────────────────────────────
baseline_pages = [d.metadata.get('page_number') for d in baseline_results]
hyde_pages     = [d.metadata.get('page_number') for d in hyde_results]
print(ff"\nBaseline pages: {baseline_pages}")
print(ff"HyDE pages:     {hyde_pages}")
# You may get different pages — HyDE uses document-like vocabulary
# which may match real document chunks better than the raw question
🌐

The web_search prompt key: When the LLM's training data doesn't have the answer, specifying prompt_key="web_search" tells HyDE's internal prompt to generate a document as if the answer was retrieved from a web search. It's a style of hypothetical document generation — not an actual web search call. Sunny noted: "If model is not having that particular information, we are going to be pass that information to the internet to get the hypothetical document."

04 — Practical 2

Sentence Window Retriever

Concept — Sunny's Blackboard Example

Sunny wrote a 4-sentence paragraph on the blackboard and walked through exactly how window size works:

Sunny's Example — 4-sentence paragraph with window_size=1
S1: "My name is Sunny."
S2: "Sunny is an AI mentor." ← matched sentence (retrieved by similarity search)
S3: "He knows about deep learning also."
S4: "He knows about data engineering."
With window_size=1: return 1 sentence each side → context returned = S1 + S2 + S3
With window_size=2: return 2 sentences each side → context returned = S1 + S2 + S3 + S4 (full paragraph)
The matched sentence is always included. window_size controls how many surrounding sentences are added.

Sentence Window Code

python · sentence window retriever 
import re
from langchain.schema import Document
from langchain_chroma import Chroma

# ── Step 1: Split documents into individual sentences ─────────────
def split_into_sentences(documents, window_size=2):
    """
    Converts documents into sentence-level chunks with surrounding context window.
    Each sentence becomes a Document with:
    - page_content = the single sentence (searchable)
    - metadata["sentence_window"] = the surrounding context window
    - metadata["sentence_index"] = position in the page
    """
    sentence_docs = []
    for doc in documents:
        # Split on sentence boundaries: period, question mark, exclamation
        sentences = re.split(r'(?<=[.!?])\s+', doc.page_content.strip())
        sentences = [s.strip() for s in sentences if s.strip()]
        for i, sentence in enumerate(sentences):
            # Build surrounding context window
            start = max(0, i - window_size)
            end   = min(len(sentences), i + window_size + 1)
            window_text = " ".join(sentences[start:end])
            sentence_doc = Document(
                page_content = sentence,     # what's stored in vector DB (searchable)
                metadata     = {
                    **doc.metadata,
                    "sentence_window": window_text,   # returned to LLM
                    "sentence_index":  i,
                    "window_size":     window_size
                }
            )
            sentence_docs.append(sentence_doc)
    return sentence_docs

WINDOW_SIZE = 2
sentence_documents = split_into_sentences(pages, window_size=WINDOW_SIZE)
print(ff"Total sentence documents: {len(sentence_documents)}")

# ── Inspect a document ───────────────────────────────────────────
ex = sentence_documents[1]
print(f"\nSearchable sentence:\n{ex.page_content}")
print(ff"\nSurrounding window:\n{ex.metadata['sentence_window']}")
# → Searchable sentence: one sentence stored in vector DB
# → Surrounding window: includes window_size sentences before and after

# ── Step 2: Create sentence-level vector store ────────────────────
SW_COLLECTION_DIR = "./data/sentence_window_store"
sentence_store = Chroma.from_documents(
    documents         = sentence_documents,
    embedding         = embedding_model,
    collection_name   = "sentence_window_collection",
    persist_directory = SW_COLLECTION_DIR
)
print("✓ Sentence-level vector store created")

# ── Step 3: Create retriever ─────────────────────────────────────
sentence_retriever = sentence_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 4}
)

# ── Step 4: Query and get window context ─────────────────────────
query   = "What safety measures does Llama 2 use?"
matched = sentence_retriever.invoke(query)

print(ff"\nRetrieved {len(matched)} sentence matches:")
for i, doc in enumerate(matched):
    print(ff"\nMatch {i+1} — Page {doc.metadata.get('page_number','?')}, "
          f"Sentence #{doc.metadata.get('sentence_index')}")
    print(ff"  Matched:  {doc.page_content[:80]}...")
    print(ff"  Window:   {doc.metadata.get('sentence_window','')[:150]}...")

# ── Step 5: Use window content (not raw sentence) for RAG ────────
# Replace page_content with the window when sending to LLM
window_docs = []
for doc in matched:
    window_content = doc.metadata.get("sentence_window", doc.page_content)
    window_docs.append(Document(
        page_content = window_content,
        metadata     = doc.metadata
    ))

Parent Document Retriever

The key insight Sunny explained: Parent Document Retriever uses two separate stores — a vector store for small child chunks (for precise similarity search) and a docstore for large parent chunks (for rich context return).

Parent Document Retriever Code

python · ParentDocumentRetriever 
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_chroma import Chroma
from langchain.text_splitter import RecursiveCharacterTextSplitter

# ── Step 1: Define parent and child splitters ─────────────────────
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size    = 2000,  # large chunks → returned to LLM
    chunk_overlap = 200
)
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size    = 300,   # small chunks → searchable in vector DB
    chunk_overlap = 50
)

# ── Step 2: Create child vector store (ChromaDB) ──────────────────
PDR_STORE_DIR = "./data/parent_doc_child_store"
child_vector_store = Chroma(
    collection_name   = "parent_collection",
    embedding_function= embedding_model,
    persist_directory = PDR_STORE_DIR
)

# ── Step 3: Create parent docstore (in-memory) ───────────────────
# Parents are NOT stored in vector DB — they're stored in a simple key-value store
parent_docstore = InMemoryStore()

# ── Step 4: Create ParentDocumentRetriever ────────────────────────
parent_retriever = ParentDocumentRetriever(
    vectorstore      = child_vector_store,   # ChromaDB: stores child chunks
    docstore         = parent_docstore,      # InMemoryStore: stores parent docs
    child_splitter   = child_splitter,
    parent_splitter  = parent_splitter,
)

# ── Step 5: Add documents ────────────────────────────────────────
# Automatically: splits into parents + children, embeds children, stores both
parent_retriever.add_documents(pages)
print("✓ Parent document retriever created")

# ── Check child count ─────────────────────────────────────────────
child_count = child_vector_store._collection.count()
print(ff"Total child chunks in vector DB: {child_count}")  # 856

# ── Step 6: Retrieve — returns parent documents ───────────────────
query   = "What is the safety evaluation methodology used for Llama 2?"
results = parent_retriever.invoke(query)

print(ff"\nRetrieved {len(results)} parent documents:")
for i, doc in enumerate(results):
    print(ff"[{i+1}] Length: {len(doc.page_content)} chars | Page: {doc.metadata.get('page_number')}")
    print(ff"      {doc.page_content[:150]}...")

# ── Step 7: Compare child vs parent length ───────────────────────
child_results = child_vector_store.similarity_search(query, k=4)
parent_results= results

print("\n--- Size Comparison ---")
print(ff"Avg child length:  {sum(len(d.page_content) for d in child_results) // len(child_results)} chars")
print(ff"Avg parent length: {sum(len(d.page_content) for d in parent_results) // len(parent_results)} chars")
# Child: ~300 chars (precise match)  |  Parent: ~2000 chars (rich context)

# ── Inspect child-to-parent relationship ─────────────────────────
for child in child_results[:2]:
    parent_id     = child.metadata.get("doc_id")  # ID linking child to parent
    parent_docs   = parent_docstore.mget([parent_id])
    print(ff"Child: {child.page_content[:60]}...")
    print(ff"ParentID: {parent_id}")
    if parent_docs[0]:
        print(ff"Parent: {parent_docs[0].page_content[:100]}...\n")
"This is the overall flow: we have the original document, then we have a parent splitter — large parent chunks. Then we have a child splitter — small child chunks. Now we are creating embedding for the child chunk, storing child chunk into the vector DB, and storing parent chunk in the docstore. Then whenever we have a user query, it will perform the embedding, search the child chunk, find out the parent ID from the metadata, fetch the corresponding parent document from the document store, and then return the larger context."

Contextual Compression Retriever

After the cross-encoder reranking use (from Class 36 Part 2), Sunny showed the LLM-based version of contextual compression — using an LLM to extract only the relevant parts of retrieved chunks before sending to the final LLM.

LLMChainExtractor Code

python · ContextualCompressionRetriever with LLMChainExtractor 
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import (
    LLMChainExtractor,   # extracts only relevant sentences from a chunk
    LLMChainFilter       # filters out entirely irrelevant chunks
)

# ── Base retriever ────────────────────────────────────────────────
base_retriever = vector_store.as_retriever(
    search_type   = "similarity",
    search_kwargs = {"k": 6}   # retrieve 6 candidates for compression
)

# ── LLMChainExtractor — trims each chunk to relevant sentences ────
# Uses an LLM to extract only the parts of each chunk relevant to the query
extractor = LLMChainExtractor.from_llm(llm)

contextual_compression_retriever = ContextualCompressionRetriever(
    base_compressor = extractor,
    base_retriever  = base_retriever
)

# ── Retrieve with compression ─────────────────────────────────────
query = "What is the RLHF training method used in Llama 2?"

# Without compression: 6 full chunks (each ~1000 chars)
raw = base_retriever.invoke(query)
print(ff"Without compression: {sum(len(d.page_content) for d in raw)} total chars")

# With compression: LLM extracts relevant sentences from each chunk
compressed = contextual_compression_retriever.invoke(query)
print(ff"With compression:    {sum(len(d.page_content) for d in compressed)} total chars")
# Typically 30-70% reduction in tokens while keeping relevant information

for i, doc in enumerate(compressed):
    print(ff"\n[{i+1}] Compressed chunk ({len(doc.page_content)} chars):")
    print(ff"     {doc.page_content}")

# ── LLMChainFilter variant ────────────────────────────────────────
# Instead of extracting relevant parts, it filters OUT entirely irrelevant chunks
llm_filter = LLMChainFilter.from_llm(llm)
filtering_retriever = ContextualCompressionRetriever(
    base_compressor = llm_filter,
    base_retriever  = base_retriever
)
filtered = filtering_retriever.invoke(query)
print(ff"\nFiltered chunks: {len(filtered)} (from 6 base candidates)")

"Multi-hop retriever — there is no such direct class in LangChain to implement this. It is one of the techniques which was introduced by Meta. This technique, you can orchestrate using LangGraph itself. I have done it over here in the notebook, but as of now I'm not going through this entire process. 🕸

Multi-Hop Retriever in brief: Multi-hop retrieval answers complex questions that can't be answered from a single retrieval step. The system retrieves initial documents, extracts intermediate facts, then uses those facts to run a second (or third) retrieval. Example: "Who trained the model that uses GRPO for preference alignment?" requires (1) find which model uses GRPO → (2) find who trained that model. Multi-hop is covered in the LangGraph/Agentic chapter.

import structlog
import logging
from pathlib import Path

def setup_logger(
    log_file: str = "logs/app.log",
    level: int    = logging.INFO
):
    """Configure structlog for both console and file output."""
    Path(log_file).parent.mkdir(parents=True, exist_ok=True)

    logging.basicConfig(
        level    = level,
        format   = "%(asctime)s | %(levelname)s | %(message)s",
        handlers = [
            logging.FileHandler(log_file),
            logging.StreamHandler()   # also prints to console
        ]
    )

    structlog.configure(
        processors = [
            structlog.processors.TimeStamper(fmt="iso"),
            structlog.stdlib.PositionalArgumentsFormatter(),
            structlog.processors.StackInfoRenderer(),
            structlog.processors.format_exc_info,
            structlog.stdlib.ProcessorFormatter.wrap_for_formatter,
        ],
        wrapper_class = structlog.stdlib.BoundLogger,
        logger_factory= structlog.stdlib.LoggerFactory(),
    )
    return structlog.get_logger()

## custom_exception.py — custom exception classes for structured error handling

class RAGException(Exception):
    """Base exception for all RAG pipeline errors."""
    def __init__(self, message: str, details: dict = None):
        super().__init__(message)
        self.details = details or {}

class ParseException(RAGException):
    """Raised when PDF parsing fails."""
    pass

class EmbeddingException(RAGException):
    """Raised when embedding generation fails."""
    pass

class RetrievalException(RAGException):
    """Raised when vector store retrieval fails."""
    pass

class GenerationException(RAGException):
    """Raised when LLM generation fails."""
    pass

logger = setup_logger(log_file="logs/parsing.log")

class MultimodalPDFParser:
    """Parses complex PDFs: extracts text, tables, and images."""

    def __init__(self, pdf_path: str, output_dir: str = "./data/parsed"):
        self.pdf_path   = pdf_path
        self.output_dir = output_dir
        os.makedirs(output_dir, exist_ok=True)
        logger.info("Parser initialised", pdf=pdf_path, output=output_dir)

    def parse(self) -> dict:
        try:
            logger.info("Starting full PDF parse")
            text_content   = self._extract_text()
            table_content  = self._extract_tables()
            image_content  = self._extract_images()
            logger.info("Parse complete",
                         pages=len(text_content),
                         tables=len(table_content),
                         images=len(image_content))
            return {
                "text":   text_content,
                "tables": table_content,
                "images": image_content,
            }
        except Exception as e:
            logger.error("Parse failed", error=str(e))
            raise ParseException(f"Failed to parse {self.pdf_path}",
                                 details={"error": str(e)})

    def _extract_text(self):
        # PyMuPDF text extraction (from Class 30 complex parser)
        doc   = fitz.open(self.pdf_path)
        pages = []
        for page in doc:
            pages.append({"page": page.number + 1, "text": page.get_text()})
        return pages

Quiz — Test Your Understanding

📝 Class 38 Concept Check

1. What does the HyDE prompt_key="web_search" parameter actually do? Does it make a real web search?

▶ Show Answer
No — it does NOT make an actual web search. The prompt_key parameter controls the style/format of the hypothetical document that the LLM generates. "web_search" tells the internal HyDE prompt to generate a document that looks like a web search result — authoritative, factual, document-like vocabulary. If the LLM's training data doesn't know the answer, it still generates a hypothetical-sounding passage based on reasoning. Other prompt_key options include "sci_fact" (scientific hypothesis style), "fiqa" (finance domain), "trec_news" (news article style). The generated document is then embedded for similarity search — no internet connection involved.

2. What are the two data stores in Parent Document Retriever and what is stored in each?

▶ Show Answer
Store 1 — Child Vector Store (ChromaDB or any VDB): stores small child chunks (e.g. chunk_size=300). These are embedded and indexed for fast similarity search. Each child document's metadata includes a parent_id linking it to its parent. Store 2 — Parent Docstore (InMemoryStore or persistent): stores large parent chunks (e.g. chunk_size=2000). NOT embedded — just stored as key-value pairs by parent_id. When a query comes in: embed query → search child VDB → find matching child chunks → look up their parent_id → retrieve full parent document from docstore → return large context to LLM.

3. Using Sunny's 4-sentence paragraph example, explain how window_size=1 works in Sentence Window Retriever.

▶ Show Answer
Paragraph: S1="My name is Sunny." S2="Sunny is an AI mentor." S3="He knows about deep learning." S4="He knows about data engineering." If S2 is the matched sentence (retrieved by similarity search) and window_size=1: return 1 sentence to the left (S1) and 1 sentence to the right (S3). The returned context window = S1 + S2 + S3. The vector database only stores single sentences (for precise matching), but what gets returned to the LLM is the larger window. With window_size=2 on S2: return S1 + S2 + S3 + S4 (the full paragraph). Increasing window_size gives more context but also more noise.

4. What is the difference between LLMChainExtractor and LLMChainFilter in contextual compression?

▶ Show Answer
LLMChainExtractor: Takes each retrieved chunk and asks an LLM to extract only the sentences/phrases relevant to the user query. The chunk is not discarded — it's trimmed to its relevant portions. A 1000-char chunk about RLHF training might be reduced to 200 chars containing only the RLHF-relevant sentences. LLMChainFilter: Takes each retrieved chunk and asks an LLM to decide: is this chunk relevant to the query at all? If yes, keep the whole chunk. If no, discard the entire chunk. It filters at the chunk level, not the sentence level. Both reduce tokens sent to the final LLM. Extractor preserves partial content; Filter does whole-or-nothing decisions.

5. Why does Python need a setup.py, pyproject.toml, or sys.path hack when importing between modules in a project?

▶ Show Answer
When parsing.py (inside src/) tries to import from logger/ and exceptions/, Python can't find those modules without help — because Python only searches sys.path (the list of directories it knows about). The project root isn't automatically in sys.path. Solutions: (1) sys.path hack — manually insert the project root into sys.path at the top of each file (quick, not professional). (2) pyproject.toml + pip install -e . — defines the project as a proper Python package, so uv/pip installs it into the virtual environment, making all directories importable. (3) setup.py + pip install -e . — older but equivalent approach. The -e (editable) flag means changes to code are reflected immediately without reinstalling. Each virtual environment needs this done once per project.
