03 — Foundations

7 Foundational Definitions

Sunny spent the first half of class writing and explaining these 7 terms on the blackboard. He said: "If you know these 7 definitions, your fundamentals of Agent and Agentic AI will be clear."

1. AI Assistant (Simple)

Definition

A system with an LLM at its core. User passes input → LLM generates output based on its training knowledge.

No external knowledge source. No tools. No memory beyond the context window. Answer comes entirely from what the model was trained on.
Q: "What is Tesla?" → A: "Tesla is an EV company." ← from model training, not from any external DB

2. RAG-Based Assistant

Definition

An AI assistant that retrieves relevant external knowledge and uses that information to generate grounded responses.

User query → Vector DB retrieval → context → LLM → grounded output. Connects to an external knowledge base maintained from a data source. Reduces hallucination by grounding answers in retrieved facts.
🔑

Important: "A RAG-based system is NOT an Agentic system." RAG is knowledge retrieval — the LLM receives context and generates an answer. There is no autonomous decision-making, no tool calling, no iterative planning. RAG can be a component inside an Agentic system, but by itself it is not one.

3. What is an Agent?

Definition

An AI system that perceives its environment, reasons about it, takes actions (uses tools), observes results, and adapts iteratively to achieve a goal.

Think — LLM reasons about the input and plans what to do
Act — Takes an action (calls a tool, queries a DB, writes code)
Observe — Reviews the result of the action
Adapt — Updates its plan and repeats if needed (iterative refinement)
"An AI agent is an autonomous system that can perceive its environment, make decisions, take actions using tools or APIs, and observe the outcome. Then it keeps on repeating this think-act-observe loop until it generates the final output. A normal AI assistant just generates; an agent also acts and observes."

4. Agentic AI

Definition

The broader paradigm of AI systems designed to act autonomously, use tools, manage state and memory, and pursue goals across multiple steps.

Agentic AI is the umbrella term. Whether you have a single agent or a network of multiple agents — if it has autonomous decision-making, iterative execution, and tool use — it falls under Agentic AI.

5. Multi-Agent System

Tesla Investment Research Report — Multi-Agent Example
"Analyse Tesla and prepare a detailed investment research report."
One Supervisor Agent receives the task → delegates to 4 specialised agents:
Research Agent

Collects background info, history, products, market position

Financial Agent

Analyses financials: revenue, P&L, debt, growth metrics

Risk Agent

Evaluates regulatory, competitive, market, and execution risks

Market Agent

Analyses market sentiment, competitor landscape, industry trends

Supervisor Agent combines all outputs → final investment research report ✓

Instead of one general agent doing everything, a Multi-Agent system uses multiple specialised agents collaborating — each an expert in its own domain, operating independently, sharing results toward a common goal.

6. Deep Agentic System

One-line Definition

A large, long-running system — for complex to very complex problems — with extensive planning, multiple task decomposition, multiple tools, sub-agents, and a repeating process until final deliverables are produced.

→ Extensive planning phase
→ Task decomposition (complex → sub-tasks)
→ Multiple tools called in sequence
→ Multiple sub-agents may run
→ Iterative refinement until done
→ Long task execution (minutes to hours)
"Deep agent is not a different paradigm. It's not some magic. It's just a variant: large and long-running. If I define it in one term — it is a large and a long-running system for the complex problem. Both a single agent and a multi-agent system can be a deep agent. The word 'deep' just means it's running in-depth, for a longer time, with extensive planning. That's it."

7. When and Why to Use an Agent

✅ Use an Agent when…

  • → Task requires multiple sequential steps
  • → External tools / APIs need to be called
  • → Decision-making is dynamic, not pre-coded
  • → Output of one step feeds input of the next
  • → Human-in-the-loop checks are needed
  • → Long-running autonomous workflows

✗ Don't use an Agent when…

  • → Task is a simple single-turn Q&A
  • → Fixed deterministic logic is sufficient
  • → Latency is critical (agents are slower)
  • → No external data or tool access needed
  • → LLM knowledge alone is sufficient

05 — Architecture

The Agentic Flow

Every Agentic system — regardless of which framework you use — follows this core loop:

Universal Agentic Flow — Sunny's Blackboard
→

Input

User query, task description, or trigger event arrives at the system

1

LLM Reasoning / Decision

The LLM thinks about the input. What does it need to do? It reasons and takes a decision on the approach.

2

Planning (if necessary)

For complex tasks, the LLM decomposes the goal into sub-tasks and creates a plan of action.

3

Take Appropriate Action

Execute the plan: call a tool (web search, code executor, database query, API), delegate to a sub-agent, or generate text.

4

Observe the Result

Examine the output of the action. Did it succeed? Is the result correct? Does it move toward the goal?

5

Adapt Based on Feedback (Iterative Refinement)

Update the plan. If the task is not complete, repeat steps 1–4 with updated context. Also called feedback-driven adaption or iterative refinement.

✓

Final Output

When the goal is achieved or a stopping condition is met, the final answer or deliverable is produced.

↻ Repeat steps 1–5 until final output is ready (iterative refinement loop)

Deterministic Flow (Workflow)

Fixed, pre-coded sequence of steps. LLM role is guided by explicit program logic.

The flow is pre-determined by the developer. Step A always leads to step B, then step C. No dynamic decision-making — the path is fixed. Also called: deterministic agent, workflow. Example: a document processing pipeline that always runs: parse → chunk → embed → store → retrieve → generate. LangGraph represents this as nodes and edges with fixed connections.

Dynamic Flow (True Agent)

LLM dynamically decides what to do next at each step — not pre-coded.

The LLM reasons about the current state and decides: which tool to call, whether to retry, whether to delegate, when to stop. The path is not fixed — it emerges from the LLM's reasoning. This is the "true" Agentic system. Much harder to debug (non-deterministic) but far more flexible for open-ended tasks.

📐

Three implementation paths: (1) Pure Python — from scratch, no framework, maximum control but high development effort. (2) LangGraph — low-level control with graph orchestration, preferred for production. (3) High-level frameworks (LangChain agent classes, Google ADK, OpenAI Agents SDK) — fast to build, but higher abstraction = less visibility into what's happening under the hood.

06 — What You Need to Know

Practical Prerequisites for Agentic Development

Sunny listed these on the blackboard as things every Agentic AI developer needs to understand:

Pydantic + Type Hints

Schema validation for agent inputs/outputs and tool parameters. Essential for structured communication between agents.

JSON Schema

How to define tool schemas that the LLM uses to understand what each tool accepts and returns.

Async Python

Concurrency for running multiple tool calls or agent actions in parallel. Reduces latency in multi-step flows.

Structured Output

Forcing the LLM to output valid JSON or typed data instead of free text. Critical for agents that chain output to next steps.

Tool Calling / Tool Engineering

Defining tools (functions, APIs, DBs), binding them to the LLM, and handling tool call/response cycles.

Memory Management

Short-term (within session), long-term (across sessions), persistent (stored in DB), transient. Agents need memory to stay on task.

State Management

Tracking what the agent has done, what it knows, and what step it's on. LangGraph's StateGraph is built around this concept.

Context Engineering

Managing what information goes into the LLM's context window efficiently — avoiding token waste while keeping enough context for the agent to reason correctly.

MCP & A2A Protocol

Model Context Protocol (tool standardisation) and Agent-to-Agent protocols for multi-agent communication. Covered later in the module.

Evaluation & Testing

How to test an Agentic system — does it reliably reach the goal? Metrics: task completion rate, tool call accuracy, latency, safety.

Observability

Tracing every agent step, tool call, and LLM interaction. LangSmith, LangFuse, OpenTelemetry for production monitoring.

Guardrails & Security

Preventing agents from taking harmful actions, bypassing safety, leaking data, or going off-course. Prompt-level and system-level safeguards.

Caching

Caching LLM responses, tool results, and embeddings to reduce cost and latency in repeated agentic flows.

Prompt Engineering

System prompts for agents are more complex — they define the agent's persona, capabilities, constraints, and output format.

07 — Primary Framework

LangGraph — Introduction

Why LangGraph?

"If you wanted to build an agent from scratch, if you wanted to build an agent with low-level control, which framework will you use? LangGraph. LangGraph gives you the control where you can develop the framework from the starting. Inside the LangGraph, you will have the low-level control over the program. If you use LangChain's agent classes directly, it's high-level abstraction — you won't see what's happening under the hood."

LangChain Agent Classes (high-level)

Pre-coded classes for implementing basic React-style agents. Fast to set up but limited control. You can't see what's happening inside. For POC and simple flows.

LangGraph (low-level control)

Graph-based framework for building Agentic systems from scratch. You define every node, edge, state, and condition. Full visibility into every step. Preferred for production systems.

LangGraph Core Concepts

StateGraph

The main graph class. Contains nodes (functions), edges (connections), and maintains state at each step. Everything flows through this.

Node

A Python function that does one unit of work — calls an LLM, executes a tool, processes data. Nodes receive and return state.

Edge

Connection between nodes. Can be fixed (always go from A to B) or conditional (go to B or C based on state value).

State

A TypedDict (Pydantic model) that flows through the graph. Each node can read from and write to it. The central data structure.

START / END

Special sentinel nodes marking the entry and exit points of the graph.

Conditional Edge

A routing function that decides which node to go to next based on the current state — enables dynamic decision-making.

Checkpointer

Persistent state storage — saves graph state after each step. Enables resumability, fault tolerance, and human-in-the-loop pauses.

SubGraph

Nested graph within a node — enables modular multi-agent systems where each agent is its own graph.

Graph API vs Functional API

Two styles: Graph API (explicit node/edge definition) and Functional API (decorator-based, more Pythonic). Both produce the same graph.

LangGraph + LangChain — How They Work Together

"Along with LangGraph, guys, we can use LangChain in our application. LangChain provides us the embedding model, the chat model, the vector database integration, the component chaining capability, the output parser. So LangChain supports us in so many ways. LangGraph provides us the orchestration — how the flow will work. LangChain provides the actual AI components that nodes in that flow will use."

## Note: Sunny found that the simple `Graph` import was removed from LangGraph.
## Everything now uses StateGraph. This is the corrected working version.

from langgraph.graph import StateGraph, START, END
from typing import TypedDict

# ── 1. Define the State ───────────────────────────────────────────
# State flows through every node in the graph
class GraphState(TypedDict):
    input_data:  str   # input passed into the graph
    output_data: str   # output collected at the end

# ── 2. Define nodes (Python functions) ───────────────────────────
# Each node receives state and returns updated state dict
def function_1(state: GraphState) -> dict:
    print("Executing function_1...")
    result = state["input_data"] + " → processed by function_1"
    return {"output_data": result}

def function_2(state: GraphState) -> dict:
    print("Executing function_2...")
    result = state["output_data"] + " → processed by function_2"
    return {"output_data": result}

def function_3(state: GraphState) -> dict:
    print("Executing function_3...")
    result = state["output_data"] + " → processed by function_3"
    return {"output_data": result}

# ── 3. Build the Graph ────────────────────────────────────────────
workflow = StateGraph(GraphState)

# Add nodes (name → function mapping)
workflow.add_node("node_1", function_1)
workflow.add_node("node_2", function_2)
workflow.add_node("node_3", function_3)

# Add edges (connections between nodes)
workflow.add_edge(START, "node_1")    # entry point
workflow.add_edge("node_1", "node_2")
workflow.add_edge("node_2", "node_3")
workflow.add_edge("node_3", END)      # exit point

# ── 4. Compile the graph ──────────────────────────────────────────
app = workflow.compile()

# ── 5. Run the graph ──────────────────────────────────────────────
result = app.invoke({"input_data": "Hello from user", "output_data": ""})
print(ff"\nFinal output: {result['output_data']}")
# → Hello from user → processed by function_1 → processed by function_2 → processed by function_3

# ── What LangGraph adds vs pure function calls ────────────────────
# Pure Python:  function_1(input) → function_2(output1) → function_3(output2)
# LangGraph:    orchestrated graph with state, checkpointing, conditional routing,
#               parallelism, sub-graphs, human-in-the-loop, streaming, and observability
# The REAL power comes in next classes with conditional edges, memory, and tool calling

08 — Tool Landscape

LangChain Ecosystem Map

Sunny walked through the full LangChain product family during the session to clarify what each tool does:

LangChain

The core framework. Provides: chat models, embedding models, vector store integrations, prompt templates, LCEL chaining, output parsers. Used alongside LangGraph to build the actual AI logic inside each node.

LangGraph

Orchestration framework built on LangChain. Defines agent workflows as graphs (nodes + edges + state). Low-level control, production-grade, built-in checkpointing and fault tolerance.

LangSmith

Observability and tracing platform. See every LLM call, tool call, token count, latency, and agent step. Like CloudWatch or MLflow — but for LangChain/LangGraph apps. Debugging, monitoring, testing.

LangFuse

Alternative observability platform (open-source). Tracing, monitoring, debugging — similar to LangSmith. Can be self-hosted. Good for teams that want full control of their telemetry.

LangFlow

Visual workflow builder. Drag-and-drop interface to build and visualise LangChain/LangGraph flows. Good for demos and no-code prototyping. Doesn't replace code for production.

LangGraph Studio

Visual debugger for LangGraph specifically. See graph nodes connected, run the graph interactively, inspect execution at each node. Like a visual IDE for Agentic flows. Comes with LangGraph Desktop.

11 — Self-Check

Quiz — Test Your Understanding

📝 Class 40 Concept Check

1. What are the 3 main levels of AI application, and what makes each different?

▶ Show Answer
Level 1 — Simple AI Assistant: An LLM receives input and generates output based purely on its training knowledge. No external data, no tools, no memory beyond context. Example: asking "What is Tesla?" and getting an answer from the model's training data. Level 2 — RAG-Based Assistant: LLM retrieves relevant external context from a knowledge base (vector DB) and uses it to generate grounded responses. Still generates, doesn't act autonomously. Level 3 — Agentic System: LLM reasons, plans, calls tools, observes outcomes, adapts iteratively. Has autonomous decision-making. Can be single-agent (mono-agentic), multi-agent, or deep (large, long-running, complex tasks).

2. Walk through the 5 steps of the universal Agentic flow. What happens at each step?

▶ Show Answer
Step 1 — Input: User query or task arrives. Step 2 — LLM Reasoning/Decision: LLM thinks about the input, decides what needs to be done, selects an approach. Step 3 — Planning (if needed): For complex tasks, decomposes the goal into sub-tasks and creates a plan. Step 4 — Take Action: Execute the plan — call a tool, query a database, write code, generate text, delegate to a sub-agent. Step 5 — Observe and Adapt: Review the result of the action. If the task is not complete, update the plan and repeat steps 2–5 (iterative refinement / feedback-driven adaptation). Loop continues until the final deliverable is produced.

3. What is the difference between Deterministic flow and Dynamic flow in an Agentic system?

▶ Show Answer
Deterministic flow (also called Workflow): The sequence of steps is pre-coded by the developer. Step A always leads to step B, then C. The path is fixed regardless of what happens. No dynamic decision-making by the LLM — the LLM executes within a predefined structure. Also called a "deterministic agent." Example: document processing pipeline where every document always goes through parse → chunk → embed → store → retrieve → generate. Dynamic flow (True Agent): The LLM dynamically decides what to do next at each step based on the current state. Path is NOT pre-determined — it emerges from the LLM's reasoning. Much more flexible but non-deterministic — harder to debug. This is the "true" Agentic system.

4. What is a Deep Agentic System? Is it a separate concept from single-agent or multi-agent?

▶ Show Answer
A Deep Agentic System is a large, long-running system designed for complex to very complex problems. It's characterised by extensive planning, multiple task decomposition, multiple tool calls, potential sub-agents, and a repeating process until final deliverables are produced. It is NOT a separate paradigm — "deep" describes the depth/scale of execution, not a different architecture. Both a single-agent system AND a multi-agent system can be deep agentic systems. If a single agent is running for a long time with extensive planning (e.g. research + write + validate + publish a long-form report), that's a deep agentic system too.

5. Why does Sunny recommend LangGraph over LangChain's built-in agent classes?

▶ Show Answer
LangChain's built-in agent classes (like AgentExecutor, ReAct) are high-level abstractions — pre-coded classes for basic agent patterns. They're fast to set up but offer limited control and limited visibility into what's happening under the hood. LangGraph offers low-level control: you define every node (function), every edge (connection), every state transition, and every routing condition yourself. This means: full visibility into the flow, easier debugging, ability to implement any custom logic, and production-grade features (checkpointing, fault tolerance, human-in-the-loop, parallelism, sub-graphs). For learning and production, LangGraph is preferred because it teaches you what's actually happening, not just how to use a wrapper.

6. What are LangSmith, LangFuse, and LangFlow — and how are they different from LangGraph?

▶ Show Answer
LangSmith: Observability platform by LangChain. Traces every LLM call, tool call, token usage, and agent step in production. Similar to MLflow or CloudWatch but for LangChain/LangGraph apps. Used for debugging, monitoring, and performance analysis. LangFuse: Open-source alternative to LangSmith for tracing and monitoring. Can be self-hosted — gives teams full control of their telemetry. LangFlow: Visual drag-and-drop workflow builder. Lets you build and visualise LangChain flows without writing much code. Good for demos and non-technical stakeholders. All three are observability/tooling tools — NOT Agentic frameworks. LangGraph is the framework used to build the actual Agentic system; LangSmith/LangFuse/LangFlow are tools to observe, visualise, or build on top of it.
