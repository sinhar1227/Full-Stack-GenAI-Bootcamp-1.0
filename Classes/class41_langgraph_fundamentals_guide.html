03 — Core Concepts

LangGraph Architecture

Nodes and Edges

Every LangGraph program is built from exactly two things:

Node = Python Function

A node is nothing more than a Python function. It receives the current state as input and returns an updated state as output. Any logic goes inside — an LLM call, a database query, a tool call, a transformation, anything.

def my_node(state: State) → dict: ...

Edge = Relationship

An edge connects two nodes. Sequential edge: always go from A to B. Conditional edge: a routing function inspects the state and returns which node to visit next — enabling dynamic Agentic flows.

graph.add_edge("node_a", "node_b")

What is State?

"State means passing information, or data, from one node to another while maintaining the state. State is the data which is flowing across the nodes. Every node is aware about all the information — what information was there at node 1, now node 3 is aware about it. We are throwing the information across the node, and throughout this node, the state will be flowing."
State Flow — Sunny's Blackboard Example (4-node RAG pipeline)
Node 1
question arrives
→
Node 2

→
Node 3

→
Node 4

State class (TypedDict): question, route, context, answer
Node 1 → state has: question
Node 2 → state has: question + route
Node 3 → state has: question + route + context
Node 4 → state has: question + route + context + answer

04 — State Definition

3 Ways to Define State

Method 1 — TypedDict (Most Common)

python · TypedDict state 
from typing import TypedDict, List, Optional

# ── Custom State using TypedDict ──────────────────────────────────
# State = a dictionary-like class where every key has a defined type
# This is what flows through every node in the graph
class State(TypedDict):
    message: str           # simple string field

# ── More realistic RAG pipeline state ────────────────────────────
class RAGState(TypedDict):
    question: str          # user's query
    route:    Optional[str] # "rag", "llm", or "web" — decided by supervisor
    context:  Optional[str] # retrieved context (from retriever node)
    answer:   Optional[str] # final generated answer

# ── Initialize and inspect ────────────────────────────────────────
my_state = State(message="Hello World")
print(my_state)   # {"message": "Hello World"}

rag_state = RAGState(
    question = "What is RLHF?",
    route    = None,
    context  = None,
    answer   = None
)

# Note: you don't have to initialize ALL fields at start
# Uninitialized fields are None — nodes set them as they execute
# By node 4: all 4 fields have values (question, route, context, answer)

Method 2 — Pydantic BaseModel (Validated)

python · Pydantic state 
from pydantic import BaseModel

# Pydantic gives you automatic type validation
# If you pass wrong types, Pydantic raises a ValidationError immediately
# Preferred in production for safety
class AgentState(BaseModel):
    question: str
    route:    str = "llm"      # default value
    context:  str = ""
    answer:   str = ""

# Pydantic validates on instantiation
state = AgentState(question="What is the HR policy?")
print(state.route)   # "llm" (default)

# Pydantic is also used for structured output schemas in LLM routing
# (covered in detail in the routing section below)

Method 3 — MessagesState (LangGraph Built-in)

LangGraph ships with a built-in state class already designed for conversational flows. Sunny navigated to the LangGraph GitHub source to show students exactly where it's defined.

MessagesState — How it stores conversation history
HumanMessage "What are the side effects of metformin?"
AIMessage "Metformin commonly causes nausea, diarrhea, and stomach upset..."
HumanMessage "Are there any interactions with other drugs?"
AIMessage "Yes, metformin can interact with iodinated contrast media..."
As many messages as needed can be appended — Annotated[List[AnyMessage], add_messages]
python · MessagesState import and usage 
from langgraph.graph.message import MessagesState
# or: from langgraph.graph import MessagesState (depending on version)

# MessagesState is equivalent to writing:
from typing import Annotated, List
from langchain_core.messages import AnyMessage, add_messages

class MessagesState(TypedDict):
    messages: Annotated[List[AnyMessage], add_messages]
# "Annotated[List[AnyMessage], add_messages]" means:
# → It's a list of messages (HumanMessage, AIMessage, SystemMessage...)
# → add_messages = append operator: new messages are ADDED to the list,
#   not overwritten — conversation history is preserved automatically

# Usage: initialize with a list of messages
initial_state = {
    "messages": [("human", "What is the company HR policy?")]
}
# Each message added by a node is appended to the list
# The LLM sees the full message history on every call
05 — First Program

First StateGraph — Build Step by Step

Simple 3-Node Graph (No LLM)

python · first StateGraph 
from langgraph.graph import StateGraph, START, END
from typing import TypedDict

# ── Step 1: Define the State ──────────────────────────────────────
class State(TypedDict):
    message: str    # single field flowing through all nodes

# ── Step 2: Define nodes (Python functions) ───────────────────────
# Each node receives state → modifies it → returns updated dict
def node_first(state: State) -> dict:
    print("Executing node_first")
    # Read from state and update
    updated = state["message"] + " → node_first processed"
    return {"message": updated}

def node_second(state: State) -> dict:
    print("Executing node_second")
    updated = state["message"] + " → node_second processed"
    return {"message": updated}

def node_third(state: State) -> dict:
    print("Executing node_third")
    updated = state["message"] + " → node_third processed"
    return {"message": updated}

# ── Step 3: Build the StateGraph ─────────────────────────────────
workflow = StateGraph(State)

# Add nodes: (name_string, function)
workflow.add_node("first",  node_first)
workflow.add_node("second", node_second)
workflow.add_node("third",  node_third)

# Add sequential edges
workflow.add_edge(START,    "first")   # entry point
workflow.add_edge("first",  "second")
workflow.add_edge("second", "third")
workflow.add_edge("third",  END)      # exit point

# ── Step 4: Compile ───────────────────────────────────────────────
# compile() validates the graph structure and returns a runnable app
app = workflow.compile()

Invoke the Graph

python · invoke 
# ── Step 5: Invoke ────────────────────────────────────────────────
# Pass initial state as a dict matching the State TypedDict
result = app.invoke({"message": "Hello from user"})
print(result)
# Executing node_first
# Executing node_second
# Executing node_third
# {"message": "Hello from user → node_first processed → node_second processed → node_third processed"}

# ── What happens inside invoke: ───────────────────────────────────
# 1. START → node_first  : state = {"message": "Hello from user"}
# 2. node_first runs, returns {"message": "Hello from user → node_first processed"}
# 3. State is UPDATED (merge): {"message": "Hello from user → node_first processed"}
# 4. → node_second runs, same pattern
# 5. → node_third runs, same pattern
# 6. → END: final state returned

Visualise the Graph

python · graph visualisation 
from IPython.display import Image, display

# Render the graph as a PNG image (Mermaid diagram)
display(Image(app.get_graph().draw_mermaid_png()))
# → Shows a visual flowchart: START → first → second → third → END
# → Each node is a box, each edge is an arrow

LLM Node with MessagesState

python · LLM-integrated graph 
from langgraph.graph.message import MessagesState
from langgraph.graph import StateGraph, START, END

# ── LLM node function ─────────────────────────────────────────────
def call_model(state: MessagesState) -> dict:
    """
    Node that calls an LLM with the current message history
    and appends the response to the messages list.
    """
    messages = state["messages"]   # get current message list from state
    print(ff"Input messages: {messages}")

    response = llm.invoke(messages)  # pass full conversation history to LLM
    print(ff"LLM response: {response.content}")

    # Return: the response message is APPENDED to state["messages"]
    # (because add_messages reducer is set on MessagesState)
    return {"messages": [response]}

# ── Build graph with MessagesState ────────────────────────────────
workflow = StateGraph(MessagesState)

workflow.add_node("my_bot", call_model)
workflow.add_edge(START,    "my_bot")
workflow.add_edge("my_bot", END)

app = workflow.compile()

# ── Invoke with a user message ────────────────────────────────────
from langchain_core.messages import HumanMessage

result = app.invoke({
    "messages": [HumanMessage(content="What is RLHF?")]
})

# result["messages"] is a list: [HumanMessage, AIMessage]
print(result["messages"][-1].content)  # last message = LLM response

HumanMessage & AIMessage — Why Both Types?

HumanMessage

The user's input message. Created before invoking the graph. HumanMessage(content="...") is passed in the initial state's messages list.

AIMessage

The LLM's response. Created by the LLM call and returned from the node. Automatically appended to the messages list via the add_messages reducer.

🟢

Simple AI assistant confirmed: This single-node graph with an LLM call produces a deterministic AI assistant — user input goes in, LLM response comes out, graph ends. Sunny called it: "This is my simple deterministic AI agent — or really it's a simple AI assistant, right? The flow is deterministic, we don't have any back and forth."

07 — Dynamic Routing

Conditional Edges

Concept

Conditional edges enable dynamic routing — the path the graph takes depends on the current state value, not a fixed sequence. This is the key mechanism that makes Agentic systems non-deterministic.

Sequential vs Conditional Edge
Sequential edge: node_A → node_B always. No logic. Fixed path.
Conditional edge: node_A → ? depends on state["route"]. Could go to node_B, node_C, or node_D.

Conditional Edge Code

python · conditional edge 
from typing import Literal

# ── Routing function (returns string = next node name) ────────────
def route_query(state: State) -> Literal["rag_node", "llm_node", "web_node"]:
    """Inspect state and return the name of the next node to execute."""
    route = state["route"]
    if route == "rag":
        return "rag_node"
    elif route == "web":
        return "web_node"
    else:
        return "llm_node"   # default

# ── Connect conditional edge to graph ─────────────────────────────
workflow.add_conditional_edges(
    "supervisor_node",    # source node
    route_query,           # routing function (receives state → returns string)
    {                      # mapping: function return value → node name
        "rag_node": "rag_node",
        "llm_node": "llm_node",
        "web_node": "web_node"
    }
)
# When supervisor_node finishes, route_query(state) is called
# Its return value selects the next node
# This is the core mechanism of dynamic Agentic routing

Full Agentic Routing Flow

The 3-Route Problem

"Conversational bot: user can ask questions from company internal data, user can ask generic question via the model itself, or user can ask from the current web data. Structured Output for Routing

Instead of keyword-matching or regex, the Supervisor Agent uses structured output — the LLM is forced to return a Pydantic-validated JSON with a specific schema. This is far more reliable than parsing free text.

python · Pydantic schema + structured output 
from pydantic import BaseModel, Field
from typing import Literal

# ── Schema 1: Route Decision ──────────────────────────────────────
# LLM MUST respond in this exact format
class RouteDecision(BaseModel):
    route: Literal["rag", "llm", "web"] = Field(
        description="The route to take: 'rag' for company data, 'llm' for general, 'web' for real-time"
    )
    reasoning: str = Field(
        description="Brief explanation of why this route was chosen"
    )

# ── Schema 2: Validation Result ───────────────────────────────────
class ValidationResult(BaseModel):
    is_valid: bool = Field(
        description="True if the response adequately answers the user's query"
    )
    score: float = Field(
        description="Confidence score 0.0–1.0 of answer quality"
    )
    feedback: str = Field(
        description="Brief feedback on the quality of the answer"
    )

# ── View schema as JSON ───────────────────────────────────────────
print(RouteDecision.model_json_schema())
# {
#   "properties": {
#     "route": {"enum": ["rag", "llm", "web"], "type": "string"},
#     "reasoning": {"type": "string"}
#   }
# }

Supervisor Agent Node

python · supervisor node with structured output 
# ── Supervisor model: LLM forced to output RouteDecision schema ───
supervisor_model = llm.with_structured_output(
    schema = RouteDecision,
    method = "json_schema"
)

# ── Test supervisor routing ───────────────────────────────────────
result = supervisor_model.invoke("Hi, how are you?")
print(result.route)      # "llm" — generic greeting → model knowledge
print(result.reasoning)  # "This is a conversational greeting..."

result2 = supervisor_model.invoke("What is the current USA GDP?")
print(result2.route)     # "web" — real-time data needed

result3 = supervisor_model.invoke("What is our company HR leave policy?")
print(result3.route)     # "rag" — company internal document

# ── Supervisor node function ──────────────────────────────────────
def supervisor_node(state: State) -> dict:
    """Decides which route to take using structured LLM output."""
    question = state["question"]
    decision  = supervisor_model.invoke(question)
    print(ff"Supervisor → route: {decision.route}, reason: {decision.reasoning}")
    return {"route": decision.route, "reasoning": decision.reasoning}

Validator Agent Node

python · validator node 
# ── Validator model: checks answer quality ────────────────────────
validator_model = llm.with_structured_output(
    schema = ValidationResult,
    method = "json_schema"
)

def validator_node(state: State) -> dict:
    """Validates the generated answer quality. Routes to final or fail."""
    question = state["question"]
    answer   = state["answer"]
    validation_prompt = ff"""
    Question: {question}
    Answer: {answer}
    Is this answer adequate, accurate, and helpful? Score it 0.0 to 1.0.
    """
    result = validator_model.invoke(validation_prompt)
    print(ff"Validator → valid: {result.is_valid}, score: {result.score}")
    return {
        "validation_result": result.is_valid,
        "validation_score":  result.score,
        "validation_feedback": result.feedback
    }

# ── Validator routing function ────────────────────────────────────
def route_after_validation(state: State) -> str:
    if state["validation_result"] and state.get("validation_score", 0) >= 0.7:
        return "final_node"    # answer is good → output it
    else:
        return "failed_node"   # answer insufficient → apologise

Full Routing Graph Assembly

python · full 5-node routing graph 
# ── All node functions defined above (supervisor, rag, llm, web, validator, final, fail)
# ── Assemble the complete graph ───────────────────────────────────

workflow = StateGraph(AgentState)

# Add all nodes
workflow.add_node("supervisor_node", supervisor_node)
workflow.add_node("rag_node",        rag_node)
workflow.add_node("llm_node",        llm_node)
workflow.add_node("web_node",        web_node)
workflow.add_node("validator_node",  validator_node)
workflow.add_node("final_node",      final_node)
workflow.add_node("failed_node",     failed_node)

# Entry point → supervisor
workflow.add_edge(START, "supervisor_node")

# Supervisor → conditional edge (route to one of 3 nodes)
workflow.add_conditional_edges(
    "supervisor_node",
    lambda state: state["route"],   # routing function: read "route" from state
    {
        "rag": "rag_node",
        "llm": "llm_node",
        "web": "web_node"
    }
)

# All 3 routes → validator
workflow.add_edge("rag_node", "validator_node")
workflow.add_edge("llm_node", "validator_node")
workflow.add_edge("web_node", "validator_node")

# Validator → conditional edge (pass or fail)
workflow.add_conditional_edges(
    "validator_node",
    route_after_validation,
    {
        "final_node":  "final_node",
        "failed_node": "failed_node"
    }
)

# Both final and failed → END
workflow.add_edge("final_node",  END)
workflow.add_edge("failed_node", END)

app = workflow.compile()

# ── Test the full routing system ──────────────────────────────────
def run_agent(question: str):
    result = app.invoke({"question": question, "answer": "", "route": ""})
    print(ff"\nQ: {question}")
    print(ff"Route: {result['route']}")
    print(ff"A: {result['answer']}")
    return result

# Test all 3 routes
run_agent("Hi, how can you help me?")         # → llm route
run_agent("What is the company HR policy?")   # → rag route
run_agent("What is the current USA GDP?")     # → web route
run_agent("What is Sunny's salary?")          # → fail route (validation score low)

09 — Important Distinction

State vs Memory — Clarification

"State means: maintaining the input and output throughout the node execution — that's it. That's the meaning of the state. Inside ONE execution, inside ONE thread. State is not memory. For every question, it is following and executing the entire workflow. Memory is different — that is a little more advanced. I haven't explained you that side, because that required a couple more sessions."

State (within one execution)

  • → Data flowing between nodes in a single graph run
  • → Lives for one invocation (one thread)
  • → All nodes in that run share the same state object
  • → Resets with each new invocation

Memory (across sessions — coming soon)

  • → Short-term: Checkpointer (within same thread/session)
  • → Long-term: Persistent storage (across different threads)
  • → Per-user: Thread ID = one user, state persists for that user
  • → Cross-thread: shared context across multiple users
📌

Thread model preview: For every user, a new thread is launched. With a Checkpointer, the state for that thread persists — enabling conversational memory within a session. Cross-thread memory requires an additional long-term storage layer (e.g. Redis or Postgres). Sunny promised to cover this in detail in upcoming classes.

11 — Q&A

Q&A Highlights

Q — Swati
Can we use Airflow instead of LangGraph for building Agentic AI flows?
A — Sunny
No — they serve different purposes. Airflow is for scheduling jobs, ETL pipelines, batch workflows, and data orchestration. LangGraph is specifically for building stateful AI agent workflows with LLM reasoning, dynamic routing, and tool calling. You can use BOTH together — Airflow to schedule and orchestrate data pipelines, LangGraph to handle the AI agent logic within those pipelines. They complement, not replace, each other.
Q — Swati
State is like XCOM in Airflow, right? And how does memory work across sessions?
A — Sunny
State analogy: yes, state in LangGraph is like XCOM in Airflow — both are mechanisms to pass data between execution units (tasks/nodes). For memory across sessions: each user triggers a new thread. With a Checkpointer attached, the state for that thread is persisted — this becomes short-term memory (within the same session). For long-term cross-session memory, you need additional persistent storage. For cross-thread memory (shared across multiple users), you need a separate store. All this is coming in upcoming classes.
Q — Raghu
Why use MessagesState when I can define my own TypedDict with the same fields?
A — Sunny
You can absolutely use your own TypedDict — it's the same concept. MessagesState is a convenience: LangGraph pre-built it so you don't need to define the messages field and its add_messages reducer yourself. The key difference is the Annotated[List[AnyMessage], add_messages] type — it enables message appending without overwriting. When you use custom TypedDict, you can do the same thing by annotating your field similarly. MessagesState is just a shortcut for the most common conversational pattern.
12 — Self-Check

Quiz — Test Your Understanding

📝 Class 41 Concept Check

1. What is a Node in LangGraph? What are the two rules every node function must follow?

▶ Show Answer
A node in LangGraph is simply a Python function — any regular def function. Two rules: (1) It must accept the current state as its only parameter (typed as the State class you defined). (2) It must return a dictionary with the keys it wants to UPDATE in the state — only the returned keys are merged into the state; unreturned keys remain unchanged. The function can contain any logic: an LLM call, a tool call, a database query, a transformation, anything. The function name is not the node name — you give it a string name when calling graph.add_node("my_name", my_function).

2. What is State in LangGraph and what is the difference between State and Memory?

▶ Show Answer
State is the data object that flows through every node during a single graph execution. It's like XCOM in Airflow — the mechanism for passing information between nodes. Every node can read from and write to the state. State is defined as a TypedDict (or Pydantic BaseModel) and passed by reference through the graph. Memory is different: State lives only for ONE execution (one invocation, one thread). Memory persists ACROSS executions/sessions. Short-term memory (same session): use a Checkpointer that saves state after each step. Long-term memory (across sessions): persistent storage like Redis or Postgres. Sunny emphasised: "State is within one execution. For every question, the entire workflow runs fresh."

3. What is MessagesState and why does it use Annotated[List[AnyMessage], add_messages]?

▶ Show Answer
MessagesState is a built-in LangGraph state class designed for conversational flows. Its messages field is typed as Annotated[List[AnyMessage], add_messages]. This means: (1) it stores a list of message objects (HumanMessage, AIMessage, SystemMessage, etc.), and (2) add_messages is a reducer — when a node returns {"messages": [new_msg]}, the new message is APPENDED to the existing list, not overwriting it. This automatically builds up the full conversation history as the graph executes. Without this annotation, returning {"messages": [x]} would overwrite the entire list. You can see the actual implementation in LangGraph's GitHub (langgraph/graph/message.py).

4. What is the difference between a sequential edge and a conditional edge? Give a concrete example of each.

▶ Show Answer
Sequential edge: always goes from node A to node B — no logic, fixed path. graph.add_edge("node_a", "node_b") — every time node_a finishes, it goes to node_b, no matter what the state contains. Example: after the retriever node, always go to the generation node. Conditional edge: a routing function inspects the current state and RETURNS the name of the next node to visit. graph.add_conditional_edges("supervisor_node", routing_fn, {return_value: node_name}) — the routing function can return "rag_node", "llm_node", or "web_node" depending on state["route"]. Example: if state["route"] == "rag" → go to rag_node; if state["route"] == "web" → go to web_node. Conditional edges enable dynamic Agentic flows — the path is decided at runtime by the LLM, not the developer.

5. What is structured output, and why did Sunny use it for the supervisor and validator nodes instead of parsing free text?

▶ Show Answer
Structured output means forcing the LLM to return its response in a specific, validated format — defined by a Pydantic schema — rather than free text. Using llm.with_structured_output(schema=RouteDecision, method="json_schema"), the LLM's output is automatically parsed and validated against the schema. If the LLM tries to return something invalid (e.g. "maybe_rag" instead of "rag"|"llm"|"web"), Pydantic raises a ValidationError. Sunny used it for the supervisor because parsing "I think this should go to the RAG database" from free text is unreliable — the Literal["rag","llm","web"] type in RouteDecision constrains the LLM to exactly those three values. For the validator, ValidationResult.is_valid=bool ensures a clean True/False routing decision. This is far more reliable than regex or keyword matching in production.
