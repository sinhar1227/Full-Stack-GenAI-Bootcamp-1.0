03 — Revision

Tool Creation Methods — Full Revision

"Tool creation is one thing, and tool calling is the another thing. We have different, different methods for the tool creation. Don't think that if I've given stars, these methods are being used in the industry — it's based on priority, means if you're learning the thing, you can learn in this particular sequence. But if you're going to perform tool engineering in real time, explore each and every methodology."

All Tool Creation Methods

@tool decorator ★★★★★ Simple custom functions — beginner default Any Python function decorated with @tool becomes a LangChain tool. Docstring becomes the tool description.

Toolkit (BaseToolkit) ★★★ Grouping multiple related tools Bundle related tools into a toolkit class. Provides a .get_tools() method to retrieve the full list.

Two Critical LLM API Methods

When you initialise any LLM using LangChain, two methods are always available. These are used heavily in Agentic workflows:

llm.bind_tools(tools)

Attaches tool schemas to the LLM. The LLM now knows what tools are available and can choose to call them. When the LLM decides to use a tool, it returns an AI message with empty content but a tool_calls field containing the tool name and arguments. The actual tool has NOT been called yet — only the intent has been expressed.

llm.with_structured_output(schema)

Forces the LLM to respond only in the format defined by a Pydantic model or TypedDict. Output is automatically parsed and validated. Used in Class 41's routing supervisor agent to force route decisions into a typed RouteDecision schema. Not for tool calling — for constraining the LLM's free-text output.

🔑

Key distinction: bind_tools = "LLM, here are tools you can call if needed." with_structured_output = "LLM, your output MUST match this schema exactly." You'll see both used throughout the Agentic chapter. Sunny: "Just remember these two functions. We are going to be using these a lot."

04 — Schema Enforcement

Pydantic + Tool — Schema Enforcement

When building production-grade Agentic systems, always pair tool definitions with Pydantic schemas. This ensures the LLM provides exactly the right type and structure of arguments — and raises an immediate error if it doesn't.

Pydantic Tool Code

python · Pydantic schema + tool 
from langchain_core.tools import tool
from pydantic import BaseModel, Field
from typing import Optional

# ── Define a Pydantic schema for the tool's input ─────────────────
# This enforces type validation on every call to the tool
class WeatherInput(BaseModel):
    location:    str   = Field(description="City name or 'city, country' format")
    unit:        str   = Field(default="celsius", description="Temperature unit: 'celsius' or 'fahrenheit'")
    include_forecast: Optional[bool] = Field(default=False, description="Include 5-day forecast")

# ── Create tool with Pydantic schema ─────────────────────────────
# Pass the Pydantic class as args_schema — schema is enforced
@tool(args_schema=WeatherInput)
def get_weather(location: str, unit: str = "celsius", include_forecast: bool = False) -> str:
    """Get current weather for a given location."""
    # In practice, call a real weather API here
    return ff"Weather in {location}: 28°{unit[0].upper()}, partly cloudy"

# ── Correct call — works fine ─────────────────────────────────────
result = get_weather.invoke({"location": "Delhi", "unit": "celsius"})
print(result)   # Weather in Delhi: 28°C, partly cloudy

# ── Wrong type call — Pydantic raises ValidationError ────────────
try:
    get_weather.invoke({"location": 12345})  # location must be str, not int
except Exception as e:
    print(ff"ValidationError: {e}")
# → Pydantic immediately raises before the tool function is even called

# ── View tool schema (what the LLM sees) ─────────────────────────
print(get_weather.name)        # "get_weather"
print(get_weather.description) # "Get current weather for a given location."
print(get_weather.args_schema.model_json_schema())
# → JSON schema that the LLM reads to know what arguments to provide

# ── Why Pydantic matters ──────────────────────────────────────────
# Sunny: "Schema enforcing is very much required. Otherwise my LLM
# might distract — it can give you the wrong output. We have to
# validate those input and output. Otherwise my Agentic flow can
# provide you the wrong answer."
05 — Key Distinction

Tool Node vs Normal Node — The Key Difference

Why Use Tools at All — Sunny's Explanation

"Suppose the user can ask: 'What is the weather in Bangalore?' or 'Search my company policy' or 'Calculate this'. Now your agent has weather, calculator, retriever, web search, database, email — if everything is only nodes, you need explicit routing for each and everything. You will have to do the routing manually. But if you are giving a capability to the LLM so that it can decide which tool node needs to be executed — where this tool calling is the important one."

Node vs ToolNode — Comparison

AspectNormal NodeTool Node
Who decides to execute? Developer — hardcoded in graph edges/routing LLM — dynamically decides at runtime
How many can you have? One node per functionality. 5 operations = 5 nodes. One ToolNode holds all tools. 5 or 100 tools — still one ToolNode.
Routing Manual conditional edges. You write every routing rule. LLM selects the right tool from its bound list automatically.
Flow type Deterministic orchestration Dynamic (Agentic) capability
Best for Known, fixed workflows with few steps. More controllable. Open-ended queries where the LLM should reason about which capability to use.
Risk More effort to build. Less flexible. LLM might make wrong tool selection. Less predictable.
⚠️

Sunny's production advice: "If you are able to perform this entire thing with the deterministic approach, do it, because it is a more deterministic, more secure approach. Use the dynamic tool approach when the LLM should dynamically choose the capability. But be very cautious — in the open-ended approach, we are leaving everything to the LLM, and LLM can make a mistake."

06 — The Pattern

ReAct Agent — What and Why

What is ReAct?

ReAct stands for Reasoning + Acting. It's a prompting pattern where the LLM interleaves reasoning steps ("I need to add first, then multiply") with action steps (calling the add tool, then the multiply tool). The result of each action feeds back into the LLM's reasoning for the next step.

💡

Sunny's framing: "The main purpose of teaching you this ReAct agent — using this React agent, basically, we can understand how our LLM can perform the tool calling. This is the entry point to understanding the full Agentic tool-calling flow. All subsequent, more complex workflows build on top of this same pattern."

The Reason-Act Loop

ReAct Loop — Step by Step
→

User Input

A question arrives. Passed to the graph as a HumanMessage in the state.

1

LLM Agent Node — Reason

LLM reads the user message, system prompt, and all prior messages/tool results in the state. It reasons: "Do I need a tool? Which one? Or can I answer directly and end?"

2

Conditional Edge — ToolCondition

Check: does the LLM's output contain a tool_calls field? If YES → go to ToolNode. If NO → go to END.

3

ToolNode — Act

Execute the tool the LLM selected. Tool receives the arguments the LLM extracted from the query. Returns result as a ToolMessage. ToolMessage is appended to the state messages list.

4

Back to LLM — Observe

ToolNode loops back to LLM Agent Node. The LLM now has the original question + the tool result. It reasons again: is the task done? Do I need another tool call?

✓

Final Answer → END

When LLM decides the task is complete, it generates a final answer (non-empty content, no tool_calls) → conditional edge routes to END.

↻ Steps 1–4 repeat until the task is complete. This loop is the "Reason-Act" cycle.

5 Math Tools

python · tool definitions 
# 5 simple math tools — kept simple to focus on the flow, not the logic
# In real projects these would call APIs, databases, web search, etc.

@tool
def add(a: float, b: float) -> float:
    """Add two numbers and return the result."""
    return a + b

@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers and return the result."""
    return a * b

@tool
def subtract(a: float, b: float) -> float:
    """Subtract b from a and return the result."""
    return a - b

@tool
def divide(a: float, b: float) -> float:
    """Divide a by b and return the result. Returns error if b is 0."""
    if b == 0:
        return "Error: Division by zero"
    return a / b

@tool
def power(base: float, exponent: float) -> float:
    """Raise base to the power of exponent."""
    return base ** exponent

# Collect all tools in a list
tools = [add, multiply, subtract, divide, power]

# ── LLM setup ────────────────────────────────────────────────────
# temperature=0 → deterministic/predictable answers (no creativity in calculations)
# reasoning_format="hidden" → hides internal chain-of-thought in reasoning models
llm = ChatGroq(model="llama-3.1-8b-instant", temperature=0)

# ── Bind all tools to the LLM ─────────────────────────────────────
# Now the LLM knows about add, multiply, subtract, divide, power
# When a math question comes in, it can choose to call the appropriate tool
llm_with_tools = llm.bind_tools(tools)

LLM Agent Node

python · agent node function 
# ── System prompt ─────────────────────────────────────────────────
SYSTEM_PROMPT = """You are a mathematical agent. You have access to 5 tools:
- add: for addition
- multiply: for multiplication
- subtract: for subtraction
- divide: for division
- power: for exponentiation

Rules:
- Always use the appropriate tool for mathematical calculations.
- Do not perform calculations yourself — always use a tool.
- Follow the user-requested calculation order.
- When one operation depends on a previous result, wait for the tool result before calling the next tool.
- After all required tool calls, provide the final answer."""

# ── Agent (LLM) node function ─────────────────────────────────────
def llm_agent_node(state: MessagesState) -> dict:
    """
    The core agent node: calls the LLM with the full message history.
    LLM either:
    (a) Requests a tool call → AIMessage with tool_calls field populated
    (b) Produces a final answer → AIMessage with content, no tool_calls
    """
    messages  = state["messages"]    # full conversation history from state
    # Prepend system prompt
    full_msgs = [SystemMessage(content=SYSTEM_PROMPT)] + messages
    response  = llm_with_tools.invoke(full_msgs)
    # Return: the response is appended to the state messages list
    # (MessagesState uses add_messages reducer → appends, not overwrites)
    return {"messages": [response]}

ToolCondition / should_continue

python · routing logic (both approaches) 
# ── Approach 1: LangGraph pre-built tools_condition ───────────────
# Automatically checks: does the last AI message have tool_calls?
# If yes → route to "tools" node; if no → route to END
# tools_condition is imported from langgraph.prebuilt

# ── Approach 2: Custom should_continue function ───────────────────
# Sunny recommends custom over pre-built for flexibility and clarity
from typing import Literal

def should_continue(state: MessagesState) -> Literal["tools", END]:
    """
    Routing function for the conditional edge after LLM Agent Node.
    Returns "tools" if LLM wants to call a tool, END otherwise.
    """
    messages = state["messages"]
    last_msg = messages[-1]   # last message is the LLM's latest response

    # If the AI message has tool_calls, the LLM wants to use a tool
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        return "tools"     # route to ToolNode

    # No tool_calls → LLM generated a final answer → end the process
    return END            # route to END

# Sunny: "To write a custom method, I think that's more flexible.
# From now onwards, we'll be using our custom functionality only,
# instead of relying much over the inbuilt functionality of LangGraph."

Full Graph Assembly

python · complete ReAct graph 
# ── Build the StateGraph ──────────────────────────────────────────
workflow = StateGraph(MessagesState)

# Add nodes
workflow.add_node("agent", llm_agent_node)  # LLM with tool awareness
workflow.add_node("tools", tool_node)         # ToolNode wrapping all 5 tools

# Add edges
workflow.add_edge(START, "agent")              # entry: always start with agent

# Conditional edge: after agent node, check if tool call needed
workflow.add_conditional_edges(
    "agent",              # source: from the agent node
    should_continue,       # routing function
    {
        "tools": "tools",  # if "tools" returned → go to tool_node
        END: END           # if END returned → terminate
    }
)

# After tool execution, ALWAYS go back to agent for next reasoning step
workflow.add_edge("tools", "agent")

# ── Compile and visualise ─────────────────────────────────────────
app = workflow.compile()
from IPython.display import Image, display
display(Image(app.get_graph().draw_mermaid_png()))
# → Graph: START → agent → (tools → agent)* → END

# ── Invoke the graph ──────────────────────────────────────────────
result = app.invoke({
    "messages": [HumanMessage(content="What is (2 + 2) multiplied by 10?")]
})

# Print the final answer (last message)
print(result["messages"][-1].content)
# → "The result of (2 + 2) × 10 is 40."

# ── Inspect the full message trail ───────────────────────────────
for msg in result["messages"]:
    print(ff"{type(msg).__name__}: {str(msg.content)[:80]}")
# HumanMessage: "What is (2 + 2) multiplied by 10?"
# AIMessage: (empty content, tool_calls=[add(a=2, b=2)])
# ToolMessage: "4"
# AIMessage: (empty content, tool_calls=[multiply(a=4, b=10)])
# ToolMessage: "40"
# AIMessage: "The result of (2 + 2) × 10 is 40."
08 — Step by Step

Multi-Step Tool Chaining Walkthrough

Sunny walked through this example live on the blackboard — query "(2+2) × 10" — to show every step of the ReAct loop:

Q
User sends: "(2+2) × 10" → goes to LLM Agent Node as HumanMessage in state
1
LLM reasons: "Order of operations: do addition first. I need the add tool with a=2, b=2." LLM returns AIMessage with empty content and tool_calls=[add(a=2, b=2)]
2
tools_condition: tool_calls detected → route to ToolNode
3
ToolNode executes add(2, 2) = 4. Returns ToolMessage("4") → appended to state messages list
4
LLM reasons again (with full history: question + add result "4"). "Now I need to multiply 4 by 10." Returns AIMessage with tool_calls=[multiply(a=4, b=10)]
5
ToolNode executes multiply(4, 10) = 40. Returns ToolMessage("40") → appended to state
✓
LLM reasons again (with full history including multiply result "40"). "All operations done. Final answer: 40." Returns AIMessage with content="The answer is 40." and no tool_calls → routes to END.
"LLM dynamically is taking a decision — based on their reasoning capability. This is called the real Agentic system, where LLM is dynamically taking the decision of which tool needs to be called, which functionality needs to be called."

MessagesState — Why All Messages Accumulate

python · understanding the state accumulation 
# MessagesState has: messages: Annotated[List[AnyMessage], add_messages]
# add_messages reducer means: each new message is APPENDED (not overwritten)
# After the (2+2)×10 query, the state contains ALL of:

messages_in_state = [
    HumanMessage(content="What is (2 + 2) multiplied by 10?"),
    AIMessage(content="", tool_calls=[{"name": "add", "args": {"a": 2, "b": 2}}]),
    ToolMessage(content="4", tool_call_id="call_xxx"),
    AIMessage(content="", tool_calls=[{"name": "multiply", "args": {"a": 4, "b": 10}}]),
    ToolMessage(content="40", tool_call_id="call_yyy"),
    AIMessage(content="The result of (2 + 2) × 10 is 40.")
]

# Why is this important?
# On every LLM call, the LLM receives the FULL message history.
# This is how it knows:
# - The original question (HumanMessage)
# - It already called add and got 4 (ToolMessage content="4")
# - It already called multiply and got 40 (ToolMessage content="40")
# - No more tools needed → generate final answer → END
# This is the LLM's "working memory" within one graph execution.
09 — Core Concept

Dynamic (Tool-Based) vs Deterministic (Node-Based)

Sunny spent significant time on the blackboard comparing these two approaches — this is one of the most important architectural decisions in Agentic AI:

Dynamic / Tool-Based (Open-Ended Agent)

LLM + bind_tools([t1, t2, t3...])
↓
ONE tool_node (holds all tools)
↓
LLM dynamically picks which tool
  • ✓ Very flexible — add 100 tools without changing graph
  • ✓ LLM reasons and selects the right capability
  • ✗ LLM may select the wrong tool
  • ✗ Non-deterministic — harder to debug
  • ✗ Risk: open-ended → LLM "might mess up"
Use when: many dynamic tools, open-ended user queries, flexibility prioritised over control

Deterministic / Node-Based (Workflow)

Supervisor LLM node
↓
Node 1 (add) | Node 2 (multiply) | ...
↓
Explicit conditional edges for routing
  • ✓ Full developer control over each step
  • ✓ Predictable, auditable, debuggable
  • ✓ Preferred for fewer, well-defined operations
  • ✗ More work — one node per functionality
  • ✗ Manual routing logic for every path
Use when: fewer operations, regulated/safety-critical flows, maximum control needed
"You have to choose this thing wisely, very, very wisely, how you are going to design your entire workflow. If you are able to perform this entire thing with the deterministic approach, do it, guys, because this is more deterministic, more secure approach. Use tool when the LLM should dynamically choose the capability. But be very cautious — we are leaving everything to the LLM, and LLM can make a mistake."

11 — Q&A

Q&A Highlights

Q — Swati
When selecting an LLM for an Agentic system, is there any criteria based on our domain (like using domain-specific models as we did in the NLP/Word2Vec era)?
A — Sunny
No — you can use a general-purpose LLM from OpenAI, Anthropic, Gemini, or Meta regardless of your domain. The era of domain-specific BERT-like models is largely obsolete for Agentic workflows. Modern general-purpose LLMs (GPT-4, Claude, Llama) have broad enough knowledge to handle domain queries effectively. For extreme domain specialisation (legal, medical), you can fine-tune a general LLM on domain data — but this is a separate concern from tool selection.
Q — Swati
How are Agents integrated in the real world? Is deployment within the scope of a GenAI engineer?
A — Sunny
Yes — you deploy the agent to a cloud platform (AWS, GCP, Azure) and it runs as a live application on a server. An agent is just code — you expose it via a FastAPI or similar API endpoint, and end users interact through a UI or direct API call. Deployment is covered in the final project phase of the bootcamp (3–4 end-to-end projects with cloud deployment). "An agent is also a codebase, right? We'll be deploying our application so that the end user can interact."
Q — Swati
Is tool engineering a separate topic in interviews, and what happens when there are hundreds of tools?
A — Sunny
Tool engineering is part of Agentic AI — not a separate topic. For the number of tools: it's not always 100 or 200 tools. It depends entirely on your use case. If you're building for a specific enterprise, requirements come from that enterprise. A focused internal HR bot might have 5 tools; a general-purpose agent might have 50. Use the deterministic approach for fewer, well-defined operations; use dynamic tool calling only when the LLM genuinely needs to choose dynamically. "It depends on the use case, actually."
Q — Bala
How does the LLM know which tool to call next when results are chained? Does it re-read all tools each time?
A — Sunny
The LLM has access to all bound tools on every call. The key is the MessagesState — it accumulates ALL messages in a list (HumanMessage, AIMessage with tool_calls, ToolMessage with result, next AIMessage, etc.). On every call to the LLM agent node, the full message history is passed. So when the LLM sees a ToolMessage containing "4" (from the add tool), it knows the first operation is done and can proceed to request the multiply tool with a=4. The growing message list IS the agent's working memory within one execution.
Q — Shivaay
If I have 10 different functions/agents for different use cases, and a user asks something that crosses multiple, how does the system decide which to call?
A — Sunny
In the dynamic (tool-based) approach: you bind all tools to the LLM, and the LLM reads the query, reasons about it, and selects the appropriate tool(s). For a query about traffic in Koramangala, if you have a traffic data tool and a mapping tool, the LLM reads both tool descriptions and decides which to call, in what order. The tool descriptions (docstrings) are critical — they must be clear and specific so the LLM can distinguish between tools. In the deterministic approach: you write the routing logic yourself — the supervisor LLM node uses structured output to explicitly select a node/route.

bind_tools(tools): Attaches tool schemas to the LLM. The LLM now knows what external capabilities are available and can choose to invoke them. When the LLM uses a tool, it returns an AIMessage with empty content and a tool_calls field — the tool has NOT been called yet, only the intent expressed. with_structured_output(schema): Forces the LLM's response to match a specific Pydantic or TypedDict schema. No tool calling — used when you need the LLM's text output to be parseable structured data. 2. What is a ToolMessage and when does it appear in the MessagesState?

▶ Show Answer
ToolMessage is the 4th message type (alongside HumanMessage, AIMessage, SystemMessage). It carries the result of a tool execution back into the message history. When does it appear: (1) LLM generates AIMessage with tool_calls=[{name, args}], (2) ToolNode executes the named tool with the provided args, (3) ToolNode wraps the result in ToolMessage(content=str(result), tool_call_id=...) and appends it to state. The LLM reads the ToolMessage on its next invocation to understand what the tool returned. Each tool call + result pair adds exactly one AIMessage (with tool_calls) + one ToolMessage to the state. For a 2-step calculation (add → multiply), the state contains: HumanMessage → AIMessage (add call) → ToolMessage (4) → AIMessage (multiply call) → ToolMessage (40) → AIMessage (final answer).

3. Why does Sunny recommend writing a custom should_continue function instead of using the pre-built tools_condition?

▶ Show Answer
Sunny's reasoning: "To write a custom method, I think that's more flexible. From now onwards, we'll be using our custom functionality only, instead of relying much over the inbuilt functionality of LangGraph." The pre-built tools_condition is a black box — you can't see or modify its decision logic. A custom should_continue function gives you: (1) Full visibility into what condition is being checked. (2) Ability to add additional conditions (e.g. maximum iteration count to prevent infinite loops, error handling, custom routing logic). (3) Better understanding of the underlying mechanism for interviews and debugging. The custom function is simple: check if messages[-1].tool_calls exists and is non-empty → return "tools"; otherwise return END.

4. What is the fundamental difference between a dynamic (tool-based) approach and a deterministic (node-based) approach? When should you choose each?

▶ Show Answer
Dynamic (Tool-Based, Open-Ended Agent): Bind all tools to the LLM. One ToolNode contains all tools. The LLM dynamically decides at runtime which tool to call. Advantages: flexible, scalable (add more tools without graph changes), LLM reasons across tools. Disadvantages: LLM may select wrong tool, harder to debug, unpredictable, higher risk in production. Deterministic (Node-Based, Workflow): Each functionality is its own node. Supervisor LLM uses structured output or explicit conditional edges to route between nodes. You control every path manually. Advantages: predictable, auditable, debuggable, safer for regulated/critical flows. Disadvantages: more development effort, less flexible (adding a new operation requires a new node + routing). Sunny's advice: "If you are able to perform this entire thing with the deterministic approach, do it — it is more deterministic, more secure. Use tools only when the LLM should dynamically choose capability."

5. Walk through every step of how the ReAct graph handles the query "(2+2) × 10" — from input to final output.

▶ Show Answer
Step 1: HumanMessage("(2+2) × 10") is passed to StateGraph via invoke(). START → LLM Agent Node. Step 2: LLM reads message + system prompt + all tools. It reasons: "Order of operations: addition first. I'll call the add tool with a=2, b=2." Returns AIMessage(content="", tool_calls=[add(a=2, b=2)]). Step 3: should_continue checks: tool_calls non-empty → return "tools" → routes to ToolNode. Step 4: ToolNode executes add(2, 2) = 4. Returns ToolMessage(content="4"). Appended to state. Step 5: Edge from "tools" → "agent". LLM reads full history (HumanMessage + AIMessage with add call + ToolMessage "4"). Reasons: "add done, result is 4. Now multiply 4 by 10." Returns AIMessage(content="", tool_calls=[multiply(a=4, b=10)]). Step 6: should_continue: tool_calls present → route to ToolNode. ToolNode executes multiply(4, 10) = 40. Returns ToolMessage("40"). Step 7: LLM reads full history (everything + ToolMessage "40"). Reasons: "Task complete. Answer is 40." Returns AIMessage(content="The result of (2 + 2) × 10 is 40."). Step 8: should_continue: no tool_calls → return END. Graph terminates. Final state messages: [HumanMessage, AIMessage(add), ToolMessage(4), AIMessage(multiply), ToolMessage(40), AIMessage("40")].
