A ground-up re-teaching of memory management in AI applications. Starts from first principles (what is memory, why LLMs are stateless), covers the legacy LangChain memory classes, then builds two practical custom Python implementations from scratch: Sliding Window Memory (pass last N messages) and Summary + Recent Memory (LLM-generated summary of old messages + last N live messages). File: memorymanagement.ipynb.

01 — Overview

What This Class Covers

  • ✓ Two definitions of memory — mechanism for retaining conversation history; ability to store, retrieve, and reuse prior interaction
  • ✓ LLM is inherently stateless — without explicit memory, each API call has no knowledge of prior messages
  • ✓ ChatGPT (application) vs GPT (model) — application layers manage memory; raw API does not
  • ✓ 6 reasons to use memory management: continuity, follow-up questions, personalisation, long-running agents, avoid repeated answers, token cost control
  • ✓ Short-term memory (within session/thread) vs Long-term memory (across sessions/threads)
  • ✓ Legacy LangChain memory classes: ConversationBufferMemory, ConversationWindowMemory, ConversationTokenBufferMemory, ConversationSummaryMemory, ConversationSummaryBufferMemory, ConversationEntityMemory
  • ✓ These are deprecated in recent LangChain/LangGraph — understand the concept; implement custom logic

02 — Definitions

What Is Memory?

Definition 1

"Memory is a mechanism that allows AI applications to retain and reuse information from previous interactions."

Definition 2

"Memory in AI is the ability of an application to store, retrieve, and reuse information from previous interactions, so the system can maintain context and provide more consistent, personalised responses."

"Memory is nothing, basically. It is just a conversation history. So, the LLM is looking into that conversation history, and based on that only it is going to reply. LLM is usually stateless by itself. If the previous context is not provided with each new call, the model does not remember the earlier conversation."
🖥️

Application vs Model: ChatGPT (the application, owned by OpenAI) manages memory for you — it stores conversation history and feeds it back to the GPT model on each turn. GPT itself (the raw model) is stateless. Similarly, Claude.ai (Anthropic's application) manages memory; the Claude model itself has no inherent memory. When you call the API directly, you are responsible for managing conversation history. This distinction matters for building your own Agentic applications.

03 — Motivation

Why We Need Memory Management

1. Maintain conversation continuity — follow-up questions reference prior context ("what did I just say?").
2. Handle follow-up questions — "compare it with what I mentioned earlier" requires memory of earlier turns.
3. Personalise responses — remember user preferences and past facts about the user across the conversation.
4. Support long-running Agentic workflows — agents need to know what they have already done across multiple steps.
5. Avoid repeated questions — don't re-generate the same answer on repeated asks; retrieve from memory instead.
6. Reduce token cost — controlled context = fewer tokens per call = lower API cost and lower latency.
04 — Two Types

Short-Term vs Long-Term Memory

Short-Term Memory

  • → Recent messages in the current session
  • → Within a single conversation thread
  • → Lost when the session ends (unless persisted)
  • → LangGraph: Checkpointer (within one thread)
  • → Purpose: continuity within one chat

Long-Term Memory

  • → Information retained across multiple conversations
  • → Across different sessions and threads
  • → User preferences, past facts, past interactions
  • → LangGraph: Store (cross-thread, per-user)
  • → Purpose: personalisation over time
📌

Key note: If you don't persist messages anywhere — whether short-term or long-term — they will be lost when the session ends. The distinction is: short-term uses a checkpointer (saves within one thread); long-term uses a store (saves across threads, keyed by user ID). Both are covered in depth in Class 45.

05 — Legacy Reference

Legacy LangChain Memory Classes

These classes were available in earlier versions of LangChain. They are largely deprecated in recent versions of LangChain/LangGraph. Understanding the concept behind each is more valuable than memorising the API.

from langchain.memory import …
ConversationBufferMemory ← stores full conversation history, passes all of it to LLM
ConversationWindowMemory ← keeps last K turns only (sliding window)
ConversationTokenBufferMemory ← limits by token count, not turn count
ConversationSummaryMemory ← LLM generates running summary; passes summary to LLM
ConversationSummaryBufferMemory ← summary of old + recent buffer (best of both)
ConversationEntityMemory ← extracts and stores named entities across conversation

Status in today's LangGraph: "In the earlier version, these classes were there. In the recent version, basically, you will not be able to find them. Instead, in LangGraph, we have the checkpointer and the store. So we'll understand the concept behind these particular classes, and implement them as custom code — that skill transfers everywhere." 06 — Strategy 1

Buffer Memory — Full History (and Its Problem)

The simplest approach: store every message in a list and pass the entire list to the LLM on every call. This works for short conversations but quickly becomes expensive and slow.

python · buffer memory (naive) 
# Naive buffer memory — pass EVERYTHING to the LLM every turn
from langchain_groq import ChatGroq

llm = ChatGroq(model="llama-3.1-8b-instant")
memory = []   # global list — accumulates ALL messages

def chat(user_input: str) -> str:
    # Add user message to history
    memory.append({"role": "user", "content": user_input})
    # Pass ENTIRE memory to LLM on every call
    response = llm.invoke(memory)
    ai_reply = response.content
    # Add AI response to history
    memory.append({"role": "assistant", "content": ai_reply})
    return ai_reply

# ❌ Problem: after 100 messages, every call sends 100 messages to the LLM.
# → Context window overflows
# → API cost grows linearly with conversation length
# → Latency increases
# → LLM may hallucinate on very long contexts ("lost in the middle" problem)
07 — Strategy 2

Sliding Window Memory

Concept & Worked Example

Store the full conversation history, but only pass the last N messages to the LLM on each call. Older messages are kept in the list (for your records / future archiving) but not sent to the LLM.

"Sliding window memory means we still store the complete conversation. But we are just going to be pass the recent message to the LLM. The stored history can be larger, but the active LLM context should be controlled. If the conversation is going to be very, very long, then ChatGPT might not remember what I asked in the first question — that's because they are just giving some last conversation to the model. That is called the sliding window memory."

Sliding Window Code

python · sliding window memory 
from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

llm = ChatGroq(model="llama-3.1-8b-instant")

memory = []             # full conversation history (every message)
MAX_CONTEXT_MESSAGES = 6  # hyperparameter: number of recent messages to send to LLM
                         # Decide this by analysing your users' conversation patterns

def chat(user_input: str) -> str:
    # 1. Store user message in full history
    memory.append({"role": "user", "content": user_input})

    # 2. Build recent context — last N messages only
    recent_context = memory[-MAX_CONTEXT_MESSAGES:]  # Python list slicing

    # 3. Call LLM with RECENT context only, not full history
    response = llm.invoke(recent_context)
    ai_reply  = response.content

    # 4. Store AI reply in full history
    memory.append({"role": "assistant", "content": ai_reply})

    return ai_reply

def run_chat_loop():
    print("Chat started. Type 'exit' or 'quit' to stop.")
    while True:
        user_input = input("You: ").strip()
        if user_input.lower() in ["exit", "quit"]:
            print("Ending chat.")
            break
        if not user_input:
            continue
        response = chat(user_input)
        print(ff"AI: {response}")
        print(ff"[Full stored messages: {len(memory)}]")
        print(ff"[Messages sent to LLM this turn: {len(memory[-MAX_CONTEXT_MESSAGES:])}]")

run_chat_loop()

# ── Sunny's live demo observations ───────────────────────────────
# After 14 total messages (full history), still only 6 sent to LLM.
# When asked "do you remember my name?" after name was mentioned in
# message 1–2 (now outside the window), LLM could not recall it.
# → Demonstrates loss of early context — the trade-off of this approach.
⚠️

Sliding window trade-off: If the user asks about something mentioned only in an early message that has fallen outside the window, the LLM will not remember it. If M1 and M6 discuss completely different topics, dropping M1 loses that context entirely. This is the limitation that motivates the next strategy: Summary + Recent Memory.

08 — Strategy 3 (Best)

Summary + Recent Memory

Concept & Blackboard Diagram

The most effective approach. Instead of losing old messages, an LLM-generated rolling summary captures their essence. Every LLM call receives: (1) the running summary of old messages, and (2) the last N messages verbatim.

Summary + Recent Memory — Full History=10, max_recent=6
Old messages Q1, Q2, Q3, Q4 → fed to LLM to generate a running summary
Summary "User is named Sunny, loves Python and AI, working on Agentic project…"
Recent msgs Q5, Q6, Q7, Q8, Q9, Q10 (last 6 verbatim)
Sent to LLM every call:
[SystemMessage(content=summary)] + [recent_messages[-6:]]
"Summary plus recent messages — so we can keep the summary of all the messages, of the entire history. And we can basically provide some recent messages also. The benefit of this particular strategy: the summary carries the essence of old messages without the full token cost. The recent messages carry the immediate context verbatim. Together they give the LLM both depth and recency."

Summary + Recent Memory — Full Code

python · summary + recent memory 
from langchain_groq import ChatGroq

llm = ChatGroq(model="llama-3.1-8b-instant")

# ── Global state ──────────────────────────────────────────────────
summary_memory      = []   # last N messages (recent context for LLM)
conversation_summary = ""  # rolling LLM-generated summary of old messages
full_history        = []   # complete conversation record (for audit/display)
MAX_RECENT_MESSAGES = 6   # hyperparameter — analyze user behavior to tune

# ── Create or update the rolling summary ─────────────────────────
def create_summary(old_summary: str, old_messages: list) -> str:
    """
    Uses the LLM to generate a concise summary of old messages.
    Builds on the previous summary (cumulative).
    """
    if not old_messages:
        return old_summary

    # Convert old messages list to readable text
    conversation_text = ""
    for msg in old_messages:
        role    = msg["role"].capitalize()
        content = msg["content"]
        conversation_text += ff"{role}: {content}\n"

    # Build the summarisation prompt
    summary_prompt = ff"""You are a conversation summariser.
Previous Summary: {old_summary if old_summary else "No previous summary available."}

New Conversation to Summarise:
{conversation_text}

Task: Create a concise, updated summary that incorporates both the previous summary 
and the new conversation. Preserve all important facts, user preferences, and context.
Keep it under 200 words. Return ONLY the updated summary."""

    response = llm.invoke([{"role": "user", "content": summary_prompt}])
    return response.content

# ── Compress memory when it exceeds the limit ─────────────────────
def compress_memory():
    """
    Called when summary_memory exceeds MAX_RECENT_MESSAGES.
    Splits into old_messages (to summarise) and recent_messages (to keep verbatim).
    """
    global summary_memory, conversation_summary

    if len(summary_memory) <= MAX_RECENT_MESSAGES:
        return   # nothing to compress yet

    # Separate old messages from recent ones
    old_messages    = summary_memory[:-MAX_RECENT_MESSAGES]   # everything before the window
    recent_messages = summary_memory[-MAX_RECENT_MESSAGES:]   # last N messages

    # Summarise old messages using LLM
    conversation_summary = create_summary(conversation_summary, old_messages)

    # Replace summary_memory with only the recent messages
    summary_memory = recent_messages

# ── Main chat function ────────────────────────────────────────────
def chat(user_input: str) -> str:
    """Process user input with Summary + Recent Memory approach."""
    global summary_memory, full_history, conversation_summary

    # 1. Create user message
    user_message = {"role": "user", "content": user_input}

    # 2. Add to both tracking lists
    summary_memory.append(user_message)
    full_history.append(user_message)

    # 3. Build message list for LLM
    # System message injects the running summary
    system_content = ff"""Previous Conversation Summary:
{conversation_summary if conversation_summary else "No previous summary available."}

You are a helpful assistant. Use the summary above for context about earlier in our conversation."""

    messages_for_llm = [{"role": "system", "content": system_content}] + summary_memory

    # 4. Get LLM response
    response = llm.invoke(messages_for_llm)
    ai_reply  = response.content

    # 5. Store AI reply
    assistant_message = {"role": "assistant", "content": ai_reply}
    summary_memory.append(assistant_message)
    full_history.append(assistant_message)

    # 6. Compress memory if it's grown too large
    compress_memory()

    return ai_reply

# ── Chat loop ─────────────────────────────────────────────────────
def run_chat_loop():
    print("Chat with Summary Memory. Type 'exit' to quit.")
    while True:
        user_input = input("You: ").strip()
        if user_input.lower() in ["exit", "quit"]:
            break
        if not user_input:
            continue
        response = chat(user_input)
        print(ff"AI: {response}\n")
        print(ff"[Full history: {len(full_history)} msgs | Recent window: {len(summary_memory)} msgs]")
        print(ff"[Current summary: {conversation_summary[:100]}...]" if conversation_summary else "[No summary yet]")

run_chat_loop()

How create_summary() Works — Sunny's Blackboard

Summary generation — incremental approach
Turn 1–6: All fit in recent window. No summary needed yet.
Turn 7 (exceeds 6): Q1 becomes "old message". create_summary("", [Q1]) → first summary generated.
Turn 8: Q2 becomes "old message". create_summary(prev_summary, [Q2]) → summary updated to include Q2.
Each subsequent turn: Old summary is passed alongside newly-old messages → LLM generates an enriched cumulative summary. The summary grows in depth but NOT in length (prompt instructs ≤ 200 words).
09 — Key Method

compress_memory() — When It Fires

python · compress_memory() logic explained 
# compress_memory() fires AFTER every chat() call.
# It only does work when len(summary_memory) > MAX_RECENT_MESSAGES.

# Example walkthrough (MAX_RECENT_MESSAGES = 6):

# After turn 6:  summary_memory has 12 messages (6 user + 6 AI)
#                len(12) > 6 → compress!
#                old_messages = summary_memory[:-6]  → first 6 messages
#                recent_messages = summary_memory[-6:] → last 6 messages
#                → LLM summarises old_messages
#                → summary_memory is replaced with recent_messages only

# After turn 7:  summary_memory grows to 8 (6 recent + 2 new)
#                len(8) > 6 → compress again
#                Oldest 2 messages get summarised and added to summary

# Key insight:
# full_history  = ALWAYS grows — every message saved
# summary_memory = BOUNDED — never exceeds ~2×MAX_RECENT_MESSAGES
# conversation_summary = updated by LLM each compression cycle

# Why global variable for conversation_summary?
# → needs to be accessible across both chat() and compress_memory() calls
# → "global" keyword makes a Python variable accessible across functions
# → in production: replace with class state (self.summary) for cleanliness
10 — Core Concept

LLM Statelessness — Why This Matters

── Without memory (stateless) ────────────────────────────────────

User: What is my name?          ← new API call, no context provided

── With memory (context provided) ───────────────────────────────

# memory now contains both messages above

AI:   That's exciting!

# later...
User: What project am I working on?
AI:   You mentioned you are working on Agentic AI.  ← memory recalled correctly

11 — Decision Guide

Which Memory Strategy for Which Use Case?

Memory Strategy Selection
Buffer Memory — short conversations only (<10 messages), testing, POC. Not for production.
Sliding Window — conversations where only recent context matters (real-time Q&A, customer support). Risk: old facts forgotten.
Summary + Recent (recommended) — long conversations where history matters (personal assistants, coaching bots, long-running Agentic workflows). Best balance of context depth and token cost.
Note: All three are custom Python implementations. In LangGraph, the Checkpointer + InMemoryStore pattern (Class 45) provides the same capabilities natively.
12 — Q&A

Q&A Highlights

Q — Kumar
If the session ends, do the messages get lost?
A — Sunny
Yes — if you are not persisting those messages anywhere, they will be lost. Whether it's short-term memory or long-term memory, if you're not storing to a database, they exist only in Python memory (RAM) for the duration of the process. When the process ends, they are gone. That's why in the next class (Class 45) we discuss LangGraph's checkpointer with SQLite — persisting the conversation to disk so it survives restarts.
Q — Sathish Kumar
How do you decide the value of max_context_messages? Is there a formula?
A — Sunny
There is no formula — it is a hyperparameter. "This number completely depends on the user application. As an AI developer, you will have to analyze that particular application, the behavior of the user — how user is asking the question, how many messages user is writing inside a single chat thread. After analyzing all those parameters only, you decide this particular parameter. As of now I've just written 6 as a random value for demonstration."
Q — Bala
Should each user message be counted as one "message" in the memory list, or should a full user+AI exchange be one unit?
A — Sunny
In the demo, each individual message (user or AI) is one unit in the list. So one conversation turn = 2 messages (1 user + 1 AI). You can write custom logic to group them as pairs (one conversation turn = one unit) — both approaches are valid depending on how you want to count. The important thing is consistency: pick one convention and apply it everywhere in your code.
Q — Student
Can we store the conversation history permanently (cold history / archive)?
A — Sunny
Yes — you can store as much history as your database capacity allows. Some history can be "recent history" (actively used by the LLM), some can be "cold history" (archived, not passed to the LLM but available for retrieval). You can maintain the conversational history with summary + recent messages for active use, while capturing the entire history in a separate database table for archiving. How much to archive depends on your storage costs and compliance requirements.
13 — Self-Check

Quiz — Test Your Understanding

📝 Class 44 Concept Check

1. Why is an LLM described as "stateless"? How does memory address this?

▶ Show Answer
An LLM is stateless because each API call is independent — the model has no inherent memory of previous calls. If you call the API twice, the second call knows nothing about the first unless you explicitly include that history in the new request. Memory addresses this by maintaining a conversation history list in your application code. On each new turn you pass the history (all or some of it) alongside the new user message, so the LLM has the context of prior exchanges and can answer follow-up questions, maintain persona, and build on earlier statements.

2. What is the difference between sliding window memory and summary + recent memory? What problem does each solve, and what problem does each introduce?

▶ Show Answer
Sliding window: store full history, pass only last N messages to LLM. Solves: context window overflow and token cost. Introduces: loss of early context — if user mentioned their name in message 1 and you're now at message 20 with window=6, the LLM has forgotten the name. Summary + Recent: LLM generates a running cumulative summary of old messages; pass [summary as system message] + [last N messages] to LLM. Solves: loss of early context (captured in summary). Introduces: extra LLM call cost for summary generation; summary may lose fine-grained details; slightly more complex implementation. Summary + Recent is Sunny's recommended production approach for long conversations.

3. When does compress_memory() fire, and what does it do?

▶ Show Answer
compress_memory() fires after every chat() call. If len(summary_memory) ≤ MAX_RECENT_MESSAGES: nothing happens. If len(summary_memory) > MAX_RECENT_MESSAGES: it splits summary_memory into old_messages (everything except the last N) and recent_messages (last N). It calls create_summary(old_summary, old_messages) to generate an updated LLM summary that incorporates the old messages. Then it replaces summary_memory with just the recent_messages. After compression: summary_memory always contains ≤ MAX_RECENT_MESSAGES messages; full_history always contains everything. The conversation_summary grows richer over time but stays bounded in length (prompt constrains it to ≤ 200 words).

4. What is the role of the global conversation_summary variable, and why did Sunny use the Python global keyword?

▶ Show Answer
conversation_summary is the LLM-generated rolling summary of all old messages — the "long-term" component of the Summary + Recent Memory strategy. It starts as an empty string and grows incrementally each time compress_memory() fires. The global keyword in Python makes a variable defined at module level accessible and modifiable from inside a function. Without it, assigning to conversation_summary inside compress_memory() would create a new local variable, not update the module-level one. Sunny used global for simplicity in the demo; in production code this would be a class attribute (self.conversation_summary) which is cleaner and avoids the global keyword entirely.
