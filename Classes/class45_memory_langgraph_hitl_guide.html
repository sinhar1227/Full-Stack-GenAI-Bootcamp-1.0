Memory is added to the generation step. The retrieval step finds relevant documents from the vector DB; the generation step combines those documents with the conversation history to produce a contextually aware answer.

Approach 1 — Simple Memory in RAG

Pass the full conversation history to the LLM alongside retrieved documents. Works for short sessions; same problem as buffer memory (grows without bound).

python · simple RAG memory 
def generate_answer(query: str, retrieved_docs: list, memory: list) -> str:
    """RAG generation with simple (full) memory."""
    # Build memory text from full history
    memory_text = ""
    for msg in memory:
        role    = msg["role"].capitalize()
        content = msg["content"]
        memory_text += ff"{role}: {content}\n"
    if not memory_text:
        memory_text = "No previous conversation."

    # Build document context
    doc_text = " ".join(retrieved_docs) if retrieved_docs else "No relevant documents found."

    # Prompt: history + retrieved context + current query
    prompt = ff"""Previous Conversation:
{memory_text}

Retrieved Context from Knowledge Base:
{doc_text}

Current Question: {query}

Answer based on both the conversation history and the retrieved context."""

    response = llm.invoke([{"role": "user", "content": prompt}])
    return response.content

RAGAssistant + ConversationMemory — Code

python · OOP RAG memory design 
from langchain_groq import ChatGroq
from langchain_community.vectorstores import FAISS
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_core.documents import Document

# ── ConversationMemory class — decoupled memory handler ────────────
class ConversationMemory:
    def __init__(self, model, max_recent_messages: int = 6):
        self.model               = model
        self.max_recent_messages = max_recent_messages
        self.memory              = []   # recent window
        self.summary             = ""  # rolling summary
        self.full_history        = []   # complete record

    def add_message(self, role: str, content: str):
        """Append a message to both memory and full history."""
        msg = {"role": role, "content": content}
        self.memory.append(msg)
        self.full_history.append(msg)

    def get_context(self) -> str:
        """Return the summary + recent messages as a formatted string."""
        context = ""
        if self.summary:
            context += ff"[Conversation Summary]: {self.summary}\n\n"
        for msg in self.memory:
            context += ff"{msg['role'].capitalize()}: {msg['content']}\n"
        return context or "No previous conversation."

    def _create_summary(self, old_messages: list) -> str:
        if not old_messages:
            return self.summary
        conv_text = "\n".join(ff"{m['role']}: {m['content']}" for m in old_messages)
        prompt = ff"""Update the conversation summary.
Previous Summary: {self.summary or "None."}
New Conversation: {conv_text}
Write an updated concise summary (max 200 words). Return ONLY the summary."""
        response = self.model.invoke([{"role": "user", "content": prompt}])
        return response.content

    def compress(self):
        """Compress if recent window exceeds threshold."""
        if len(self.memory) <= self.max_recent_messages:
            return
        old      = self.memory[:-self.max_recent_messages]
        self.memory   = self.memory[-self.max_recent_messages:]
        self.summary  = self._create_summary(old)

# ── RAGAssistant class — full RAG pipeline with memory ────────────
class RAGAssistant:
    def __init__(self, model, retriever, max_recent_messages: int = 6):
        self.model      = model
        self.retriever  = retriever
        self.conv_memory = ConversationMemory(model, max_recent_messages)

    def chat(self, user_query: str) -> str:
        # 1. Add user message to memory
        self.conv_memory.add_message("user", user_query)

        # 2. Rewrite query using conversation context (standalone query)
        context  = self.conv_memory.get_context()
        standalone_prompt = ff"""Given this conversation:
{context}

Rewrite the latest user question as a standalone question 
that doesn't need the conversation context to make sense.
Return ONLY the rewritten question."""
        standalone = self.model.invoke([{"role": "user", "content": standalone_prompt}]).content

        # 3. Retrieve relevant documents
        docs = self.retriever.invoke(standalone)
        doc_text = " ".join(d.page_content for d in docs) if docs else "No relevant documents."

        # 4. Generate answer using memory + retrieved docs
        gen_prompt = ff"""Conversation History:
{context}

Retrieved Knowledge Base Context:
{doc_text}

Current Question: {user_query}
Answer using both the conversation history and the retrieved context."""
        answer = self.model.invoke([{"role": "user", "content": gen_prompt}]).content

        # 5. Add AI answer to memory and compress if needed
        self.conv_memory.add_message("assistant", answer)
        self.conv_memory.compress()

        return answer

# ── Usage ─────────────────────────────────────────────────────────
llm       = ChatGroq(model="llama-3.1-8b-instant")
embedding = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")
texts     = ["Employees receive 20 annual leaves...", "Probation period is 3 months..."]
vdb       = FAISS.from_texts(texts, embedding)
retriever = vdb.as_retriever(search_kwargs={"k": 3})

assistant = RAGAssistant(llm, retriever, max_recent_messages=6)
print(assistant.chat("How many annual leaves do employees receive?"))
print(assistant.chat("And what are the carry-forward rules?"))  # uses memory
print(assistant.chat("After completing probation, what benefits become available?"))

Checkpointer — Short-Term Memory

The Checkpointer saves graph state at the end of every node execution within a single thread. It gives the agent memory of the current conversation session. Two implementations:

MemorySaverlanggraph.checkpoint.memoryIn RAM❌ Lost on restart
SqliteSaverlanggraph.checkpoint.sqliteSQLite file✅ Survives restarts

The Store persists information keyed by user_id, accessible across all of that user's threads. Two implementations:

Full LangGraph Memory Graph Code

python · LangGraph memory graph 
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.store.memory import InMemoryStore
from langchain_groq import ChatGroq
from pydantic import BaseModel, Field
from typing import Annotated, List
import uuid

llm = ChatGroq(model="llama-3.1-8b-instant")

# ── Short-term memory: MemorySaver (in-memory checkpointer) ───────
checkpointer = MemorySaver()
# For persistence: from langgraph.checkpoint.sqlite import SqliteSaver
# import sqlite3
# conn = sqlite3.connect("checkpoint.db", check_same_thread=False)
# checkpointer = SqliteSaver(conn)

# ── Long-term memory: InMemoryStore ───────────────────────────────
store = InMemoryStore()
# For persistence: custom SQLiteLongTermMemory class (see below)

# ── Pydantic schema for extracted memory ─────────────────────────
class Memory(BaseModel):
    memory: List[str] = Field(
        default_factory=list,
        description="List of important facts to remember about the user"
    )

memory_extractor = llm.with_structured_output(Memory)

# ── Helper: extract memories from message ─────────────────────────
def extract_memory(user_message: str) -> Memory:
    prompt = ff"""Extract important facts to remember from this message.
User: {user_message}
Extract: name, preferences, goals, context, any important facts.
Return as a list of strings."""
    return memory_extractor.invoke([{"role": "user", "content": prompt}])

# ── Node 1: Chatbot node ─────────────────────────────────────────
def chatbot(state: MessagesState, config: dict, *, store) -> dict:
    """Chat with long-term memory retrieval."""
    user_id = config["configurable"].get("user_id", "default_user")

    # Retrieve user's long-term memory from store
    memories = store.search(("memory", user_id))
    memory_context = ""
    if memories:
        memory_context = "Known about user:\n" + "\n".join(
            ff"- {m.value['fact']}" for m in memories
        )

    messages = state["messages"]
    full_msgs = []
    if memory_context:
        from langchain_core.messages import SystemMessage
        full_msgs.append(SystemMessage(content=memory_context))
    full_msgs.extend(messages)

    response = llm.invoke(full_msgs)
    return {"messages": [response]}

# ── Node 2: Save memory node ──────────────────────────────────────
def save_memory(state: MessagesState, config: dict, *, store) -> dict:
    """Extract facts from latest user message and save to long-term store."""
    user_id      = config["configurable"].get("user_id", "default_user")
    messages     = state["messages"]
    last_human   = [m for m in messages if m.type == "human"]

    if not last_human:
        return {}

    extracted = extract_memory(last_human[-1].content)
    for fact in extracted.memory:
        # store.put(namespace, key, value)
        store.put(
            namespace = ("memory", user_id),       # keyed by user_id
            key       = str(uuid.uuid4()),
            value     = {"fact": fact}
        )
    return {}

# ── Build graph ───────────────────────────────────────────────────
builder = StateGraph(MessagesState)
builder.add_node("chatbot",    chatbot)
builder.add_node("save_memory", save_memory)
builder.add_edge(START,        "chatbot")
builder.add_edge("chatbot",   "save_memory")
builder.add_edge("save_memory", END)

# Compile with BOTH checkpointer (short-term) and store (long-term)
graph = builder.compile(checkpointer=checkpointer, store=store)

# ── Test with two threads for same user ──────────────────────────
user_id = "sunny123"

# Thread 1: introduce name and interest
config1  = {"configurable": {"thread_id": "t1", "user_id": user_id}}
result1  = graph.invoke({"messages": [{"role": "user", "content": "My name is Sunny."}]}, config1)
print(result1["messages"][-1].content)

# Thread 2 (NEW THREAD — simulates "New Chat"): long-term memory carries over
config2  = {"configurable": {"thread_id": "t2", "user_id": user_id}}
result2  = graph.invoke({"messages": [{"role": "user", "content": "What is my name?"}]}, config2)
print(result2["messages"][-1].content)
# → "Your name is Sunny." — because long-term store carries the fact across threads

# Short-term memory check within same thread:
# result in t2 does NOT know what Sunny said in t1 short-term
# But LONG-term store (keyed by user_id) carries the name fact across both threads

06 — Persistence

SQLite Persistence for Memory

python · SQLite persistence for both memory types 
import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

# ── Short-term memory: SqliteSaver checkpointer ───────────────────
# Creates checkpoint.db in current directory
conn_checkpoint = sqlite3.connect("checkpoint.db", check_same_thread=False)
checkpointer    = SqliteSaver(conn_checkpoint)

# ── Long-term memory: custom SQLiteLongTermMemory ─────────────────
class SQLiteLongTermMemory:
    """Persistent long-term memory using SQLite database."""

    def __init__(self, db_path: str = "longterm.db"):
        self.conn = sqlite3.connect(db_path, check_same_thread=False)
        self._create_table()

    def _create_table(self):
        self.conn.execute("""
            CREATE TABLE IF NOT EXISTS memories (
                id        TEXT PRIMARY KEY,
                user_id   TEXT NOT NULL,
                fact      TEXT NOT NULL,
                created   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
            )""")
        self.conn.commit()

    def save_memory(self, user_id: str, fact: str):
        import uuid
        self.conn.execute(
            "INSERT INTO memories (id, user_id, fact) VALUES (?, ?, ?)",
            (str(uuid.uuid4()), user_id, fact)
        )
        self.conn.commit()

    def get_memories(self, user_id: str, limit: int = 5) -> list[str]:
        cursor = self.conn.execute(
            "SELECT fact FROM memories WHERE user_id=? ORDER BY created DESC LIMIT ?",
            (user_id, limit)
        )
        return [row[0] for row in cursor.fetchall()]

    def add_memory(self, user_id: str, fact: str):
        self.save_memory(user_id, fact)

09 — New Topic (Preview)

Human-in-the-Loop (HITL)

Introduced briefly at the end of Class 45. The full walkthrough is scheduled for the next class (Class 46). Code in: class45/human_loop.ipynb.

🧑‍💻

What is HITL? Human-in-the-Loop means pausing a LangGraph workflow at a specific node to require human approval or input before continuing. This is critical in production Agentic systems where certain actions are irreversible (e.g. sending an email, executing a database write, making an API call with side effects). The human inspects the state, approves or rejects, then the graph continues.

python · Human-in-the-Loop preview 
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver

def draft_action(state): ...   # prepares a potentially risky action
def execute_action(state): ... # actually executes the risky action

builder = StateGraph(MessagesState)
builder.add_node("draft",   draft_action)
builder.add_node("execute", execute_action)
builder.add_edge(START,     "draft")
builder.add_edge("draft",  "execute")
builder.add_edge("execute", END)

checkpointer = MemorySaver()

# interrupt_before tells LangGraph to PAUSE before "execute" runs
# and wait for a human to approve via graph.update_state() before continuing
graph = builder.compile(
    checkpointer      = checkpointer,
    interrupt_before  = ["execute"]   # ← pause before execute node
    # interrupt_after = ["draft"]    ← alternatively: pause after draft completes
)

config = {"configurable": {"thread_id": "approval_thread"}}

# Step 1: Run graph → pauses before "execute"
state = graph.invoke({"messages": [...]}, config)
print("Graph paused. Review state:", state)

# Step 2: Human inspects state, approves
# In a real app, this could be a UI button click, Slack message, etc.
human_approval = input("Approve? (yes/no): ")

# Step 3: Resume if approved
if human_approval.lower() == "yes":
    graph.invoke(None, config)   # pass None to resume from where it stopped
else:
    print("Action cancelled by human.")

# Key facts about HITL:
# - interrupt_before = ["node_name"] pauses BEFORE that node runs
# - interrupt_after  = ["node_name"] pauses AFTER that node runs
# - Graph state is saved by checkpointer at the pause point
# - graph.invoke(None, config) continues from the exact checkpoint

Q&A Highlights

Q — Bala
In production, how do you handle 1 million messages in long-term memory? You can't just set limit=5.
A — Sunny
At that scale, you'll have a separate team dedicated to memory management infrastructure. The architecture scales: instead of InMemoryStore, use a distributed database (Postgres, Redis cluster) that can handle billions of records. For retrieval, use semantic search over a vector database so you don't retrieve by recency alone but by relevance to the current query. "You will understand the solution once you look at the architecture — limit and all, you can decide just by understanding the solution." For production RAG memory at scale, the Memory-Augmented RAG assignment shows the pattern.
Q — Student
What is semantic memory?
A — Sunny
Semantic memory is memory that you retrieve not by ID or recency but by semantic relevance to the current query. You store memories as embeddings in a vector database. When a new question comes in, you embed the question and retrieve the most semantically similar memories — facts the user told you in the past that are relevant to the current topic. "It's like based on the retrieval context, actually. So around to that, also, we can build the memory." This is one of the 4 memory types in the Memory-Augmented RAG assignment.
Q — Student
How does LangGraph's checkpointer relate to what we implemented manually in Class 44?
A — Sunny
They achieve the same goal — maintaining conversation context within a session — but the checkpointer is built into LangGraph and works automatically. In Class 44, you had to manually: (1) append messages to a list, (2) pass the recent slice to the LLM, (3) update the global list. With LangGraph's MemorySaver checkpointer, this is handled for you: the MessagesState accumulates all messages, and the checkpointer saves the full state after every node. The thread_id configuration key tells LangGraph which conversation's state to restore on the next call. The add_messages reducer in MessagesState is the equivalent of your manual append logic.
Q — Vikas
Why is the Groq API taking 1–2 minutes to respond in my RAG system?
A — Sunny
Groq should respond in a fraction of a second or at most 10–15 seconds, not 1–2 minutes. The bottleneck is almost certainly not the LLM API but the retrieval step. Debug by: (1) manually pass a prompt directly to the Groq LLM and check if it responds fast → if yes, the LLM is fine. (2) Manually run the retriever step and measure how long it takes → that's where the delay is. Likely you're running a local Llama model via Ollama in the retrieval or embedding step, which is slow on 12GB RAM. Switch to Qdrant Cloud (free tier) + Groq API to eliminate local model overhead entirely.

📝 Class 45 Concept Check

1. In LangGraph, what is the difference between a Checkpointer and a Store? What type of memory does each handle?

▶ Show Answer
Checkpointer handles short-term memory — it saves the graph state (including all messages) after every node execution, scoped to a specific thread_id. If you call graph.invoke() again with the same thread_id, the checkpointer restores the prior state so the conversation continues seamlessly. Examples: MemorySaver (in-memory, lost on restart), SqliteSaver (SQLite file, persists). Store handles long-term memory — it stores arbitrary key-value facts keyed by user_id, accessible across all threads for that user. When a user starts a new conversation (new thread_id), the store still holds facts from prior sessions. Examples: InMemoryStore (lost on restart), custom SQLiteLongTermMemory. The graph is compiled with both: builder.compile(checkpointer=checkpointer, store=store). Sunny's one-liner: "Checkpointer = thread-specific (short-term). Store = user-specific, cross-thread (long-term)."

2. Explain the thread_id / user_id relationship using the ChatGPT analogy. What is "long-term memory" in this context?

▶ Show Answer
Analogy: ChatGPT user "Sunny123" has one user_id (Sunny123). Every time Sunny clicks "New Chat" in the sidebar, a new thread_id is created (t1, t2, t3...). Short-term memory (checkpointer) is scoped to ONE thread — in thread t1, the LLM remembers everything said in that chat. In thread t2 (new chat), the short-term memory is fresh — the LLM has no idea what was said in t1. Long-term memory (store) is scoped to the user_id and shared across ALL threads for that user. If Sunny told the system his name in t1, the store saved "user is named Sunny" under the key (memory, sunny123). When Sunny opens t2 and asks "what is my name?", the chatbot node retrieves from the store using user_id and correctly answers "Sunny" — even though t2 has no message history from t1.

3. What is Human-in-the-Loop in LangGraph, and how does interrupt_before work?

▶ Show Answer
Human-in-the-Loop (HITL) is a mechanism to pause a LangGraph workflow at a specified node, allowing a human to review the graph state, approve or reject the planned action, and then decide whether to continue. It's critical for actions with side effects (sending emails, database writes, calling external APIs). interrupt_before=["node_name"] tells LangGraph to pause BEFORE the named node runs. The graph saves its current state via the checkpointer. When graph.invoke() is called and hits the interrupt: execution pauses and returns the current state. A human (or a UI) inspects the state. If approved: graph.invoke(None, config) resumes from the exact checkpoint — the interrupted node now runs. If rejected: the human can modify the state with graph.update_state() or simply not resume. interrupt_after=["node_name"] pauses AFTER the node completes. Full walkthrough scheduled for Class 46.

4. What are the 4 memory types in the Memory-Augmented RAG Assignment? What database is recommended for each?

▶ Show Answer
(1) Short-term memory — session context within one conversation. Database: Redis (production) or SQLite (development). Implementation: LangGraph checkpointer. (2) Long-term memory — user facts persisted across sessions, keyed by user_id. Database: Postgres (production) or SQLite (development). Implementation: LangGraph store / SQLiteLongTermMemory. (3) Semantic memory — facts retrieved by semantic similarity to the current query using embeddings. Database: vector database (Qdrant, Chroma, FAISS, Pinecone). Implementation: embed facts and store in vector DB; query by similarity at retrieval time. (4) RAG knowledge base — domain documents for answering queries. Database: vector database. Implementation: the standard RAG pipeline (ingest → embed → store → retrieve → generate). All 4 are combined in the assignment to build a production-ready Agentic RAG system inspired by Sunny's real-time project.
